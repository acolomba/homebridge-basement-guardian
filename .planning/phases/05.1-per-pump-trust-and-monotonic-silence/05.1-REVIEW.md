## Summary

This phase splits monitoring trust per pump (`shadowSilent` moves from `TransportTrust` to a
per-device `MonitoringTrust`, resolved by `monitoringTrustByDevice`), measures live-path silence
against a new monotonic-plus-wall-clock pair that survives both a wall-clock correction and a
process restart (`monotonicClock.ts`, `arrivalAnchors.ts`, `silenceElapsedMs`), and renders the
lost-controller-link warning from the accessory's own published service list instead of a fixed
five-word phrase.

I read every file in scope in full, traced the call chains across `accountRuntime.ts` ->
`monitoringHealth.ts` -> `platform.ts` -> `basementGuardian.ts`, and cross-checked the Cucumber
feature file and its support code against the unit-level behavior. I additionally ran the
project's own verification gates rather than trusting that they had been run:

- `npx tsc --noEmit` — clean.
- `npx eslint <every file in scope> --max-warnings=0` — clean.
- `node --test` with `--experimental-test-coverage` at 100% lines/branches/functions, run
  **directly** against each changed source-test pair alone (`monotonicClock`, `arrivalAnchors`,
  `monitoringHealth`, `failureLog`, `accountRuntime`, `accessories/basementGuardian`, `platform`)
  — all 100.00/100.00/100.00.

I specifically hunted for the failure modes this kind of change invites: a per-device fact
collapsed back to a single account-wide boolean somewhere on the write path (checked every call
site of `MonitoringTrust`/`TransportTrust` end to end); a stray shadow message after a device
removal resurrecting the in-memory arrival stamp or the persisted anchor (traced the new
`options.store.deviceIds().includes(deviceId)` guard and its accompanying regression tests); an
anchor write racing a rename or leaving an orphaned temp file (traced `storeAnchors`'s `wx` +
rename + `rm`-on-failure sequence and its negative-path test); and the wall-vs-monotonic max()
in `silenceElapsedmS` being invertible by a mutation (the surrounding comment names the exact
mutation it guards and the test suite pins both directions explicitly). None of these turned up
a defect. Both the production reasoning comments and the test titles consistently name the actual
edge case being pinned rather than a vague description, and I did not find a test whose assertion
would still pass under a plausible wrong implementation (e.g., the two-pump silence tests assert
the *unaffected* pump's list membership and log-line absence in the same case as the affected
pump's, which is exactly the case a per-device/account-wide regression would flip).

The one item below is an informational note about a pre-existing (not introduced by this phase)
gap in the Cucumber harness that is adjacent to this phase's restart/silence work but is not
currently exercised by any scenario in a way that would hide a regression.

### IN-01: `watchedDeviceIds` is not cleared across a harness restart, silently disabling change-notification tracking for a redevice-scanned deviceId

**File:** `features/support/world.ts:208, 416-421, 737-757`
**Issue:** `restartPlugin()` discards `this.accountRuntime` and builds a brand-new
`AccountRuntime` (with a brand-new `DeviceStateStore`), but does not clear
`this.watchedDeviceIds`. `watchDevices()` only calls `store.subscribe(deviceId, ...)` for a
`deviceId` not already in `watchedDeviceIds`. After a restart, a `deviceId` the pre-restart run
already watched is skipped on the post-restart store even though that store is a different object
with no listener registered on it at all — so `this.changes` (and any future step built on it)
would silently stop reporting post-restart canonical changes for that device. This is pre-existing
harness code (not touched by this phase's diff) and is not currently reached by any scenario:
every restart scenario in `degradedOperation.feature` asserts through direct `store.snapshot(...)`
reads or characteristic reads, never through the "the plugin reports N canonical changes" step, so
no scenario is silently passing against this gap today. Flagging it because this phase adds
several restart-adjacent scenarios and a future restart scenario that reused the existing
"canonical changes" step would pass or fail for the wrong reason.
**Fix:** Clear the set in `restartPlugin()` alongside resetting `this.accountRuntime`:
```ts
async restartPlugin(): Promise<void> {
  await this.stopPlugin();
  this.accountRuntime = undefined;
  this.watchedDeviceIds.clear();
  this.starting = this.launch();
  await this.starting;
}
```
