### Locked Decisions

**Per-device trust signal (entry 19)**

- **D-01:** `onMonitoringHealth` becomes map-valued — `ReadonlyMap<deviceId, MonitoringTrust>`.
  The runtime resolves per-device trust and `applyMonitoringHealth` looks each accessory up.
  Chosen over keeping one account-wide struct beside a `silentDeviceIds` list, which is a
  smaller diff but leaves the callback saying something other than what it means.
  `MonitoringTrust` itself is unchanged, so `markMonitoring`, `monitoringDegradedScopes` and
  every accessory-tier trust literal stay as they are; the churn is in `src/platform.ts`,
  `src/runtime/accountRuntime.ts`, `features/support/world.ts` and the runtime tests.
  — **Reversibility:** costly — the signature is bound by the platform, the Cucumber harness
  and the runtime test suite, so undoing it touches all four call sites at once.

- **D-02:** An accessory with no per-device answer reads **silent**. A device admitted after
  the last push, or an accessory restored from cache before discovery completes, does not
  vouch. This follows the project constraint that unknown never becomes a normal default,
  and it matches `RES-04`, which already marks every restored service stale until a poll
  succeeds. Explicitly not chosen: falling back to the old any-pump-silent boolean, which
  would reintroduce the flatten on the path most likely to be hit at startup.

- **D-03:** The flatten at `src/runtime/monitoringHealth.ts:212`
  (`shadowSilent: silentDevices().length > 0`) is removed. `silentDevices()` already answers
  per device and needs no new tracking.

- **D-04:** Marking breadth still follows the cause, not the transport. `shadowSilent` and
  `controllerLinkLost` become per-pump; `restDegraded` and `credentialsRejected` stay
  account-wide, because those causes genuinely do affect every pump. This is the Phase 5
  ruling restated, not a new decision.

**Controller-link diagnostic (entry 6)**

- **D-05:** The log message is **derived from the marked set** rather than hand-written, so
  it cannot drift from behaviour by construction. A test still pins the rendering. Not
  chosen: a static sentence naming all 16 with a drift test, and logging at seven-scope
  granularity instead of naming services.

**Monotonic silence (entry 14 / IN-03)**

- **D-06:** A **separate `MonotonicClock` port**, injected where silence is measured.
  `Clock.now()` stays honest wall-clock for receipt times and for anything persisted, and the
  two time bases cannot be confused at a call site. Not chosen: adding `monotonicNow()` to
  the existing `Clock` (one interface carrying two incompatible bases), and clamping
  `systemClock.now()` forward-only (smallest diff, but it silently changes what `now()` means
  for persisted receipt timestamps and would swallow a real wall-clock correction).
  — **Reversibility:** costly — a second port is wired at the composition root and threaded
  to every silence measurement; undoing it means re-deriving which call sites wanted which
  time base.

- **D-07:** A wall-clock arrival anchor **is persisted**, and it is **clamped so it can only
  ever report silence sooner, never later**. Across a restart the anchor may lengthen a
  silence window and may never shorten one, so a backwards wall-clock jump cannot hide a
  dead pump — the failure IN-03 exists to close, kept closed on the restart path too.

- **D-08:** Nothing persists shadow-arrival times today. Measured during discussion:
  `AccessoryContext` in `src/persistence/accessoryContext.ts` carries `primaryPump`,
  `backupPump`, `watermarks` and `lastVendorName`, and no arrival timestamp exists anywhere
  in `src/`. D-07 therefore adds a new persisted field, and an install predating it carries
  no anchor and falls through to D-02 — silent until told otherwise.
  — **Reversibility:** one-way — the field enters `accessory.context`, which is written to
  Homebridge's cached accessory store on real installs. Removing it later needs a migration
  path for installs that already carry it, the same shape `PumpObservation` already has.

## Summary

This phase changes three things in code and records one ruling. Nothing here needs a new dependency,
a new framework, or an external service. All six research questions were answerable from the
repository and from two locally installed Node runtimes, and four of them turned up a premise in the
phase's own inputs that does not survive measurement.

The three code changes are each small at their core and each carry one non-obvious hazard.
**Per-device trust** is a two-line change in `monitoringHealth.ts` surrounded by a signature change
that touches 105 references across 8 files — and it has an unhandled case: on a launch the vendor
refused before the first inventory, a `ReadonlyMap<deviceId, MonitoringTrust>` is **empty**, and the
credential-rejection pass that makes restored accessories unreadable currently reads
`trust.credentialsRejected` from the single struct. An empty map deletes that behaviour silently, and
one shipped unit case (`test/platform.test.ts:1259`) exists precisely to hold it. **The derived
controller-link message** is straightforward once the right unit is chosen: the message must name the
*published rows that stop vouching*, which is 15 on a default install and fewer when `ignoredFaults`
suppresses notification sensors — neither the "16" nor the "11" in the phase inputs is a number the
source produces. **Monotonic silence** has an exact answer: `process.hrtime.bigint()`, measured in a
Linux time namespace this session to follow `CLOCK_MONOTONIC` and *not* `CLOCK_BOOTTIME`, which also
means it does not advance across a system suspend.

The harness items are the ones to do first, and one of them is not the defect its ledger entry says
it is. Entry 18's stated mechanism — "returns once the client subscribed to *either* device" — is
false for the shipped shadow client, which subscribes to every device's topics in **one awaited
call** before it publishes any `get` (`src/cloud/shadow.ts:346-352`). The real defect is adjacent and
worse for this phase: `publishedTopics` is cumulative and never reset, so on any scenario that
reconnects, `awaitSubscription` returns instantly against the *previous* connection's evidence. Entry
17's "dead single-device leftovers" is also not what it says: both helpers have live callers, and the
actual problem is that `features/support/steps/harness.ts:131` is a second, worse `currentAccessory`
shadowing the shared one in `features/support/publishedServices.ts:30`.

**Primary recommendation:** Sequence the phase as harness-correctness first (entries 17/18, with the
corrected diagnoses recorded), then the derived controller-link message (self-contained, one file
plus its test), then `MonotonicClock` and the persisted anchor, then the per-device trust signature
last — because it is the largest diff and it wants a `checkpoint:decision` on how the account-wide
credential fact travels once the callback is map-valued.

## Research Questions Answered

### Q1 — Monotonic time source on Node `^22.10.0 || ^24.0.0`

**Answer: back `MonotonicClock` with `process.hrtime.bigint()`, converted to whole milliseconds.**

| Property | `process.hrtime.bigint()` | `performance.now()` | `Date.now()` |
|---|---|---|---|
| Monotonic across a wall-clock change | Yes — reads `CLOCK_MONOTONIC` `[VERIFIED: probe below]` + `[CITED: nodejs.org/api/process.html — "not subject to clock drift"]` | Yes, same source family `[CITED: nodejs.org/api/perf_hooks.html]` `[ASSUMED]` for the syscall identity | **No** — this is the defect IN-03 names |
| Epoch | System boot on Linux — matched `/proc/uptime` to 0.01 s `[VERIFIED: probe below]` | Process start (`performance.timeOrigin`) `[VERIFIED: probe below]` | Unix epoch |
| Advances during system suspend | **No** — does not follow `CLOCK_BOOTTIME` `[VERIFIED: probe below]`; `CLOCK_BOOTTIME` is the clock that includes suspend `[CITED: man 2 clock_gettime]` | Not measured `[ASSUMED]` | Yes |
| Precision | Smallest observed non-zero tick **93 ns** over 200 000 samples `[VERIFIED: probe below]` | sub-millisecond float | 1 ms |

**The probe, run this session.** A Linux time namespace can offset `CLOCK_MONOTONIC` and
`CLOCK_BOOTTIME` independently, which turns "which clock is this?" into a falsifiable question. It
worked unprivileged here via `unshare -r -T`.

```text
$ P='const t=process.hrtime.bigint();console.log(JSON.stringify({hrtime_s:Number(t)/1e9,date_ms:Date.now(),perf_now:performance.now(),perf_origin:performance.timeOrigin,uptime_s:require("node:fs").readFileSync("/proc/uptime","utf8").trim()}))'

--- baseline (no namespace), /usr/bin/node v22.22.2 ---
{"hrtime_s":1172267.10281092,"date_ms":1788483478446,"perf_now":178.106846,"perf_origin":1788483478274.33,"uptime_s":"1172267.11 17845994.23"}
--- time ns, monotonic +600 ---
{"hrtime_s":1172867.372454776,"date_ms":1788483478716,"perf_now":172.639473,"perf_origin":1788483478549.488,"uptime_s":"1172267.37 17845997.97"}
--- time ns, boottime +600 (monotonic untouched) ---
{"hrtime_s":1172267.640655147,"date_ms":1788483478984,"perf_now":171.593562,"perf_origin":1788483478818.887,"uptime_s":"1172867.64 17846001.55"}
--- baseline again ---
{"hrtime_s":1172267.880509423,"date_ms":1788483479224,"perf_now":161.801507,"perf_origin":1788483479068.573,"uptime_s":"1172267.88 17846004.90"}
```

Read it as three facts. Offsetting `CLOCK_MONOTONIC` by +600 s moved `hrtime.bigint()` by +600.27 s
while `/proc/uptime` stayed put: **`hrtime.bigint()` is `CLOCK_MONOTONIC`.** Offsetting
`CLOCK_BOOTTIME` by +600 s moved `/proc/uptime` and left `hrtime.bigint()` at its baseline:
**`hrtime.bigint()` is not `CLOCK_BOOTTIME`.** And `Date.now()` advanced only by real elapsed time in
every run, so the two bases are genuinely different clocks. The same three runs on the local
`node` v26.8.1 gave the same three results (`1172283.59` → `1172883.70` → `1172283.79`).

**Node 24 was not measured.** It is not installed on this host (`node` is v26.8.1, `/usr/bin/node` is
v22.22.2). Do not let any plan claim a Node 24 result it did not run; CI runs `[22.x, 24.x]`
`[VERIFIED: .github/workflows/build.yml:31]` and is the place that result comes from.

**The suspend consequence, and what is not proven.** `CLOCK_MONOTONIC` excluding suspend time is the
documented Linux distinction from `CLOCK_BOOTTIME` `[CITED: man 2 clock_gettime]`, and the probe above
establishes which of the two `hrtime` follows. What the probe does **not** do is suspend this host and
watch the divergence: this machine shows no accumulated suspend time (`hrtime_s` and `/proc/uptime`
agree to within process-start latency), so there was nothing to observe and no falsification attempt
was possible. Treat "a suspended host under-counts silence" as `[CITED]`, not `[VERIFIED]`.

**Why the suspend gap matters, and why it is already closed.** A host that sleeps for two hours
resumes with the monotonic counter two hours short, so a pump that has said nothing all night reads
as recently heard. This is precisely the failure D-07's persisted wall-clock anchor closes, and the
clean way to close it is to make the anchor a **continuous** second opinion rather than a
restart-only one:

> silence elapsed = **max**(monotonic elapsed since last arrival, wall elapsed since the anchor)

`max` is D-07's clamp stated as an expression. It can only ever report silence **sooner**: a
backwards wall jump makes the wall term small and the monotonic term wins; a suspend makes the
monotonic term small and the wall term wins; a forward wall jump inflates the wall term and marks
early, which the STATE.md ruling already accepts as harmless ("Forward jumps only mark early, which
is harmless"). The same expression serves the restart path, where the monotonic term restarts at zero
and the wall term is the whole of the evidence.

**Shape of the port.** Mirror `Clock` exactly so nothing at a call site can confuse them:

```typescript
// src/runtime/monotonicClock.ts — sibling of clock.ts, same one-method shape.
export interface MonotonicClock {
  /** Milliseconds since an arbitrary fixed point. Never comparable to a wall-clock time. */
  now(): number;
}

const NANOSECONDS_PER_MILLISECOND = 1_000_000n;

export const systemMonotonicClock: MonotonicClock = {
  now: () => Number(process.hrtime.bigint() / NANOSECONDS_PER_MILLISECOND),
};
```

Integer-divide the `bigint` before widening: at 1.17e6 s of uptime the value is ~1.17e9 ms, far inside
`Number.MAX_SAFE_INTEGER`, and dividing first keeps the result an exact integer so every existing test
that moves time by a whole number of milliseconds keeps working unchanged.

### Q2 — Homebridge accessory-context persistence for a new optional field

**Answer: a `number | undefined` field round-trips to absent, exactly like `primaryPump` already does —
and the pinned Homebridge was read to confirm it, not assumed.**

The pinned version is `homebridge@2.4.0` `[VERIFIED: node_modules/homebridge/package.json:4]`, and
`engines.node` there is `"^22 || ^24 || ^26"` `[VERIFIED: node_modules/homebridge/package.json:33]`.
The write path, read from the installed dist this session:

- `PlatformAccessory.serialize()` puts the context in verbatim — `context: accessory.context`
  `[VERIFIED: node_modules/homebridge/dist/platformAccessory.js:92-97]`.
- `PlatformAccessory.deserialize()` restores it verbatim — `platformAccessory.context = json.context`
  `[VERIFIED: node_modules/homebridge/dist/platformAccessory.js:106]`.
- `updatePlatformAccessories()` emits `UPDATE_PLATFORM_ACCESSORIES`
  `[VERIFIED: node_modules/homebridge/dist/api.js:229-231]`, whose handler calls
  `saveCachedPlatformAccessoriesOnDisk()` `[VERIFIED: node_modules/homebridge/dist/bridgeService.js:420-428]`.
- That saves through `StorageService.setItemSync`, which is `fs.writeJsonSync(...)`
  `[VERIFIED: node_modules/homebridge/dist/storageService.js:25-27]` — i.e. `JSON.stringify`.

So the round trip is plain JSON, and plain JSON drops `undefined` properties:

```text
$ /usr/bin/node -e 'const o={a:undefined,b:1,c:NaN,d:null};const s=JSON.stringify(o);console.log("stringify:",s);const r=JSON.parse(s);console.log("parsed:",r,"has a:", "a" in r);'
stringify: {"b":1,"c":null,"d":null}
parsed: { b: 1, c: null, d: null } has a: false
```

Three consequences for D-07/D-08:

1. **A restored accessory from an install predating the field carries no key at all.** `context.anchor`
   reads `undefined` and `'anchor' in context` is `false` — indistinguishable from a field written as
   `undefined`. That is the same "absent is the ordinary first-run state" shape the existing members
   are documented against `[VERIFIED: src/persistence/accessoryContext.ts:91-104]`, and the platform's
   own context type already says so: *"`device` is optional so an accessory restored from before this
   field existed does not fail its structural type"* `[VERIFIED: src/platform.ts:31-54]`.
2. **`NaN` and `Infinity` serialize to `null`, not to an error.** A computed anchor that ever went
   `NaN` would come back as `null`, which `typeof x === 'number'` rejects — so the read-back guard must
   be a `typeof` test, never a truthiness test. Follow `isPumpObservation`
   `[VERIFIED: src/accessories/pumpRecords.ts:109-122]` and `isTokenCacheFile`
   `[VERIFIED: src/cloud/auth.ts:118-126]`: both narrow untrusted stored JSON with a hand-written
   predicate, and the auth one carries the comment *"The cache file is untrusted input like any other
   stored JSON, so it is narrowed by a hand-written predicate rather than assumed."*
3. **The harness reproduces this faithfully.** `features/support/fakeHomebridgeApi.ts:244` stores
   `context: JSON.stringify(accessory.context)` and line 296 restores it with
   `Object.assign(accessory.context, JSON.parse(entry.context))` — the same drop-undefined behaviour,
   so a scenario can prove the absent-anchor fallback without a real bridge.

**Write amplification, and why the clamp makes it a non-issue.** `saveCachedPlatformAccessoriesOnDisk`
re-serialises **every** cached accessory on each call, so persisting the anchor on every shadow
message would rewrite the whole cache on every heartbeat, per device. It does not need to. Because the
clamp is *sooner, never later*, a **stale** anchor is the safe direction: an older stored anchor makes
the wall term larger, so silence is reported earlier, never later. The write cadence is therefore free
to be coarse — persist on the poll tick, or when the anchor has moved by more than some quantum, or
only at shutdown — and the correctness argument does not depend on which is chosen. Say this out loud
in the plan; it is the kind of reasoning a later reader will otherwise redo.

### Where the anchor should live (Claude's discretion under D-08)

**Recommendation: a runtime-scoped store under `api.user.storagePath()`, not `accessory.context`.**

The deciding fact is *when the anchor is read*. Silence is seeded at admission —
`health.admitDevice(device.deviceId)` inside `applyDevices`
`[VERIFIED: src/runtime/accountRuntime.ts:343-349]` — and `onTrustworthyInventory` (which is what
creates or restores the accessory objects) is called **after** that loop, at
`src/runtime/accountRuntime.ts:351-352`. So at the moment the runtime needs the anchor, the accessory
tier has not yet been asked about this device on this poll, and the runtime holds no handle to
accessory context in any case. Routing an accessory-context value back into the runtime means either
inverting that order or adding a callback purely to fetch a timestamp.

The precedent for runtime-tier persistence already exists and is small: the Auth0 token cache writes
JSON under `join(options.storagePath, TOKEN_CACHE_FILENAME)`
`[VERIFIED: src/cloud/auth.ts:113]`, parses defensively (`parseCacheFile` returns `undefined` for
unreadable *and* malformed, `src/cloud/auth.ts:138-147`), narrows with a predicate
(`isTokenCacheFile`, `:118-126`), and writes atomically through a temp file
(`writeFile(temporary, contents, { mode: OWNER_ONLY_MODE, flag: 'wx' })`, `src/cloud/auth.ts:213`).
`storagePath` is already threaded into the runtime seam
`[VERIFIED: src/runtime/accountRuntime.ts:999, :1036; src/platform.ts:549]`.

Costs of this choice, stated so the planner can weigh them: a second file in the storage directory; a
new async read on the launch path (the token cache shows the shape); and a store whose entries are
never pruned unless `forgetDevice` also removes them — mirror `health.forgetDevice`'s single call site
at `src/runtime/accountRuntime.ts:382`, which is deliberately the *only* place stamps are pruned and
carries the reason why (`:377-381`).

### Q5 — Entries 17 and 18 in the harness: both diagnoses need correcting

**Entry 18 — the stated mechanism is false; a different, worse defect is real.**

Ledger entry 18 says `awaitSubscription` *"answers once the client subscribed to either device"*. The
shipped shadow client makes that impossible. `requestEveryShadow` subscribes to **every route of every
device in one awaited call**, and only then publishes the per-device `get`:

```typescript
// src/cloud/shadow.ts:346-352 — verbatim
async function requestEveryShadow(target: ShadowConnection, reopen: () => void): Promise<void> {
  try {
    await target.transport.subscribe([...routes.keys()]);

    for (const deviceId of devices) {
      await target.transport.publish(SHADOW_TOPICS.get(deviceId), '');
    }
```

`routes` holds three topics per device — `get/accepted`, `get/rejected`, `update/accepted`
`[VERIFIED: src/cloud/shadow.ts:152-160]` — filled once from the device list at
`start()` `[VERIFIED: src/cloud/shadow.ts:453-459]`. And `publishedTopics` records only what a *client*
published `[VERIFIED: features/support/fakeShadowBroker.ts:182-186]`. So the first published topic
proves the subscription for **all** devices already completed. The current wait is sound for the
question it asks, on a first connection.

**The real defect: `publishedTopics` is cumulative and is never reset.** Every reconnect runs
`handleConnect` → `requestEveryShadow` again `[VERIFIED: src/cloud/shadow.ts:377-380]`, but the array
still holds the previous connection's entries, so:

```typescript
// features/support/steps/shadow.ts:110-114 — verbatim
async function awaitSubscription(world: BasementGuardianWorld): Promise<void> {
  const broker = await world.broker();

  await world.untilTrue(() => broker.publishedTopics.length > 0, DEADLINE_MS, 'the plugin subscribed to no shadow topic');
}
```

returns **instantly** on any scenario that has already connected once — a wait satisfied by evidence
from a connection that no longer exists. That is the project's named blocking anti-pattern ("a check
that passes because the thing it rests on already sits at the value the defect produces"), just not for
the reason the ledger records. It bites this phase because a per-pump silence scenario naturally drives
reconnects and staggered heartbeats.

**The correct wait condition.** Ask the broker what it is subscribed to, not what was published to it.
`aedes` emits a `subscribe` event; recording `(subscriptions, client)` alongside the existing
`clientIds`/`publishedTopics` arrays gives a per-connection view, and the wait becomes "the current
client holds `$aws/things/<deviceId>/shadow/update/accepted`". A cheaper fix that stays inside the
existing surface is to wait on the **per-device** published `get` topic —
`` `$aws/things/${deviceId}/shadow/get` `` `[VERIFIED: src/cloud/shadow.ts:33]` — with a count captured
before the act, so the wait is for a *new* publish rather than for a non-empty array. Either way the
two properties to hold are: (a) named per device, (b) relative to a baseline taken at the step, never
absolute.

**Which scenarios depend on the current behaviour.** `awaitSubscription` has exactly two callers:
`publishReported` (`features/support/steps/shadow.ts:179-184`), which backs the steps
`the device publishes these heartbeat fields:`, `the device reports these fields:`,
`the {string} device publishes these heartbeat fields:` and
`the device reports these device metadata fields and a telemetry section that cannot be read:`; and
`publishRequestedState` (`:221-226`), backing `the device publishes a requested value`. Any scenario
using one of those after a reconnect is currently relying on the cumulative array — in particular

(`features/degradedOperation.feature:72`) and the credential/recovery scenarios that follow it. Re-run

### Pattern 1: A sibling port, not a widened one

**What:** `MonotonicClock` is a new one-method interface in its own module beside `Clock`, wired at the
composition root only, exactly as `systemClock` is (`src/runtime/clock.ts:12-15`).
**When to use:** D-06 fixes this. The reason it beats a second method on `Clock` is that a call site
reading `clock.now()` cannot then tell which base it got, and every existing consumer —
`src/cloud/shadow.ts:252` (SigV4 date), `src/cloud/auth.ts:135` (token expiry against a vendor-issued
instant), `src/device/state.ts:348,362` (`receivedAt`, which is persisted and published as ISO-8601),
`src/runtime/accountRuntime.ts:756` (rotation delay against a vendor `Expiration`), and
`src/runtime/failureLog.ts:49` (reminder cadence) — genuinely wants wall time. Only
`src/runtime/monitoringHealth.ts:176,191,196` moves.

**Example:**

```typescript
// src/runtime/monitoringHealth.ts — the shape after the change.
export interface MonitoringHealthOptions {
  clock: Clock;                    // wall — still needed for the persisted anchor
  monotonic: MonotonicClock;       // forward-only — the silence measurement
  anchors?: ArrivalAnchors;        // D-07; absent means "no anchor was restored" (D-08)
}
```

### Pattern 2: The clamp is a `max`, and its direction is the test

**What:** `silenceElapsed(deviceId) = Math.max(monotonicNow - monotonicStamp, wallNow - anchor)`, with
the wall term omitted when no anchor exists.
**Why:** it is D-07 stated as one expression, and it covers three failures at once — a backwards wall
jump (monotonic term wins), a system suspend (wall term wins), and a restart (only the wall term
exists). A `min` would be the exact inversion and would hide a dead pump; that inversion is the
discriminating mutation for this behaviour (§ Validation Architecture).
**Anti-pattern:** applying the anchor only at restart. It leaves the suspend case open for the entire
life of a long-running process, which is the common case on a home server that sleeps.

### Pattern 3: Derive the diagnostic from the state that produced it

**What:** build the controller-link sentence from `published` filtered by the withdrawn scope set, at
the point `reportControllerLink` is already called (`basementGuardian.ts:1006`, one line after
`published` is recomputed at `:1004`).
**Why:** D-05. A hand-written list drifts; the project has the receipts — the message currently names
five of seven scopes and has done so since it was written.
**Rendering note (discretion):** the existing sentence is one line, names the `deviceId`, quotes no
credential, and says values are *retained rather than refreshed*
`[VERIFIED: src/accessories/basementGuardian.ts:817-821]`. Keep all four properties. A list of 15
display names is long; joining with `', '` and a final `' and '` reads acceptably in a Homebridge log,
and the log-once discipline at `:829-831` means it is printed once per transition, not per poll.

### Pattern 4: Untrusted stored JSON gets a hand-written predicate

**What:** whatever backs the persisted anchor, narrow it on read with a `typeof`-based guard and treat
unreadable and malformed as the same answer.
**Precedents, both opened this session:** `isTokenCacheFile`/`parseCacheFile`
(`src/cloud/auth.ts:118-126`, `:138-147`) and `isPumpObservation`
(`src/accessories/pumpRecords.ts:109-122`, with the seeding path at `:227` and `:248-250`).

### Anti-Patterns to Avoid

- **Joining the trust map to `basementGuardianAccessories` by key.** That map is UUID-keyed
  (`platform.ts:279`, `:201`, `:328`). Read `accessory.deviceId` instead
  (`basementGuardian.ts:80-81`).
- **Letting an empty map mean "nothing to do".** See § *Common Pitfalls, Pitfall 1*.
- **Adding a member to `MonitoringTrust` without adding it to the comparison in `markMonitoring`.**
  The comment at `basementGuardian.ts:888-907` states this and names what each member proves; a member
  left out *"still reaches the write path, which reads the stored value directly, so it is silent here
  rather than harmless"*. D-01 says the type does not change — if a plan finds itself changing it, that
  is a signal to stop and re-read D-01.
- **Copying the fan-out into the harness.** `applyMonitoringHealth` is exported so the harness runs the
  real one (`platform.ts:375-378`, `world.ts:645-650`). A per-device fan-out written inside the
  platform callback would be copied and every scenario would assert against the copy.
- **Piping a suite into a filter in a `<verify>` block.** `pipefail` is off. Capture output and status
  separately — the form is in § Validation Architecture.

|---------|-------------|-------------|-----|
| A clock immune to wall-clock jumps | A tick counter on `setInterval`, or a "last seen max" clamp over `Date.now()` | `process.hrtime.bigint()` | The clamp variant was explicitly rejected by D-06; a tick counter drifts under load and needs a timer this module refuses to own (`monitoringHealth.ts:14-17`). |
| Per-device silence tracking | A new map keyed by device | `health.silentDevices()` | It already exists and already answers per device in admission order (`monitoringHealth.ts:173-179`); D-03 says the only change is removing the flatten. |
| Atomic JSON persistence under `storagePath` | A fresh `writeFile` | The token-cache shape at `src/cloud/auth.ts:203-215` | Temp file + `flag: 'wx'` + `rename`, owner-only mode, already reviewed and shipped. |
| Reading a service's display name | A second list of names | `ServiceRow.displayName` / the `ServiceDescriptor.name` the accessory already pushes (`basementGuardian.ts:738`) | The catalogue is the single declaration of kind, display name, class and subtype (`serviceCatalogue.ts:628-645`); a second list is the drift D-05 exists to prevent. |
| Finding an accessory by name in a scenario | A new lookup | `serviceOnNamed` / `accessoryNamed` (`publishedServices.ts:46-56`, `:83-85`) | Already throws on a miss instead of silently reading the wrong pump. |
| Waiting for a device to be reachable in a scenario | A `sleep` | `world.untilTrue(..., DEADLINE_MS, '<named failure>')` | The suite's established shape; a deadline turns silence into a named failure. |

**Key insight:** almost every capability this phase needs already exists one layer down and was built
per-device in Phase 5 — the phase is mostly *removing* a flatten and *carrying* an answer that is
already correct at its source.

## Common Pitfalls

### Pitfall 1: A map-valued callback is empty on a refused launch, and silently deletes the credential marking

**What goes wrong:** `applyMonitoringHealth`'s second half is gated on `trust.credentialsRejected`
(`src/platform.ts:385-387`) and then walks `context.accessories` — the raw, UUID-keyed platform map —
to make restored services unreadable (`:404-408`). With a `ReadonlyMap<deviceId, MonitoringTrust>` and
no devices discovered, that map is empty and there is nowhere to read the credential fact from.

**Why it happens:** the halt push at `src/runtime/accountRuntime.ts:533` fires from
`haltOnTerminalAuthFailure`, which the *launch* routes through — before any inventory succeeds, so
before `health` has admitted any device and before `store.deviceIds()` has anything in it (the shadow
connect itself is gated on `deviceIds.length === 0`, `src/runtime/accountRuntime.ts:629`).

**Why it is not hypothetical:** the platform already documents the case —
*"A run whose first grant the vendor refused never reaches discovery, so that map is empty, while the
accessories an owner is actually looking at are the ones Homebridge restored into this one"*
`[VERIFIED: src/platform.ts:399-403]` — and a shipped unit case exists for it:
`test('makes every restored accessory unreadable when the vendor has refused the credentials')` at
`test/platform.test.ts:1259`, which calls `applyMonitoringHealth` with **no**
`basementGuardianAccessories` at all (`:1262`). Four more cases at `:1290`, `:1425`, `:1452`, `:1472`
drive the same branch.

**How to avoid:** give the account-wide facts their own channel. Three options, with costs:

| Option | Shape | Cost |
|---|---|---|
| **A (recommended)** | `applyMonitoringHealth(context, account: MonitoringTrust, byDevice: ReadonlyMap<string, MonitoringTrust>)`; a missing entry means "the account trust with `shadowSilent: true`" (D-02) | Deviates from D-01's literal wording ("becomes map-valued"), so it needs a `checkpoint:decision`. Smallest correct diff; also gives D-02 a well-defined value for the other three members. |
| B | Map only; read `credentialsRejected` from any entry | Empty-map case unhandled — this is the bug, not a fix. |
| C | Map for per-device trust + a separate `onCredentialsRejected` callback | Cleanest conceptually, largest diff, and it splits one push into two that can arrive out of order. |

**Warning sign:** a plan that changes the signature and reports `test/platform.test.ts` green without
touching `:1259`. That case does not construct a device map at all, so it will need editing — and if it
is edited to *pass* rather than to keep asserting, the behaviour is gone.

### Pitfall 2: D-02's "silent" needs three more members than `shadowSilent`

**What goes wrong:** an accessory with no entry reads "silent" — but `MonitoringTrust` has four members
(`restDegraded`, `shadowSilent`, `commandTransportReady`, `credentialsRejected`,
`src/runtime/monitoringHealth.ts:56-89`) and `markMonitoring` compares all four
(`src/accessories/basementGuardian.ts:908-912`). A default literal invented at the lookup site would
assert three facts nobody supplied — including `commandTransportReady`, whose safe default is `false`
per the Phase 5 ruling recorded in STATE.md ("the accessory's stored trust starts with
`commandTransportReady` false … because a safety fact defaults to the refusing value").

**How to avoid:** option A above answers it — the missing entry resolves to the account trust with
`shadowSilent` forced true, so the three account-wide members are the account's real values and only
the per-device one is defaulted.

### Pitfall 3: `reportedShadowSilent` is a single account-wide latch

**What goes wrong:** `reportedShadowSilent` (`src/runtime/accountRuntime.ts:282`) is assigned from
`trust.shadowSilent` (`:465`) and gates the arrival-driven recovery report (`:670-672`). Once
`shadowSilent` is per device there is no single boolean to assign, and a naive `some()` re-creates the
flatten D-03 removes — one noisy pump would keep re-reporting for a quiet neighbour, or a quiet
neighbour would suppress the noisy pump's recovery report.

**How to avoid:** make the latch per device (`Set<deviceId>` or a map), and have the arrival callback
consult the latch for `deviceId` — the callback already has it (`:637`, `:667`). The failure-log side
(`options.failures.recordFailure(LIVE_REPORTING, …)` at `:473-477`) is a separate decision: the failure
log is account-scoped and this phase has no requirement to make it per device. Recommend leaving the
log account-wide and recording that as a deliberate narrowing, so the phase does not grow a fourth
change.

### Pitfall 4: The harness `advanceClock` must move both clocks

**What goes wrong:** all 102 scenarios drive time by `advanceClock`
(`features/support/world.ts:239-242`), and the silence scenarios rely on it
(`features/degradedOperation.feature:97`, `:249`, `:253`). If the World implements `MonotonicClock` but
`advanceClock` only moves the wall clock, every silence scenario stops tripping and passes for a new
wrong reason.

**How to avoid:** `advanceClock` moves both; a *new*, separately named step moves the wall clock alone.
The unit tier needs the same pairing — `movableClock()` at `test/runtime/monitoringHealth.test.ts:24-36`
returns `{ clock, moveTo }` and will need a monotonic sibling.

### Pitfall 5: A `<verify>` that cannot fail

**What goes wrong:** `pipefail` is off in this shell, so `npm test | grep x` returns grep's status.
Named `blocking` in the Phase 5 handoff's Critical Anti-Patterns table, with the proof `(exit 7) | grep x`
returning 1.

**How to avoid:** the two-variable form, used for every measurement in this document:

```bash
O=$(npm run test:unit 2>&1); R=$?; test $R -eq 0 && printf '%s\n' "$O" | grep -qE '^ℹ fail 0$'
```

And never gate a `<verify>` on `mdformat`, `markdownlint-cli2`, the texthooks or `npm run format:check`
for a `.planning/` path: `.planning/` is excluded from the markdown hooks and `format:check` covers
`js,json,mjs,ts` only `[VERIFIED: package.json:"format:check": "prettier --check \"**/*.{js,json,mjs,ts}\""]`.

### Pitfall 6: Concurrent suite runs produce a false red

Two overlapping `npm run check` runs were measured at `pass 1383 / fail 2` against a solo
`1385 / fail 0`. Run one suite at a time; re-run a red gate alone before believing it, and say in the
summary if you had to.

### Pitfall 7: 100% coverage is a real gate, and a new branch with no scenario reaches it

`npm run test:coverage:all` enforces 100 lines / 100 branches / 100 functions over
`dist-test/src/**/*.js` `[VERIFIED: package.json scripts]`. A new `MonotonicClock` module, an anchor
guard, or a `max` with two arms each add branches. Ledger entries 16 and 23 record earlier plans that
had to add unit cases they had not listed for exactly this reason. Also `npm run fallow` runs
`dead-code`, `health` and `dupes` — a new exported symbol with no production consumer fails
`dead-code`, which is why `accessoryNamed` stays module-local
`[VERIFIED: STATE.md, Phase 05 accumulated context]`.

function silenceElapsedMs(deviceId: string): number {
  const monotonicElapsed = monotonic.now() - (lastShadowMonotonic.get(deviceId) ?? monotonic.now());

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| A corrupted or hand-edited anchor file makes a dead pump read as trustworthy | Tampering | The clamp direction. ## Open Questions

1. **How does the account-wide credential fact travel once `onMonitoringHealth` is map-valued?**
   - What we know: an empty map is reachable on a refused launch, the credential branch of
     `applyMonitoringHealth` is gated on it, and `test/platform.test.ts:1259` exists to hold that case.
   - What's unclear: whether the maintainer reads D-01's "becomes map-valued" as forbidding a second
     parameter.
   - Recommendation: open plan 1 with a `checkpoint:decision` naming the three options in Pitfall 1 and
     recommending A. Mark that plan `autonomous: false`, as plan 05-01 was for the same class of
     question.

2. **Does the failure log's `LIVE_REPORTING` observation become per device?**
   - What we know: `reportMonitoringHealth` records one account-scoped failure/success
     (`accountRuntime.ts:473-477`), and the `reportedShadowSilent` latch beside it is a single boolean
     (`:282`, `:465`).
   - What's unclear: nothing in the phase's success criteria asks for a per-device *log*; only the
     marking is per pump.
   - Recommendation: make the **latch** per device (it gates correctness of the recovery push) and
     leave the **log** account-wide, recording the narrowing. Otherwise the phase grows a fourth change
     and the log's rate limiting has to be redesigned.

3. **Which write cadence for the persisted anchor?**
   - What we know: the clamp direction makes a stale anchor the safe direction, and
     `saveCachedPlatformAccessoriesOnDisk` rewrites every accessory per call.
   - What's unclear: whether the maintainer wants a bounded write rate or is content with per-poll.
   - Recommendation: Claude's discretion under D-08 — persist on the poll tick, which already happens
     at a configured interval and is where `reportMonitoringHealth` already runs.

4. **Does the derived message name services or scopes when the list is long?**
   - What we know: 15 display names on a default install. D-05 rules out seven-scope granularity as the
     chosen option.
   - What's unclear: readability of a 15-name sentence in a Homebridge log.
   - Recommendation: name the services, one line, log-once. It is what criterion 2 asks for, and the
     line is printed once per transition.
