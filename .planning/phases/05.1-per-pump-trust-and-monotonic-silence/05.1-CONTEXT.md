## Implementation Decisions

### Per-device trust signal (entry 19)

- **D-01:** *(amended 2026-09-03 after research — see **Corrections after research** below.)*
  `onMonitoringHealth` carries **both** an account-wide `MonitoringTrust` and a
  `ReadonlyMap<deviceId, MonitoringTrust>`:
  `applyMonitoringHealth(context, account, byDevice)`. The runtime resolves per-device trust
  and `applyMonitoringHealth` looks each accessory up, falling back per D-02.

  The original wording was "becomes map-valued", with a single map. Research measured that a
  single map is **empty** on a launch the vendor refused before the first inventory, and
  `applyMonitoringHealth`'s credential branch (`src/platform.ts:385-408`) is gated on
  `credentialsRejected` with nowhere to read it from. `test/platform.test.ts:1259` exists to
  hold that case and passes no device map at all; four more cases drive the same branch. A
  map-only shape would have silently deleted a shipped safety behaviour.

  `MonitoringTrust` itself is unchanged, so `markMonitoring`, `monitoringDegradedScopes` and
  every accessory-tier trust literal stay as they are. Blast radius counted, not estimated:
  105 references across 8 files, 56 of them `restDegraded`, and **three** `onMonitoringHealth`
  push sites — `accountRuntime.ts:479`, `:533` and `:967`.
  — **Reversibility:** costly — the signature is bound by the platform, the Cucumber harness
  and the runtime test suite, so undoing it touches all four call sites at once.

- **D-01a:** The per-device map is keyed by **`deviceId`**, and `basementGuardianAccessories`
  is **UUID-keyed** (`src/platform.ts:279`). The fan-out joins on `accessory.deviceId`, not on
  the map key. A direct key join would silently match nothing.

- **D-02:** An accessory with no per-device answer reads **silent**. A device admitted after
  the last push, or an accessory restored from cache before discovery completes, does not
  vouch. This follows the project constraint that unknown never becomes a normal default,
  and it matches `RES-04`, which already marks every restored service stale until a poll
  succeeds. Explicitly not chosen: falling back to the old any-pump-silent boolean, which
  would reintroduce the flatten on the path most likely to be hit at startup.

  *Amended after research:* "silent" is not one member. `MonitoringTrust` has four, and
  `markMonitoring` compares all four (`src/accessories/basementGuardian.ts:908-912`). A
  default literal invented at the lookup site would assert three facts nobody supplied. D-01's
  amended shape answers it: a missing entry resolves to **the account trust with `shadowSilent`
  forced true**, so the three account-wide members carry the account's real values and only the
  per-device one is defaulted.

- **D-03:** The flatten at `src/runtime/monitoringHealth.ts:212`
  (`shadowSilent: silentDevices().length > 0`) is removed. `silentDevices()` already answers
  per device and needs no new tracking.

- **D-04:** Marking breadth still follows the cause, not the transport. `shadowSilent` and
  `controllerLinkLost` become per-pump; `restDegraded` and `credentialsRejected` stay
  account-wide, because those causes genuinely do affect every pump. This is the Phase 5
  ruling restated, not a new decision.

### Controller-link diagnostic (entry 6)

- **D-05:** The log message is **derived from the marked set** rather than hand-written, so
  it cannot drift from behaviour by construction. A test still pins the rendering. Not
  chosen: a static sentence with a drift test, and logging at seven-scope granularity instead
  of naming services.

  *Corrected after research — the premise this was built on was wrong.* The log does not name
  "11 of 16 services". It names **five scope words** in prose (`water, pump, power, battery,
  and fault`), and the figure 11 in `STATE.md` and in the Phase 5 handoff is not derivable
  from any source. Measured by executing the shipped catalogue: **17 rows, 16
  non-connectivity, 15 that actually stop vouching** — `Pump Controller Link Lost` tolerates
  its own cause — across **7 scopes**.

- **D-05a:** The derived list names **the published rows that stop vouching**, not the whole
  catalogue. `ignoredFaults` suppression and unprojected rows make any catalogue-wide count
  wrong on a real install, so the message is built from `published` at the point
  `reportControllerLink` is already called, one line after `published` is recomputed. Rendering
  stays one line, keeps naming the `deviceId`, quotes no credential, and keeps saying values are
  *retained rather than refreshed*. The log-once discipline already in place means it prints
  once per transition, not per poll.

### Monotonic silence (entry 14 / IN-03)

- **D-06:** A **separate `MonotonicClock` port**, injected where silence is measured.
  `Clock.now()` stays honest wall-clock for receipt times and for anything persisted, and the
  two time bases cannot be confused at a call site. Not chosen: adding `monotonicNow()` to
  the existing `Clock` (one interface carrying two incompatible bases), and clamping
  `systemClock.now()` forward-only (smallest diff, but it silently changes what `now()` means
  for persisted receipt timestamps and would swallow a real wall-clock correction).
  — **Reversibility:** costly — a second port is wired at the composition root and threaded
  to every silence measurement; undoing it means re-deriving which call sites wanted which
  time base.

- **D-07:** A wall-clock arrival anchor **is persisted**, and it is **clamped so it can only
  ever report silence sooner, never later**. The anchor may lengthen a silence window and may
  never shorten one, so a backwards wall-clock jump cannot hide a dead pump — the failure
  IN-03 exists to close.

  *Strengthened after research.* The clamp is **continuous**, not restart-only:

  ```
  silenceElapsed(deviceId) = max(monotonicNow - monotonicStamp, wallNow - anchor)
  ```

  with the wall term omitted when no anchor exists. One expression covers three failures — a
  backwards wall jump (the monotonic term wins), a **system suspend** (the wall term wins),
  and a restart (only the wall term exists). Applying the anchor only at restart leaves the
  suspend case open for the entire life of a long-running process, which is the common case on
  a home server that sleeps. **Inverting this `max` to a `min` is the single most important
  discriminating mutation in the phase.**

- **D-08:** Nothing persists shadow-arrival times today. Measured during discussion:
  `AccessoryContext` in `src/persistence/accessoryContext.ts` carries `primaryPump`,
  `backupPump`, `watermarks` and `lastVendorName`, and no arrival timestamp exists anywhere
  in `src/`. D-07 therefore adds new persisted state, and an install carrying none falls
  through to D-02 — silent until told otherwise.

  *Storage location resolved after pattern mapping — this was Claude's discretion and is now
  decided.* The anchor lives in **its own store under `api.user.storagePath()`**, following the
  token cache (`src/cloud/auth.ts:113`, `:140`, `:213`), **not** in `accessory.context`. Two
  measured reasons:

  1. **Timing.** `health.admitDevice` runs at `src/runtime/accountRuntime.ts:343-349`, *before*
     `options.onTrustworthyInventory` at `:351-352` builds the accessories. At the moment the
     runtime needs the anchor, no `BasementGuardianAccessory` exists for that device.
  2. **Layering.** `accountRuntime.ts` already receives `storagePath` (`:999`, `:1036`) and
     imports nothing from the persistence tier — no `AccessoryContext`, no `PlatformAccessory`.
     Threading accessory context into the runtime to reach the anchor would be a layering
     violation for a runtime-tier concern.

  `isPumpObservation` (`src/accessories/pumpRecords.ts:109-122`, seeding at `:227`, `:248-250`)
  still supplies the migration language and the absent-on-first-run shape, and D-08's read must
  narrow the stored JSON with a hand-written `typeof` predicate that treats unreadable and
  malformed as the same answer.
  — **Reversibility:** reversible — a file of the plugin's own under `storagePath`, not a
  published contract. Deleting it is safe: an absent anchor falls through to D-02, which is the
  conservative answer. *(Rated `one-way` before the location was resolved, on the assumption it
  would enter `accessory.context`; that assumption was wrong.)*

### Evidence bar

- **D-09:** The bar is the **two-pump Cucumber harness with named discriminating mutations,
  plus a live single-device regression check** against the one real Gemini, proving the
  change did not alter single-device behaviour.

- **D-10:** **No real multi-device evidence exists and none can be obtained.** The vendor
  account has exactly one Gemini and the dev Homebridge container holds that one device. This
  is recorded as a limit of the phase, not worked around. Any claim this phase makes about
  two-pump behaviour rests on the harness and on mutation, and must say so.

- **D-11:** Every safety-bearing assertion carries a discriminating mutation, per
  `05-VALIDATION.md`'s binding discipline: apply the mutation, watch the named test fail,
  revert, confirm green, and record which test failed on what line. Before trusting a new
  assertion, check whether its expected value is already what the field holds.

### Harness correctness (entries 17 and 18, pulled in)

- **D-12:** Entries 17 and 18 are fixed **in this phase, before the harness carries this
  phase's evidence.** Both are still in scope, but *both ledger entries state their mechanism
  wrongly*, and research corrected them:

  - **Entry 18.** The entry says `awaitSubscription` returns once the client subscribed to
    *either* device. It cannot: the shadow client subscribes to **every device's topics in one
    awaited call** before any `get` publish (`src/cloud/shadow.ts:346-352`). The real defect is
    that `publishedTopics` is **cumulative and never reset**, so the wait returns instantly on
    any **reconnect**. Still a defect worth fixing before this phase's evidence rests on it —
    just not the one recorded.
  - **Entry 17.** The entry calls them dead leftovers. They have **10 live callers**. The real
    problem is that `features/support/steps/harness.ts:131` declares a second, worse
    `currentAccessory` that **shadows** the shared one at `features/support/publishedServices.ts:30`.

  The ledger has no edit verb, so these corrections live here and must be carried into the
  phase's own records rather than silently applied.

### Ledger entry 41

- **D-13:** Ruled **not adopted**, with the limits of the evidence recorded. The silence
  timer keeps arming on any message. The 90-minute live probe that informs this covers one
  device in steady state, seven messages, six heartbeats, and no pump cycle, fault, power
  event, reconnect or firmware update — so event-driven vendor reports are unmeasured.
  Adopting it would guard a shape nobody has observed, which is how entry 34's original false
  reason was born. The ruling closes entry 41; it does not claim the sample is strong.

### Signal path, resolved after research

- **D-14:** The `reportedShadowSilent` latch becomes **per device**, and the `LIVE_REPORTING`
  failure-log observation becomes **per device too**. A naive `some()` over the latch would
  re-create the flatten D-03 removes: one noisy pump would keep re-reporting for a quiet
  neighbour, or a quiet neighbour would suppress the noisy pump's recovery report. The arrival
  callback already has the `deviceId` it needs (`accountRuntime.ts:637`, `:667`).

  Research recommended leaving the log account-wide because "the log's rate limiting has to be
  redesigned". **Measured: it does not.** `FailureLog` already rate-limits per `kind` string via
  `warnedAt: Map<string, number>` (`src/runtime/failureLog.ts:45`, `:50-57`), so a per-device
  kind gets independent rate limiting for free. `kind` is the subject of the recovery sentence,
  and the vendor `deviceId` is a Phase 2 ruling's non-sensitive value that may enter logs.
  One real cost to handle: `warnedAt` retains a removed device's kind until it recovers, so
  device removal should drop it.

### Corrections after research

Four premises this context was written on did not survive measurement. Each is corrected in
place above rather than appended, because this file records what is currently decided, not an
account of what some earlier step did.

| Premise as written | Where it came from | What measurement showed |
|---|---|---|
| The controller-link log names 11 of 16 services | `STATE.md`, the Phase 5 handoff, D-05 here | It names **five scope words**. 17 rows, 16 non-connectivity, **15 stop vouching**, 7 scopes. |
| Entry 18: the wait returns on either device's subscription | `WINDOWS.md` entry 18, D-12 here | Subscription is one awaited call for all devices. The defect is a **cumulative, never-reset** topic count that returns instantly on **reconnect**. |
| Entry 17: dead single-device leftovers | `WINDOWS.md` entry 17, D-12 here | **10 live callers.** The defect is a **shadowed** `currentAccessory`. |
| A single map-valued callback is sufficient | D-01 here | **Empty on a refused launch**, which deletes the credential branch's only input. Corrected to account + byDevice. |

A fifth is a strengthening rather than a correction: the clamp in D-07 must be continuous, not
restart-only, because `process.hrtime.bigint()` does not advance across system suspend.

**Evidence note.** The monotonic finding was falsified in both directions with a Linux time
namespace on the two installed Node runtimes. **Node 24 is not installed and no Node 24 result
is claimed.** The suspend consequence is cited from `man 2 clock_gettime`, not observed — this
host has no accumulated suspend time, so it is recorded as no observation rather than as a
finding.

### Reusable Assets

- **`silentDevices()` already answers per device.** `src/runtime/monitoringHealth.ts:175-179`
  returns every admitted device silent for two heartbeats, in admission order. Entry 19 needs
  no new tracking — only the flatten at line 212 removed and the answer carried downstream.
- **`admitDevice` / `forgetDevice` / `recordShadowMessage` are already device-keyed.** The
  per-device map `lastShadowMessageAt` exists and its docblock already argues why the question
  has one answer per controller.
- **The `Clock` port is injected everywhere.** `src/runtime/clock.ts` is a one-method interface
  with `systemClock` wired at the composition root only, so D-06 adds a sibling rather than
  retrofitting injection.
- **The two-pump Cucumber harness** landed in plan 05-13 and is what D-09 rests on.
- **`PumpObservation` is the shape D-08's migration follows** — optional, absent on first run,
  with the seeding path treated as the only one that has ever existed.

### Established Patterns

- **Constructor dependency injection**, per PROJECT.md's open implementation preference.
  `MonotonicClock` follows it.
- **`markMonitoring` compares every member of `MonitoringTrust` by name**, with a comment
  explaining what makes each one load-bearing. A member added to the type and left out of that
  comparison is silent rather than harmless — read the comment at
  `src/accessories/basementGuardian.ts:887-907` before touching the type.
- **`applyMonitoringHealth` is exported for the harness's sake**, so a fan-out living only in
  the platform's callback would be copied into the harness and every scenario would assert
  against the copy. Keep the fan-out exported and shared.
- **The layering order in `distrustReasonsOf` is a decision, not an accident.** Monitoring
  scopes fill before controller-link scopes so a blackout reports the cause that happened.

<specifics>
## Specific Ideas

- **Entry 18 is the reason entries 17 and 18 came into this phase.** A two-pump scenario that
  waits on a cumulative subscription count can return once *either* device subscribed, so it
  could pass for the wrong reason on exactly the multi-device behaviour this phase adds. Fix
  the harness before it carries the evidence.
- **The anchor clamp has a direction and the direction is the whole point.** Sooner, never
  later. A test should fail if the clamp is inverted.
- **Say what the evidence does not cover.** D-10 and D-13 both require the phase's records to
  state their limits rather than read cleaner than the measurement. The Phase 5 handoff names
  this as the most valuable behaviour it observed: an agent measuring a premise its own plan
  asserted and reporting it false, and null results reported as null.
