### The latch drop — a measured null result

**The plan's `must_haves` say a removed device must leave "no failure-log kind **and no latch entry** behind". Measurement says the latch entry needs no drop, and adding one would have been unpinnable code.**

`reportMonitoringHealth` reassigns `reportedSilentDevices` **wholesale** from the map it is about to push (`src/runtime/accountRuntime.ts:551`), and that map is built from `store.deviceIds()`. `runPoll` awaits `applyDevices` — which performs the removal — and only then calls `recordPollSuccess`, so by the time the latch is next written the store has already dropped the device. The entry cannot survive the removal poll, and the latch cannot grow for the life of the process. No drop was added.

This is not asserted by argument alone: `reports nothing for a message from a pump the account has already removed` (`test/runtime/accountRuntime.test.ts:2551`) **passes with no latch-drop code in the tree**, which is the null result stated as a measurement.

Where the behaviour is pinned instead: make the latch accumulate rather than be rebuilt —

**Mutation:** `src/runtime/accountRuntime.ts:551`, `new Set([...byDevice].filter(...))` → `new Set([...reportedSilentDevices, ...[...byDevice].filter(...)])`.

**Result: red.** Two cases failed:

```
✖ reports once per recovery rather than once per message when two messages arrive together
✖ reports nothing for a message from a pump the account has already removed
tests 119 / pass 117 / fail 2
```

Reverted; 119/119. So the case earns its place — it pins the rebuild, which is what makes the drop unnecessary.

## Which Drop Mechanism Shipped, and What an Owner Sees

**`FailureLog.forget(kind)` shipped. `recordSuccess` did not.**

The plan's action text recommends `recordSuccess`, and names the cost: it "emits the recovery line for a device that did not recover, it was removed", then asks which reading an owner is better served by.

An owner is better served by silence. `Live device reporting for account-1_serial-1 recovered.` is a false statement about a safety system: the reporting did not come back, the system left the account. This plugin's stated core value is that HomeKit must not show a false normal, and the plan's own threat register carries `T-05.1-07` (Repudiation) for exactly this line. A one-line info message is low severity, but it is the wrong class of thing to ship deliberately from a file whose comments argue at length against guessed normals.

The plan's argument for `recordSuccess` — that reaching past the log would let "the log's own state and its lines disagree" — does not apply to `forget`, which is the log's own method and leaves nothing claimed. What `recordSuccess` would have made disagree is its own docstring: it means *this activity succeeded*, and a removed system's reporting did not.

**What an owner sees because of the choice:** at the removal, nothing from the failure log — only the platform's own accessory-unregistration line. If the same identifier is ever re-added, its first silence warns as a first warning rather than being rate-limited by its predecessor, and no recovery is announced for a system that has been back for one poll and never failed in that life. The consequence is written at `src/runtime/accountRuntime.ts:411-429` and in the `forget` docblock at `src/runtime/failureLog.ts:26-36`.

**Cost of the choice, stated plainly:** one new interface member on a single-implementation interface, three cases in `test/runtime/failureLog.test.ts`, and a drop that is invisible at the moment it happens — which is why the case observes it at the re-add instead.

## Decisions Made

- **`forget` over `recordSuccess`.** Argued in full above.
- **The harness's `onDeviceRemoved` mirrors the platform's handler.** `src/platform.ts:480` calls `store.remove(deviceId)` on the same signal. A harness that only recorded the call left the device in the store, so the very next poll's success path swept the retained kind and V15's mutation would have failed nothing. This is the phase's named blocking anti-pattern — a check that passes because the thing it rests on already sits at the value the defect produces — met a sixth time and caught before the case was trusted. The change was measured against the existing suite before anything was built on it: 117/117, no shipped case disturbed.
- **The cadence case reads back the two constants it depends on.** `gapBetweenSilencesMs: HEARTBEAT_MS` and `reminderIntervalMs: FAILURE_REMINDER_MS` are asserted as `898_000` and `900_000`. If a heartbeat ever grows past the reminder cadence, the two silences stop sharing an interval and the case would go on passing while proving nothing. Written as data rather than as `HEARTBEAT_MS < FAILURE_REMINDER_MS`, which ESLint correctly rejects as an always-true comparison of two literals.
- **The latch case asserts push counts, not only log lines.** Measured above: the recovery line is identical under the latch collapse. A case built on the recovery line alone would have been the anti-pattern again.
