## Corrected Ledger Diagnoses

`WINDOWS.md` has no edit verb, so both corrections are recorded here in full for plan 05.1-07 to carry into the records. **Both ledger entries state their mechanism wrongly.**

### Entry 18 — the ledger text is wrong

**What the ledger says:** `awaitSubscription` returns once the client subscribed to *either* device.

**Why that cannot be the mechanism:** the shadow client subscribes to every route of every device in **one awaited call** before it publishes any `get` — `src/cloud/shadow.ts:346-352`, `await target.transport.subscribe([...routes.keys()])` followed by the per-device `publish` loop. The routing table and the subscription list are the same set (`fillRoutes`, `src/cloud/shadow.ts:151-160`), so there is no moment at which one device is subscribed and another is not. A per-device partial subscription is not expressible.

**The real defect:** `broker.publishedTopics` is **cumulative and never reset**. The old condition was `publishedTopics.length > 0`. Every reconnect runs `requestEveryShadow` again (`src/cloud/shadow.ts:377-380`), and the array still holds the previous connection's publishes, so on any reconnect the wait returns **instantly** — before the new connection has subscribed to anything. A message published at that moment is lost, and the scenario would report the wrong reason for whatever followed.

**Fixed by:** a per-connection subscription record and `currentSubscriptions()`, plus a wait naming the device.

### Entry 17 — the ledger text is wrong, and the fix is narrower than the entry implies

**What the ledger says:** dead single-device leftovers.

**Why that is wrong:** they have **10 live callers**. In `harness.ts` alone, `currentAccessory` had four (`:382`, `:569`, `:580`, `:593` before this plan) and `topicNamed` had two (`:175`, `:237`).

**The real defect:** `features/support/steps/harness.ts:131` declared a **second** `currentAccessory` that **shadowed** the shared, documented one at `features/support/publishedServices.ts:30`. The local copy returned `registerPlatformAccessoryCalls[0]?.accessories[0]` — the first accessory of the first registration call. On a two-device account that is whichever pump registered first, and after a restart it is a detached object still holding whatever the previous run published to it. The shared rule returns `handedAccessories.at(-1)` — the newest accessory the plugin was handed — and its docblock already argues both cases.

**The `topicNamed` half is narrower than the entry implies, and this is a measurement, not an opinion.** `topicNamed`'s device is **not** resolvable from the world's seeded device list. The four scenarios that reach it — `features/harness.feature:43`, `:50`, `:56`, `:62` — **seed no devices at all**. They are self-tests of the fake broker; their device identifier is only the subject of a topic string. So the two callers pass the module placeholder `DEVICE_ID` explicitly. That removes the hidden closure and makes the single-device assumption visible at the call site, which is the whole of what is available here. **It does not make those four scenarios multi-device, and entry 17 is not closed more widely than that.**

## Decisions Made

- **The record is cleared on each `client` event, not only keyed by identifier.** A reconnecting plugin presents the same client identifier, so a `Map` keyed by `client.id` alone would carry the previous connection's subscriptions forward — cumulative again, which is exactly entry 18's defect in a new shape. Clearing on connect is what makes `currentSubscriptions()` a statement about the connection now open.
- **The new assertion reads the production topic contract.** `SHADOW_TOPICS.updateAccepted` rather than the harness `shadowTopic`, so a divergence between what the plugin subscribes to and what the harness names would surface rather than cancel out. `shadow.ts` already imported `SHADOW_TOPICS`, so no new import was added.
- **The assertion refuses an empty seed.** `every` over an empty list is true, so on an unseeded scenario the step would have passed with no connection open at all — this phase's named blocking anti-pattern in miniature. The step throws instead, naming the missing premise.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing Critical] The per-client record is cleared when a client of the same identifier reconnects**

- **Found during:** Task 1 (GREEN)
- **Issue:** The plan specified `Map<string, string[]>` keyed by `client.id` with `currentSubscriptions()` reading the newest entry of `clientIds`. On a reconnect that reuses the client identifier — which the plugin does whenever credentials have not rotated — `clientIds.at(-1)` is the *same* identifier, so the map entry still holds the closed connection's topics. That contradicts the task's own stated behaviour ("a closed connection's history cannot satisfy a wait") and the plan's prohibition on a wait satisfied by a cumulative record.
- **Fix:** the `client` listener sets an empty array for that identifier, so each connection starts from an empty record.
- **Files modified:** `features/support/fakeShadowBroker.ts`
- **Verification:** `npm run test:cucumber` green at 102/102. Honest caveat recorded above: mutating this line out fails nothing today, so the behaviour is reasoned rather than pinned.
- **Committed in:** `44f3f13`

**2. [Rule 2 - Missing Critical] The new Then step refuses an empty seeded device list**

- **Found during:** Task 1 (RED)
- **Issue:** the plan's wording — "asserts `currentSubscriptions()` contains the `update/accepted` topic of every device in `world.devices`" — is vacuously true when `world.devices` is empty. `features/harness.feature` has four scenarios that seed no devices; the step would pass there with no connection at all.
- **Fix:** the step throws with a named message when nothing was seeded, following the voice of `deviceIdNamed` in the same module.
- **Files modified:** `features/support/steps/shadow.ts`
- **Verification:** the step is used only in a scenario whose Background seeds one device (`features/degradedOperation.feature:7-11`), and the RED gate failed on the subscription, not on the guard.
- **Committed in:** `2dd67a2`

**3. [Rule 3 - Blocking] Two unused type imports removed from `harness.ts`**

- **Found during:** Task 2
- **Issue:** deleting the local `currentAccessory` orphaned `FakeAccessory` and then `FakeHomebridgeApi` in `harness.ts`'s type imports. `npm run lint --max-warnings=0` failed with `'FakeHomebridgeApi' is defined but never used`.
- **Fix:** both names removed from the type import; the whole import line went with the second.
- **Files modified:** `features/support/steps/harness.ts`
- **Verification:** `npm run lint && npm run typecheck` exit 0.
- **Committed in:** `c2921ef`

**4. [Documented, not a fix] The assertion reads `SHADOW_TOPICS.updateAccepted`, not the harness `shadowTopic`**

- **Found during:** Task 1
- **Issue:** the plan says to build the topic with "the exported `shadowTopic` helper rather than a hand-written string". Both `shadowTopic` (harness) and `SHADOW_TOPICS.updateAccepted` (production) produce the identical string and both satisfy the plan's stated reason, which is to avoid hand-writing.
- **Fix:** used `SHADOW_TOPICS.updateAccepted`, already imported by `shadow.ts`. It asserts against the plugin's own topic contract, so a divergence would surface instead of cancelling out, and it adds no import.
- **Files modified:** `features/support/steps/shadow.ts`
- **Verification:** `npm run test:cucumber` green; the RED failure message printed the full production topic.
- **Committed in:** `2dd67a2`, `44f3f13`
