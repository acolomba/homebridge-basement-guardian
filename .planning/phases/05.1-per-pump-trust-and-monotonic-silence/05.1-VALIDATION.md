# Phase 05.1 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution.
>
> **Binding, in the sense `05-VALIDATION.md` is binding.** Every row names the mutation that
> must fail it. A row whose named mutation still passes is not evidence. Apply the mutation,
> run the named command, **record which test failed and on what line**, revert, confirm green.
> A mutation that fails nothing is a finding to write down, not a failure to hide — say where
> the behaviour is pinned instead, as ledger entries 21 and 26 do.

## Sampling Rate

- **After every task commit:** `npm run test:unit`, in the capture-both form below.
- **After every plan wave:** `npm test`, **run alone** — a concurrent run has been measured
  producing false failures (`1385 / fail 0` solo versus `pass 1383 / fail 2` concurrent).
- **Before `/gsd-verify-work`:** `npm test` green **plus** `npm run test:coverage:all` at
  100/100/100 **plus** `npm run fallow`.
- **Max feedback latency:** ~25 seconds (`npm run test:unit`).

### The verify form, every time

`pipefail` is **off** in this shell, so `npm test | grep x` returns *grep's* status and npm's
failure is discarded. Proven: `(exit 7) | grep x` returns 1. Capture and assert both:

```bash
O=$(npm test 2>&1); R=$?; test $R -eq 0 && printf '%s\n' "$O" | grep -qE '^ℹ fail 0$' && printf '%s\n' "$O" | grep -qE '^[0-9]+ scenarios \([0-9]+ passed\)$'
```

**Never** pipe a suite command directly into a filter inside a `<verify>` block.
