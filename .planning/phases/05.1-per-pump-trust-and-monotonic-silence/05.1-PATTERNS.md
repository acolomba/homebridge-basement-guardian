## 1. The new `MonotonicClock` port

### `src/runtime/monotonicClock.ts` (port, pull)

**Analog:** `src/runtime/clock.ts` — the whole file, 15 lines. Copy its shape line for line.

**The analog, verbatim (`src/runtime/clock.ts:1-15`):**

```typescript
/**
 * Source of the current time.
 *
 * Scheduling, timeout, and receipt-time code takes a clock by injection rather
 * than reading `Date.now()`, so a test drives time without faking a global.
 */
export interface Clock {
  /** Returns the current time in milliseconds since the Unix epoch. */
  now(): number;
}

/** The process clock. Wire this at the composition root only. */
export const systemClock: Clock = {
  now: () => Date.now(),
};
```

**Conventions to copy, named so nothing is guessed:**

| Convention | What `clock.ts` does |
|---|---|
| Module docblock | None. A file-level `/** … */` sits on the **interface**, not on the module. (Contrast `monitoringHealth.ts:1-18`, which uses `@fileoverview` — that is the convention for modules with behaviour, not for a bare port.) |
| Interface doc | States *why injection*, not just what the type is. The monotonic sibling's reason is the one D-06 gives: the two bases must not be confusable at a call site. |
| Method doc | One `/** … */` line on `now()` naming the **unit and the epoch**. The sibling's line must say the epoch is arbitrary and never comparable to wall time. |
| Export style | Named exports only. No default, no barrel. |
| Production instance | A `const` object literal with an arrow body, doc-commented **"Wire this at the composition root only."** Copy that sentence verbatim. |
| Naming | `systemClock` → the sibling is `systemMonotonicClock`. |
| Constants | `clock.ts` has none. The sibling needs `NANOSECONDS_PER_MILLISECOND = 1_000_000n` as a module-level `const` above the instance — that placement matches `monitoringHealth.ts`, where constants sit above the code that uses them with a docblock giving the reason for the value. |

### Precedent B — `isPumpObservation` (accessory-context member)

```typescript
// src/accessories/pumpRecords.ts:102-122 — verbatim
function isNumberOrAbsent(value: unknown): boolean {
  return value === undefined || typeof value === 'number';
}

// A record restored from the Homebridge cache is whatever JSON was on disk, whatever its declared
// type promises, so it is checked before it is resumed. The narrowing assertions below are safe
// because every member they reach for is read back through a `typeof` test.
function isPumpObservation(value: unknown): value is PumpObservation {
  if (typeof value !== 'object' || value === null) {
    return false;
  }

  const candidate = value as Partial<PumpObservation>;
  const label = candidate.lastActivationWasTestActivity;

  return (
    typeof candidate.observationStartedAt === 'number' &&
    typeof candidate.activationCount === 'number' &&
    isNumberOrAbsent(candidate.lastActivationAt) &&
    (label === undefined || typeof label === 'boolean')
  );
}
```

Resume-or-seed, which is the exact migration verb (`src/accessories/pumpRecords.ts:217-236`):

```typescript
// The stored record is resumed whole or not at all. …
function resumedRecord(): StoredRecord | undefined {
  const { primaryPump, backupPump, watermarks } = context;

  if (primaryPump === undefined && backupPump === undefined && watermarks === undefined) {
    return undefined;
  }

  if (!isPumpObservation(primaryPump) || !isPumpObservation(backupPump) || !isActivationWatermarks(watermarks)) {
    log.warn('The stored pump observation record could not be read, so observation starts again from now.');

    return undefined;
  }

  return { primaryPump, backupPump, watermarks };
}

let record = resumedRecord();
```

```typescript
   * observed anything.
   *
   * Absent is the ordinary first-run state rather than an error: an
```

### Which one the anchor should follow, and why

**Follow Precedent A (`auth.ts`) for the store, Precedent B for the field's doc-comment and its
absent-is-ordinary migration language.**

The deciding fact is timing, and it is a read of the code rather than a preference. The anchor is
consumed at **admission**:

```typescript
// src/runtime/accountRuntime.ts:343-352 (research-verified)
  health.admitDevice(device.deviceId);   // :343-349 — inside applyDevices
  …
  options.onTrustworthyInventory(…);     // :351-352 — accessories exist only after this
```

`onTrustworthyInventory` is what creates or restores accessory objects, and it runs **after** the
admission loop. So at the instant the runtime needs the anchor, no `AccessoryContext` for that device
has been touched on this poll, and the runtime holds no handle to accessory context at all. Precedent
B would require either inverting that order or adding a callback whose only job is fetching a
timestamp — new coupling for a value that is purely a runtime concern.

Precedent A already has `storagePath` threaded into the same seam
(`src/platform.ts:550` → `src/runtime/accountRuntime.ts:998`, `:1043`), so the store is constructible
where `createMonitoringHealth` is (`accountRuntime.ts:265`) with no new plumbing.

Two Precedent-A costs the plan must state, both with existing answers in the analog:

1. **Pruning.** Anchors must be dropped where stamps are, and there is exactly one such place:
   `health.forgetDevice` at `src/runtime/accountRuntime.ts:382`, whose surrounding comment
   (`:377-381`) is the reason it is the only one. Add the anchor removal there and nowhere else.
   `forgetDevice` in the projection is a one-liner to mirror (`monitoringHealth.ts:198-200`).
2. **Predicate shape.** The anchor value is a `number`, so the read-back guard is
   `typeof x === 'number'`, never truthiness — `JSON.stringify` turns `NaN`/`Infinity` into `null`
   and a zero anchor is a legal value. `isNumberOrAbsent` (`pumpRecords.ts:102-104`) is the exact
   helper to copy for the per-entry check even under Precedent A.

If the maintainer overrides to Precedent B, the plan must answer the admission-ordering question
above and D-08's "one-way" reversibility applies in full.

### 3a. The movable clock — `test/runtime/monitoringHealth.test.ts:26-40`

```typescript
// One clock a case moves by assignment, so elapsed time is stated rather than
// waited for.
interface MovableClock {
  clock: Clock;
  moveTo: (at: number) => void;
}

function movableClock(): MovableClock {
  let now = START_TIME;

  return {
    clock: { now: () => now },
    moveTo: (at: number): void => {
      now = at;
    },
  };
}
```

Copy this shape exactly for the monotonic sibling. Three things about it are load-bearing:

- **`moveTo`, not `advance`.** Every case in the file reads
  `const { clock, moveTo } = movableClock();` then `moveTo(START_TIME + TWO_MISSED_HEARTBEATS_MS)`.
  A monotonic sibling with an `advance` verb would read differently from the 17 cases at
  `:129`–`:349` beside it. (Note `test/runtime/failureLog.test.ts:19-27` uses the *other* shape,
  `{ clock, advance }` — do not mix them into one file.)
- **Boundary constants stated, not computed.** `:20-22`:

  ```typescript

  const TWO_MISSED_HEARTBEATS_MS = 1_796_000;
  ```

  with the comment at `:17-19` explaining why they are written out rather than derived from the

- **The named two-device fixtures already exist**: `DEVICE_ID` / `OTHER_DEVICE_ID` (`:14-15`) and

```typescript
/**
 * The accessory a scenario's plugin is publishing onto now.
 *
 * Every scenario seeds exactly one physical device, so a step reads state back through the newest
 * accessory the plugin was handed. It is the registered one until a restart, and the one restored
 * from the cache afterwards: reading the registered one after a restart would read a detached
 * object still holding whatever the previous run published to it, which passes an assertion about
 * a value that came back without anything having brought it back.
 *
 * One device is the default shape, not the only one: an account carrying several systems hands over
 * one accessory per system, and a step meaning a particular one reaches for `accessoryNamed`.
 */
export function currentAccessory(homebridge: FakeHomebridgeApi): FakeAccessory | undefined {
  return homebridge.handedAccessories.at(-1);
}
```

**What a correct shared binding looks like — three properties, all already present in the exported
one:**

1. **`handedAccessories`, not `registerPlatformAccessoryCalls`.** The `harness.ts` copy reads the
   *first* accessory of the *first* registration call. After a restart that object is detached and
   still holds what the previous run published to it — the copy's own docblock does not know this;
   the exported one's does.
2. **`.at(-1)`, not `[0]`.** On a two-device account `[0]` is whichever pump registered first, which
   is an ordering the scenario never stated.
3. **A named escape hatch exists for multi-device steps** — `accessoryNamed`
   (`features/support/publishedServices.ts:45-…`), which **throws** on an unknown name rather than
   falling back, with the reason stated at `:37-41`: a fallback would let every assertion in a
   multi-device scenario read one system twice and pass whether or not the other was ever published.

**The fix, and its exact blast radius** (measured with
`grep -n 'currentAccessory\|topicNamed\|DEVICE_ID' features/support/steps/harness.ts`):

| Symbol | Callers in `harness.ts` |
|---|---|
| `currentAccessory` | `:382`, `:569`, `:580`, `:593` — **4 live callers**, not dead |
| `topicNamed` | `:175`, `:237` — 2 live callers; closes over module `DEVICE_ID` at `:142` |
| `DEVICE_ID` (`:37`) | `:142`, `:293`, `:301`, `:309`, `:622` |

Delete the local `currentAccessory` (`:131-133`) and import the shared one — the import precedent is
