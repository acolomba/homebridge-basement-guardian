<objective>
Build the durable half of the phase: the four read-only record characteristics an owner reads, the
module that decides what a record says, and the one-method port that writes it to disk.

Purpose: `src/persistence/accessoryContext.ts` has typed `primaryPump`, `backupPump` and `watermarks`
since Phase 1 and no production code has ever read or written any of them. This plan defines the whole
runtime behaviour behind those types, including the three places it can go quietly wrong: a run
counted twice because a restart landed mid-cycle, a device timestamp stored in the wrong unit and
rendering a 1970 date, and a count on a characteristic narrow enough that HAP clamps it into a
permanent lie.
Output: a record per pump that survives a restart, counts only what the plugin watched, and says so.
</objective>

The classification table the algorithm implements, measured on real hardware
(`.planning/intel/constraints.md` lines 491-505). `backup_pump_timestamp` advances several seconds
before `test_timestamp`, which is why classification waits:

```
phase                 backup timestamp   test timestamp   backup running   test running
idle                  prior value        prior value      false            false
backup pump active    prior value        prior value      true             true
backup pump stops     new value          prior value      false            true
test completes        new value          new value        false            false
```

| Boundary | Description |
|----------|-------------|
| Decoded device state -> the persisted record | The first durable state this plugin writes. Once written it outlives the code that wrote it. |

| The record -> published characteristics | A number an owner reads as a fact about their basement. |
