## The six open decisions

### 1. Narrow `D-15` — drop the `update/rejected` leaf from the fake broker? **OPEN**

`D-15` says the phase adds `update/rejected` to `ShadowTopicLeaf`. The plugin makes
exactly one MQTT publish in its whole life and it is a shadow `get` with an empty
payload `[VERIFIED: src/cloud/shadow.ts:345, the only publish call in the module]`, so
it never sends a shadow update and the service never has one of its updates to reject.
It does not subscribe to the leaf either `[VERIFIED: src/cloud/shadow.ts:151-158]`. The
`{"desiredData": ...}` body `D-15` calls "the plugin's publish" is the REST body
`[VERIFIED: src/cloud/api.ts:169]`.

- **Recommendation:** narrow it. The broker instead gains the fake pump's *reaction* —
  an accepted command flips `test_running` and reports on `update/accepted`. Rejected,
  timed-out and late come from `fakeRestApi`, where the wire shapes are measured.
- **If refused:** the harness publishes a message the real system never sends, to a
  client that never subscribes.
- **Note:** whoever ratifies should strike the `update/rejected` clause from `D-15` in
  `04-CONTEXT.md` at the same time.

### 2. Allow a test-only import of `@homebridge/hap-nodejs`? **OPEN**

`features/support/fakeHap.ts` has no `Switch`, no `On`, no `onSet`, no `HAPStatus`
`[VERIFIED: features/support/fakeHap.ts:172-190, 296-300]`. The phase would author every
write-path semantic it then tests. The "never import HAP-NodeJS directly" rule is scoped
to **runtime** in both `CLAUDE.md` and `src/accessories/customCharacteristics.ts:21-25`;
this would be the first test-scope exception.

- **Recommendation:** allow it for one file, `test/accessories/hapWriteFidelity.test.ts`,
  running the same four write cases against real HAP and the fake and asserting they
  agree. The package resolves as a bare specifier
  `[VERIFIED: require.resolve('@homebridge/hap-nodejs') this session]`.
- **If refused:** the five CTRL-05 scenarios are self-confirming.

### 3. Accept a deferred push to clear HAP's sticky `statusCode`? **OPEN — highest consequence**

After a rejected `onSet`, every later **read** of that characteristic throws the same
status until something pushes a value
`[VERIFIED: node_modules/@homebridge/hap-nodejs/dist/lib/Characteristic.js:1729, read and
executed this session]`. `03-CONTEXT.md` D-05 forbids `HapStatusError` because it produces
"No Response"; `04-CONTEXT.md` D-04 requires it for six refusal causes. Not a direct
contradiction — D-05 governed degradation reporting, D-04 governs command refusal, and the
effect is per-characteristic rather than per-accessory (probed). The residual is real: a
refused press leaves that Switch answering an error to every read until the next poll,
up to ~15 minutes.

- **Recommendation:** push the reported `On` value back through the injected `Timers`
  port at delay 0. It must be a macrotask — a microtask queued in the handler runs
  *before* HAP assigns the status. The existing timer-freedom assertions are scoped to
  `update()` `[VERIFIED: test/accessories/basementGuardian.test.ts:1482-1517]`, so this
  does not break them, but it is the first deferral in the accessories tier.
- **Also add** a real-home check to the D-03 session: press a refused control and watch
  what the tile does.
- **If refused:** the Switch is unreadable between a refusal and the next poll, and what
  Apple Home draws in that window is unknown.

### 4. Add `uint32` to the characteristic format table? **OPEN**

`define()` supports `'bool' | 'uint8' | 'string'`
`[VERIFIED: src/accessories/customCharacteristics.ts:91]`. `uint8` caps at 255 and HAP
**clamps** rather than rejects, so an activation count would silently stop advancing and
keep reading as fact. Reachable in weeks.

- **Recommendation:** add `uint32`. One line.

### 5. Timestamp unit for `lastActivationAt`? **OPEN**

Device timestamps are Unix **seconds**
`[VERIFIED: .planning/intel/constraints.md:231 and :241]`; `lastActivationAt` is
documented local **milliseconds**
`[VERIFIED: src/persistence/accessoryContext.ts:31-32]` and `isoTimestamp` expects ms
`[VERIFIED: src/accessories/basementGuardian.ts:288-290]`. `D-11` stores the device value,
so the units must be reconciled or the characteristic renders a 1970 date.

- **Recommendation:** convert to ms at the record boundary and reword the field's
  docblock. `constraints.md:503` forbids *comparing* a device timestamp against local
  time; a unit conversion compares nothing.
- **If read more strictly:** widen the stored type to carry seconds explicitly.

### 6. Pending-window scope? **OPEN**

Not stated in `04-CONTEXT.md`: is the 30-second window per capability per accessory, or
global?

- **Recommendation:** per capability per accessory, so one accessory's pending self-test
  cannot block another's mute.

## What the research already settled, so nobody re-derives it

- HAP retains an accepted write and never stores a rejected one — `D-05` and `D-04` both
  hold as written `[Characteristic.js:1799-1833, read and executed]`.
- `StatusActive` on a `Switch` is settled on HAP's side: `addOptionalCharacteristic` has
  no per-service allow-list, so the mechanism is identical to the `ConfiguredName`-on-
  `ContactSensor` route `39560ac` proved. Only Apple Home's rendering is open, which is
  `D-03`'s own item.
- `api.hap` carries every status `D-04` names, at the documented values.
- The record characteristics belong on the existing `PumpService` as **optional** — the
  service's own docblock pre-authorises exactly this
  `[src/accessories/customServices.ts:24-29]`.
- `test_timestamp` belongs to the new `self-test` scope, not `pump`; filing it under
  `pump` would let a bad timestamp deactivate live pump safety signals.
- The `ensureService` projection-length gate needs an explicit `alwaysPublish` exemption
  for the two control rows, and its docblock must be revised rather than left claiming a
  rule that now has exceptions.
