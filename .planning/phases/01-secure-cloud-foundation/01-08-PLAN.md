  <action>
Create the broker from the in-process MQTT broker package and expose it over a WebSocket server bound to the loopback address on an ephemeral port, resolving the factory promise once the port is known.

**Do not pair the WebSocket library's own stream helper with the broker.** That combination produces a WebSocket connection and a broker client object and then nothing at all: no error, no acknowledgement, no timeout — the scenario simply hangs. The cause is that the MQTT client writes each connect field as a separate stream write and the WebSocket layer turns each write into its own frame, while the broker reads exactly one chunk per readable event; it consumes the first byte, finds no complete packet, and never reads again. Over plain TCP the kernel coalesces the writes, which is why the same pairing works there and hides the defect.

Write the coalescing bridge instead: a duplex whose write side sends the chunk as a binary WebSocket message, whose destroy side closes the socket, and whose read side accumulates every message arriving in a tick into a pending list, then on the next immediate tick concatenates the list into one buffer and pushes it once. Push the null terminator when the socket closes, after a final flush, and destroy the duplex on a socket error. The research reference implementation is roughly twelve lines and was verified end to end including a shadow-topic round trip and a forced reconnect.

Record every accepted handshake's query string and every connecting client identifier, so a scenario can assert that a reconnect carried rotated credential material and a new client identifier without the scenario knowing anything about how the URL was signed.

Provide publish helpers for the three subscribable shadow topics, each building the topic from the supplied device identifier and publishing a JSON payload carrying the shadow document and its version. Provide `disconnectAll` so a scenario can force the reconnect path, which matters because the provider closes a signed WebSocket at its twenty-four-hour ceiling regardless of anything the plugin does, making a periodic reconnect normal operation rather than a fault.

Publish helpers for the delta topic and for the plugin-side update topic are deliberately absent: this version never writes the shadow, and delta messages carry requested state that the merge rules ignore entirely. Do not add them.

`close()` closes the broker and the WebSocket server and resolves once every connection is destroyed.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test suite → network | A test harness that can reach the public network can reach the real vendor with real credentials. |
| harness code → production code | A seam added for the harness can become a bypass that ships. |
| test fixtures → repository | Fixture data is committed and published to a public repository. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-40 | Information disclosure | deterministic suite reaching the live vendor | high | mitigate | Every vendor service has a loopback stand-in bound explicitly to the loopback address on an ephemeral port; no fixture holds a real credential, and the opt-in real-hardware profile is a separate Cucumber profile selected by tag. |
| T-01-41 | Elevation of privilege | unsecured scheme in the harness | high | mitigate | The harness reaches its local broker through the injected scheme parameter the signer already accepts. No certificate-verification bypass exists anywhere, and production always supplies the bundled secure protocol constant. The alternative — serving TLS with a self-signed certificate — was rejected precisely because it would require a verification escape hatch that must never reach production. |
| T-01-42 | Tampering | test-only production hooks | medium | mitigate | The harness composes the real modules through their existing dependency-object factories. No reset hook, state reader, test mode, or exported-for-testing symbol is added to production code. |
| T-01-43 | Denial of service | leaked sockets between scenarios | medium | mitigate | The world owns every fake's lifetime and an after hook runs cleanup in reverse order; the acceptance criteria require the Cucumber process to exit on its own. |
| T-01-44 | Information disclosure | committed fixtures | medium | mitigate | Fixture values are short, self-describing placeholders. The device identifier in fixtures is a placeholder, never a real account identifier joined to a real serial number, and the pre-commit secret scan runs on every commit. |
</threat_model>
