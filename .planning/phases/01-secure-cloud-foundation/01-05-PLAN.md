<objective>
Make unattended authentication survive restarts without weakening the account, and make every authentication failure route to the one response that is safe for it.

Purpose: `AUTH-01` needs a cached token reused across restarts; `AUTH-02` needs that cache to be owner-only, under the Homebridge storage path, and free of the raw email. `D-08` invalidates the cache when the configured account changes, so a token for the previous account cannot be reused for up to its observed thirty-day lifetime. `D-13` stops on credential rejection, because the vendor's brute-force block is lifted only when thirty days pass from the last failed attempt and a retrying plugin refreshes that window forever. `D-22` deliberately overrides the research recommendation for HTTP 429 and retries on a long interval instead, with mitigations this plan must implement rather than soften.

Output: an auth client that reuses a valid cached token, rewrites the cache atomically at owner-only permissions, and answers every failure class distinctly.
</objective>

Vendor authentication contract (`.planning/intel/constraints.md` section 3):

- `POST https://<auth0Domain>/oauth/token` with a JSON body carrying `grant_type` of
  `http://auth0.com/oauth/grant-type/password-realm`, `realm`, `client_id`, `username`, `password`,
  and `scope` of `openid profile email`.
- The observed `id_token` lifetime is thirty days. Reauthenticate before the cached token expires.
- An unauthenticated REST request returns HTTP 403 with a token-missing error.

Vendor throttling behavior (Auth0 brute-force protection, cited in `01-RESEARCH.md`):

- The default threshold is ten incorrect attempts from one IP address against one user identifier.
- A block is lifted only when thirty days pass from the **last** failed attempt.
- A blocked request returns HTTP 429 with an error of `too_many_attempts`.

  <action>
Add the disk cache to `src/cloud/auth.ts`, keeping the exported signature the `<interfaces>` block declares and adding `storagePath` and `createSalt` to `AuthClientOptions`. Export `TOKEN_CACHE_FILENAME` so the test and the composition root agree on one name.

Read the cache on the first `idToken()` call. Validate the parsed payload with a hand-written predicate rather than trusting it: `strictTypeChecked` makes an unchecked parse unusable anyway, and `D-08` requires that unreadable, malformed, expired, or fingerprint-mismatched all mean the same thing — log at debug and reauthenticate, never a hard failure.

Compute the fingerprint as a SHA-256 digest over the stored salt concatenated with the configured email. Generate the salt once through the injected `createSalt` and store it in the cache file alongside the fingerprint so the comparison is stable across restarts. The raw email must not appear in the file.

Write the cache with a temporary sibling file and a rename over the target. Passing an owner-only mode to a write against an **existing** file is silently ignored, because the POSIX open call applies the mode only when it creates the file; the very first token refresh after any mode drift would otherwise leave the token readable by every local user on the host. The temp-then-rename shape also makes the write atomic, which matters because a truncated cache is a reauthentication trigger and reauthenticating too often walks toward the vendor's brute-force threshold. Name the temporary file with the process id so two Homebridge processes cannot collide on it.

Reauthenticate on a renewal margin rather than at the exact expiry: treat a token as unusable once the injected clock is within the margin of `expiresAt`. Declare the margin as a named module-level constant.

Place the cache under the injected storage path and nowhere else; the Verified checklist requires files to live inside the Homebridge storage directory.

Write the behavior cases first. Use one `mkdtemp` under the OS temporary directory per case as the injected storage path, and remove it with a recursive, forced removal registered through `t.after()`. Do not share a directory across cases and do not write into the repository. Gate the permission assertions on a non-Windows platform, since `AUTH-02` requires owner-only permissions only where the operating system supports them; record the gate in the case title.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin → local filesystem | The cached identity token is written to a multi-user host's disk. |
| plugin → vendor Auth0 tenant | Repeated failed attempts against this boundary can lock the administrator out of their own account for thirty days. |
| vendor Auth0 tenant → plugin | Response bodies and error objects can quote the credentials that were sent. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-21 | Information disclosure | token cache file | high | mitigate | Write to a per-process temporary sibling at owner-only mode and rename over the target, because a mode passed to a write against an existing file is ignored. The permission assertion runs after a **second** write, which is the only ordering that catches the defect. |
| T-01-22 | Information disclosure | token cache location | high | mitigate | The cache path is built from the injected Homebridge storage path and nowhere else, satisfying the Verified rule that plugin-written files live inside the Homebridge storage directory. |
| T-01-23 | Spoofing | stale token for a previous account | medium | mitigate | The cache holds a salted fingerprint of the configured email; a mismatch discards the cache and reauthenticates, so a token for a previous account cannot be reused for up to its thirty-day lifetime. The raw email is never stored. |
| T-01-24 | Denial of service | self-inflicted account lockout | high | mitigate | An explicit credential rejection latches the client halted and makes zero further network calls until the process restarts, so a typo cannot refresh the vendor's thirty-day block. |
| T-01-25 | Denial of service | HTTP 429 retry policy | medium | accept | `D-22` deliberately retries a 429 on a long interval rather than halting, because a 429 can originate from shared-IP throttling unrelated to this account and permanently halting a basement safety monitor on a throttling response is the worse outcome. The accepted risk is that a genuine block has its thirty-day window refreshed. Mitigations implemented: a thirty-minute interval rather than the capped backoff, and a warning that names the 429, states the thirty-day window, and tells the administrator how to stop the plugin. |
| T-01-26 | Information disclosure | authentication failure logging | high | mitigate | Every failure path logs a fixed message plus an HTTP status; the request body, headers, and response body never reach the logger, and the redacting wrapper is a second, structural line of defence. |
</threat_model>

## Flagged Planner Assumptions

The deterministic edge probe returned one `unclassified` row for `AUTH-01` that the auto-resolution
rules leave `unresolved`. It is surfaced here rather than dropped:

- **AUTH-01, category `unclassified`.** The probe could not classify the requirement. The planner's
  reading is that the uncharted edge is what the vendor's Auth0 tenant actually returns for wrong
  credentials on the password-realm grant. The research assumptions log records this as an open
  assumption: the rejection error code is widely reported but the vendor's own error-code page does
  not list it. This plan handles it by treating **any** non-429 4xx as terminal, so the `D-13` stop
  path fires even if the code differs from the expected one. The residual risk if that reading is
  wrong is the opposite failure — halting on a recoverable 4xx — which is recorded here and is safe
  relative to the alternative of retrying into a thirty-day block.
