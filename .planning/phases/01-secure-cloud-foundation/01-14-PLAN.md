<objective>
The shadow client keeps its connection state in four closure variables shared by every connection it has ever opened, and superseding a connection neither detaches its handlers nor ends it. The verifier reproduced both consequences against the built code: a late close from a replaced connection flipped the client to disconnected while a newer connection was live and subscribed, and a retry whose wait had already elapsed opened a second connection after `close()` that nothing would ever end.

Purpose: SC-4's own words are that repeated connection cycles leave no superseded connection driving live state and no connection nothing will close. Both halves currently fail. The reproduced direction errs safe — it reports degraded while healthy — but the same structure supports the unsafe direction, and a connection that is live with nothing subscribed is a monitoring path that is dead and says it is fine.

Output: a connection that owns its own state, an opener that refuses to run during shutdown, and transport operations that fail on a deadline instead of parking forever.
</objective>

    Close gap 3 and the shadow half of gap 5 (CR-03, CR-05). Start red: write the first and the fourth cases above against the current module with injected transport doubles, and watch each reproduce the verifier's finding.

    Give each connection a generation. Take a token when the opener runs, and have every handler the opener registers check that its token is still the current one before it does anything. A notification from a connection the client has replaced is then ignored rather than allowed to rewrite the live connection's health or start a reconnect chain.

    End the connection being replaced before installing the new one. The transport memoizes its own end, so this is safe whether or not the connection had already gone down, and it is the half of SC-4 that reads literally as leaked work.

    Guard the opener itself on the closing flag. The flag is checked when a reconnect is scheduled, but the work handed to the retry policy is the opener, which has no guard of its own — so a timer that had already resolved when `stop()` ran opens a brand-new connection after shutdown, and the memoized ending promise belongs to the previous transport, so nothing ever ends the new one. D-05 chose a client library whose own reconnect timer defaults to one second with no ceiling, which is why the adapter disables it and the guarded policy owns the shape of the delays.

    Stay inside the health budget: sixty lines per unit and cognitive complexity fifteen. The opener will want a small named predicate for "this notification belongs to the current connection" rather than the same comparison repeated at four registration sites.

  <behavior>
    - The connected notification is raised after the subscription resolves, not when the socket opens.
    - A connection whose subscribe callback never fires reports a refused subscription once the deadline passes, ends the connection, and retries.
    - A connection whose publish callback never fires does the same.
    - A subscribe or publish that settles normally leaves no pending timer behind.
    - A device identifier that would form a wildcard topic is left out of the routing table and the subscription list, and is reported once without naming the identifier.
  </behavior>
  <action>
    Close WR-11, the third consequence of CR-03, and WR-14 item 2.

    Today the client sets itself live and raises the connected notification the moment the socket opens, then fires the subscription without waiting. If that connection is already dead, its subscribe callback may never fire at all — there is no deadline on it — so the client sits reporting connected with nothing subscribed and no shadow message able to reach the store, while the runtime reports the healthy combined path. That is a silently dead monitoring path reporting normal, which is the failure class this project exists to prevent.

    Under D-15 a shadow the plugin cannot use costs latency rather than correctness, because the poll is the reconciliation backstop — but that trade only holds if the runtime knows the shadow is unusable. Reporting connected over a socket with nothing subscribed converts a degraded path into a silent one.

    Move the connected notification, and the flag the `connected` getter reads, to after the subscription resolves. Keep the established flag where it is: it exists to tell a refused handshake apart from a routine close, and that distinction is made at socket level. Guard the notification on the current generation from task 1, so a late subscription belonging to a replaced connection cannot announce anything.

    Give the transport a deadline. Add a required deadline to the transport options and race both the subscribe and the publish against it, rejecting when it expires so the existing catch in the full-shadow request runs, gives the connection up, and retries through the guarded policy. The loser timer must be cancelled when the operation settles, through an abort signal or an equivalent — a pending timer left behind would hold the Node process open and contradict the SYNC-05 claim that shutdown leaves no timer running. Assert that property in the transport's own test.

    Supply the deadline from the shadow client as a named module constant with a comment giving its reasoning.

    Then keep wildcards out of the topic surface. The device identifier is interpolated into MQTT topics with no checking, so an identifier containing a wildcard character would create a subscription whose incoming topics cannot be found in the routing table, and every message for that device would be dropped by the unresolved-route path in silence. Refuse such an identifier where the routes are built: leave it out of both the routing table and the device list, and report it once at warn saying that a device identifier could not be used as a shadow topic — without quoting the identifier, because it embeds the account identifier. The device still has the poll as its source, so this is a narrowed scope rather than a lost device, and the message says so.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| AWS IoT message broker → plugin | Connection notifications from a remote party drive the plugin's own health reporting. |
| superseded connection → live connection state | A replaced connection can still speak, and what it says is believed. |
| vendor device identifier → MQTT topic | An untrusted identifier is interpolated into the topic the subscription is built from. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-75 | Spoofing | superseded connection reporting the live connection's health | high | mitigate | Every handler checks its generation token before acting, so a notification from a replaced connection is ignored rather than believed. Reproduced first as a failing case, then asserted. |
| T-01-76 | Denial of service | connection nothing will close | high | mitigate | Opening a replacement ends the connection it replaces, and the opener refuses to run once closing, so no transport can appear after `close()`. Both asserted with injected transports. |
| T-01-77 | Spoofing | connected reported with nothing subscribed | critical | mitigate | The connected flag and the notification both move behind the resolved subscription, so the combined path cannot be reported while no shadow message can arrive. |
| T-01-78 | Denial of service | subscribe or publish callback that never fires | high | mitigate | Both operations race a deadline and reject on expiry, which routes into the existing refused-subscription path; the losing timer is cancelled so no handle is held open. |
| T-01-79 | Tampering | wildcard-bearing device identifier | medium | mitigate | An identifier that would form a wildcard topic is excluded from the routing table and the subscription list and reported once without being quoted, so no message can arrive on an unresolvable topic and no account identifier reaches the log. |
| T-01-80 | Information disclosure | connection diagnostics naming a signed URL or an identifier | high | mitigate | The module logs no URL, no topic, and no device identifier; the new warn keeps that rule, and the redacting logger remains the second line of defence. |
| T-01-81 | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs no package. The deadline is built from the Node standard library; if a task appears to need a dependency, stop and re-plan rather than installing. |
</threat_model>
