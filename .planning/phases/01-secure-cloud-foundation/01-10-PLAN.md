<objective>
Assemble the account runtime: two timers, one credential cache, one shadow connection, one degraded path, and one abortable stop that can be called any number of times at any point.

Purpose: `SYNC-04` needs credentials refreshed before expiry with the next refresh always scheduled, even after a failure — the surveyed failure mode is a plugin that logs and returns on a failed refresh, leaving its push channel dead until a restart. `SYNC-03` needs REST polling as a reconciliation backstop under a shadow that synchronizes current state rather than replaying events. `SYNC-05` needs one abortable lifecycle covering timers, subscriptions, waits, and the socket. `D-15` keeps the plugin useful when the shadow will not connect, and `D-14` keeps a thirty-second retry loop from producing 120 warnings an hour.

Output: a runtime that starts on the Homebridge launch event, keeps itself fed, degrades honestly, and releases everything on shutdown.
</objective>

Operational facts this plan implements, from the ingested runtime record:

- Temporary credentials last approximately one hour; refresh ten minutes before the expiry value and
  schedule the next refresh from the **new** expiry. Do not reconnect only because the credentials
  changed. Retry the refresh if the credential request fails.
- The device heartbeat is approximately 898 seconds, so roughly fifteen minutes of shadow silence is
  normal and one missed heartbeat is never evidence that a device is offline.
- The REST snapshot is the liveness backstop; a failed REST request is not evidence that the device
  reported itself offline.
- Teardown order: abort the root controller first, then clear timers, then close the shadow socket.

Hold the credential cache as a small object exposing the current value, and hand it to the shadow client as its credential cache. The rotation timer replaces that value and nothing else — refreshing the cache is the whole of rotating in place, because the next handshake reads it and nothing re-signs a live socket.

Write `scheduleRotation` as a named unit that clears any existing timer first, computes the delay as the returned expiry minus the clock's value minus the lead, floors it at the minimum, and arms the timer. The timer's body refreshes the cache inside a `try`, reports the failure through the failure discipline inside a `catch`, and calls `scheduleRotation` again inside a `finally`. The `finally` is the requirement that failed refreshes remain scheduled, and it is the single most commonly missed line in this pattern.

Write `schedulePoll` the same way for the REST backstop at the configured interval, converting the configured seconds to milliseconds at this one site. Each poll applies every returned device through the store's discovery path. The shadow synchronizes current state rather than replaying events, so the poll is what reconciles anything missed while the socket was down; the protocol's retained subscriptions are not event replay and must not be treated as such.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Homebridge lifecycle → plugin runtime | Startup and shutdown events arrive at times the plugin does not choose, including during in-flight work. |
| vendor availability → plugin state | An outage must degrade latency, not correctness, and must not fabricate a device condition. |
| plugin → Homebridge log | A retry loop is the most likely source of log flooding and of leaked credential material. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-52 | Denial of service | unhandled rejection during shutdown | high | mitigate | One root controller owns every wait, request, and socket; `stop()` aborts first, then clears timers, then closes the connection, and swallows the abort rejections that cancellation produces. Cases cover shutdown during a retry wait, during a request, and with an open connection. |
| T-01-53 | Denial of service | dead push channel after a failed refresh | high | mitigate | The rotation timer reschedules in a `finally`, so a failed refresh cannot leave the channel dead until a restart. A case asserts the reschedule specifically. |
| T-01-54 | Denial of service | self-inflicted account block | high | mitigate | The runtime schedules nothing after an explicit credential rejection, so a wrong password cannot be retried into a thirty-day block. |
| T-01-55 | Repudiation | log flooding hiding a real fault | medium | mitigate | Every transient failure routes through the rate-limited discipline: one warning, then debug, then a reminder every fifteen minutes, and one informational recovery line. A case proves four warnings rather than a hundred and twenty over an hour. |
| T-01-56 | Tampering | fabricated device condition on a monitoring failure | high | mitigate | A failed poll changes no snapshot and marks nothing disconnected; the degraded monitoring path is a separate, separately logged condition exposed through `monitoringPath`. |
| T-01-57 | Information disclosure | credential material in runtime logs | high | mitigate | The runtime logs through the redacting wrapper, and the failure discipline records a short reason classification rather than an error object or a response body. |
| T-01-58 | Repudiation | silent accessory deletion | high | mitigate | No accessory registration or removal call exists in this phase, and a case drives every lifecycle sequence asserting zero such calls on the injected API. |
