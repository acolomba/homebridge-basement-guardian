<objective>
Give the administrator one settings form that cannot be saved incomplete, make the runtime refuse rather than guess when configuration is wrong, and route every log line through a wrapper that cannot leak a secret.

Purpose: `CONF-02` needs the generated Settings GUI with a masked password and an explicit plaintext-storage disclosure, which is also a Homebridge Verified requirement. `CONF-03` and `D-16` need the plugin to start nothing when configuration is absent or invalid — `strictValidation` guards only the UI, so a hand-edited `config.json` reaches the runtime. `D-18` makes secret redaction structural rather than a convention, because a convention cannot be tested and a wrapper can.

Output: a shipped settings schema, a validator that refuses instead of clamping, and a redacting logger installed before anything can log.
</objective>

`Logging` is a **callable interface with seven members**, identical in `homebridge@1.8.0` and
`homebridge@2.4.0`, so the wrapper must be a function with properties attached, never a class:

```typescript
export interface Logging {
  prefix: string;
  (message: string, ...parameters: any[]): void;
  info: (message: string, ...parameters: any[]) => void;
  success: (message: string, ...parameters: any[]) => void;
  warn: (message: string, ...parameters: any[]) => void;
  error: (message: string, ...parameters: any[]) => void;
  debug: (message: string, ...parameters: any[]) => void;
  log: (level: LogLevel, message: string, ...parameters: any[]) => void;
}
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| administrator `config.json` → plugin | `strictValidation` guards the UI form only; a hand-edited file reaches the runtime unchecked. |
| plugin → Homebridge log | Log output is copied into support requests and public issue reports. |
| Homebridge UI → `config.json` | The form decides what the administrator is told about how the password is stored. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-15 | Information disclosure | account password in `config.json` | high | transfer | Unattended authentication requires the password, and Homebridge owns `config.json` and its backups. The risk transfers to the administrator through explicit disclosure: a root `headerDisplay` in the settings form states the plain-text storage, and the user-facing documentation repeats it in a later phase. This is the locked project position on unattended credentials, not a defect. |
| T-01-16 | Information disclosure | refusal message quoting a configuration value | high | mitigate | The redacting wrapper is installed as the first statement of the platform constructor, before any call that can log, and the password is registered as a secret the moment validation accepts. |
| T-01-17 | Information disclosure | all seven `Logging` members | high | mitigate | The wrapper is a function with all seven members attached and every path substitutes; the test suite asserts each member individually, including the bare callable form and `log(level, ...)`, so a partial wrapper fails. |
| T-01-18 | Tampering | hand-edited `config.json` | medium | mitigate | `validateConfig` range-checks every field and refuses on the first failure. Refusing rather than clamping prevents a mistyped poll interval from silently becoming a different monitoring cadence than the administrator believes is configured. |
| T-01-19 | Denial of service | refusal path | medium | mitigate | The refusal path returns; it never throws. No listener is registered, so no timer, socket, or accessory work starts, satisfying the Verified rules on unhandled exceptions and on not starting when unconfigured. |
| T-01-20 | Information disclosure | vendor protocol constants as configuration | low | mitigate | The schema declares exactly six properties and the test asserts the key set, so an additional vendor constant cannot be exposed as a configuration field without failing a test. |

## Flagged Planner Assumptions

The deterministic edge probe returned one `unclassified` row for `CONF-02` that the auto-resolution
rules leave `unresolved`. It is surfaced here rather than dropped:

- **CONF-02, category `unclassified`.** The probe could not classify the requirement. The planner's
  reading is that the uncharted edge is the boundary between what the form validates and what the
  runtime validates: the UI refuses to save an invalid block, but a hand-edited or restored-from-backup
  `config.json` bypasses the form entirely. This plan closes that specific gap by duplicating every
  schema bound in `validateConfig`, but the schema and the validator are two hand-maintained copies of
  one contract and nothing mechanically proves they agree. Recorded as an assumption: a future change
  to one must be mirrored in the other, and a generated-from-one-source approach was not adopted in
  this phase.
