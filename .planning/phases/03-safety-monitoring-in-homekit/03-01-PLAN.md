<objective>
Build the one hand-built HAP stand-in this phase measures against: `Service` and `Characteristic` as
constructible base classes, the standard definitions the phase publishes, the real three-argument
`addService`, and the characteristic surface a scenario reads back. Then add the zero-advance clock
step the immediacy scenarios bind to.

Purpose: this phase's production modules declare custom HomeKit types by subclassing the injected
`api.hap` namespace, so every test seam needs a `hap` whose `Service` and `Characteristic` are real
classes. The current stand-in has neither: `features/support/fakeHomebridgeApi.ts` exposes `hap` as a
plain object of identifier constants, and its `addService(identifier, subtype?)` at line 41 takes the
subtype second while production calls the real `addService(Class, displayName, subtype)` — called with
the production form it would record a display name as a subtype and every scenario built on it would
pass while proving nothing. The stand-in also has no `updateCharacteristic`, `removeService`,
`testCharacteristic`, `addOptionalCharacteristic`, or `optionalCharacteristics`. Splitting the HAP half
into its own module is what lets the accessories unit tests import the same stand-in instead of
growing a second one — two stand-ins of one boundary would also be a clone family against a
`fallow dupes` baseline that is currently zero.
Output: `features/support/fakeHap.ts`, a Homebridge stand-in that consumes it, and a `When` step that
advances the scenario clock by zero.
</objective>

Real HAP behaviour the stand-in must reproduce, all verified in 03-RESEARCH.md against
`@homebridge/hap-nodejs@2.2.2`:
- `addService(Class, displayName, subtype)` throws `Cannot add a Service with the same UUID '<uuid>'
  and subtype '<subtype>' as another Service in this Accessory.` on a duplicate pair.
- `addService(Class)` throws `Cannot add a Service with the same UUID '<uuid>' as another Service in
  this Accessory without also defining a unique 'subtype' property.` when that UUID already exists
  and no subtype is given.
- `getServiceById(uuid, subType)` matches `typeof uuid === 'function' && ((service instanceof uuid)
  || (uuid.UUID === service.UUID)) && service.subtype === subType`.
- `updateCharacteristic(Class, value)` adds the characteristic when it is not yet present.
- `addOptionalCharacteristic` is NOT idempotent — two calls push two entries.
- `testCharacteristic(Class)` matches by `instanceof` OR by static `UUID`.
- Format defaults: `bool` -> `false`; a numeric format -> its declared `minValue`. So a freshly added
  `LeakDetected` reads `0`, a freshly added `ContactSensorState` reads `0`, a freshly added
  `StatusLowBattery` reads `0`, and a freshly added `StatusActive` reads `false`.
- `Formats.BOOL === 'bool'`, `Formats.UINT8 === 'uint8'`, `Formats.STRING === 'string'`,
  `Formats.FLOAT === 'float'`; `Perms.PAIRED_READ === 'pr'`, `Perms.NOTIFY === 'ev'`;
  `Units.PERCENTAGE === 'percentage'`.
- Standard characteristic UUIDs this phase uses: `LeakDetected` `00000070-`,
  `ContactSensorState` `0000006A-`, `WaterLevel` `000000B5-`, `StatusActive` `00000075-`,
  `StatusFault` `00000077-`, `StatusLowBattery` `00000079-`, `BatteryLevel` `00000068-`,
  `ChargingState` `0000008F-`, `Name` `00000023-`, each completed by the Apple base suffix
  `0000-1000-8000-0026BB765291`.
