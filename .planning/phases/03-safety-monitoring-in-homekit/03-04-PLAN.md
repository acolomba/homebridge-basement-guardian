<objective>
Wire one validated vendor field through every layer this phase touches, end to end, and publish the
confirmed-offline adapter that proves the accessory's own per-poll state reaches HomeKit: a vendor
`ac_power` becomes a read-only fact on a custom `Sump Mains Power` service and an activation of the
standard `Mains Power Lost` Contact Sensor, and a run of disconnected snapshots becomes an activation
of `Basement Guardian Offline`.

Purpose: this is the phase's tracer. Every remaining plan expands out from the contracts fixed here —
the catalogue row shape, the projection input, the get-or-add and remove helpers, the trust-scope
mapping, and the `StatusActive` discipline. Proving the architecture end to end on one field first
means an architectural dead end costs one commit rather than eleven. It is production-quality, not a
prototype: the two power rows and the offline row are the real, final implementation of `SAFE-05` and
the Phase-3 half of `RES-03`.
Output: the custom HomeKit type definitions, the service catalogue, an accessory that publishes from
it, and a Cucumber scenario that drives the real plugin against the fake vendor cloud and reads the
published characteristics back.
</objective>

Verified HAP behaviours this plan depends on (03-RESEARCH.md, probed against the pinned typings):
- `accessory.getServiceById(ServiceClass, subtype) ?? accessory.addService(ServiceClass, displayName, subtype)`
  is the correct get-or-add. The string overload of `getServiceById` matches only `displayName`/`name`
  and returns `undefined` for a UUID string, which turns a get-or-add into an `addService` throw.
- `getService(Type)` returns the FIRST service of that UUID regardless of subtype, so it is wrong for
  any service that has siblings.
- `updateCharacteristic(Class, value)` adds an optional characteristic that is not yet present, so
  pushing `StatusActive` onto a standard sensor service needs no prior `addCharacteristic`.
- `service.testCharacteristic(Class)` matches by `instanceof` OR by static `UUID`, which is what a
  restored plain `Service` needs; `addOptionalCharacteristic` is NOT idempotent, so a
  `!testCharacteristic(C) && !optionalCharacteristics.some((c) => c.UUID === C.UUID)` guard is
  required, not cosmetic.
- HAP clamps an out-of-range value instead of refusing it: `ContactSensorState` `7` publishes as `1`,
  the alarm state under this project's convention. `NaN` is the one value HAP refuses outright.
- Format defaults are the good-news values: `LeakDetected` `0`, `ContactSensorState` `0`,
  `StatusLowBattery` `0`. `StatusActive` defaults to `false`, which is the correct starting point.
- `Service.BatteryService` is absent from the Homebridge 2.x HAP line; `Service.Battery` exists on
  both supported lines.
- Do not build a custom UUID inside Apple's assigned base namespace, whose suffix is
  `0000-1000-8000-0026BB765291`.

  <decision>Freeze the published HomeKit identity contract: the service subtype strings and the custom service and characteristic UUIDs</decision>
  <context>
    HomeKit identifies a service by its type together with its subtype, and a custom service or
    characteristic by its UUID. Both become part of `cachedAccessories` on the first run and both are
    what a user's automations, scenes, notifications, and Apple Activity History attach to. Changing
    either afterwards orphans the service and everything attached to it, with no migration path —
    `src/accessories/services.ts` already records that these strings are a user-facing contract from
    the first release.

    What is already fixed, and what is not. The service *kind* slugs exist today: they have been in
    the `CoreServiceKind` and `NotificationServiceKind` unions since the first milestone, and
    `'primary-pump-running'` was added to `CoreServiceKind` earlier in this phase. Under `D-12` the
    subtype is that slug verbatim, so one end of the mapping is settled. Nothing is orphanable yet,
    though: no `subtype:` literal has been written, no custom UUID exists, no service has been
    published, and no `cachedAccessories` entry names any of it. All three options below are still
    fully reachable. What this gate governs is the two things the next task makes permanent — how a
    kind slug is *rendered* into a subtype, and the custom service and characteristic UUIDs.

    `03-CONTEXT.md` `D-12` already records the developer's decision — the subtype is the `ServiceKind`
    slug verbatim, no prefix and no version segment — and rates it one-way. This checkpoint confirms
    that door rather than reopening it, and adds the UUID half, which `D-12` left to discretion.

    One discrepancy is worth seeing before confirming: `docs/research/PLUGIN.md` section 8 proposes
    namespaced subtypes such as `fault.water-sensor`. `D-12` supersedes it, and that document predates
    the decision. It is a local research note and is not tracked in git, so no code or repository file
    disagrees with `D-12`; this is recorded here so a reviewer who reads that note does not file the
    difference as a defect.
  </context>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Decoded domain state -> a published HAP characteristic | The last point at which a wrong value can still be refused. HAP itself clamps rather than refuses, so nothing downstream can catch a bad push. |
| The accessory's per-poll state -> the confirmed-offline adapter | A physical-device alert derived from plugin-side counting rather than from a reported field. Miscounting produces an alert the vendor never raised. |
| Administrator `ignoredFaults` -> the published service set | Removing a service orphans whatever a user attached to it in their controller. |
