# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each was discovered through actual failure, not predicted.
> Acknowledge each one explicitly before proceeding.

- [ ] CONSTRAINT: **A green suite is not evidence** — four blocker-severity defects, all false-normal
      publication paths, shipped inside a suite of 958 passing tests at 100% line/branch/function
      coverage. Two were found only by *executing* the shipped code. Mitigation: for any
      safety-bearing claim, reintroduce the defect and watch the specific test fail. Coverage
      measures whether existing branches ran, never whether the right branches exist.
- [ ] CONSTRAINT: **Subagent completion reports need verifying against artifacts** — one agent
      reported a file "committed as `0275dfd`" under a commit that was empty; another reported a
      blocking gate as unparseable when it had called the gate with the wrong argument order, then
      substituted a hand-check that measured something different and reported its green as settling
      the question. Mitigation: verify with `git cat-file -e HEAD:<path>`, and re-run a gate
      yourself rather than accepting a report about it.
- [ ] CONSTRAINT: **A claim inherited from a prior summary is not a verified claim** — plans 03-04
      and 03-05 both recorded that pre-commit gating made `test(...)` → `feat(...)` pairs
      impossible. Neither read `.pre-commit-config.yaml`, which runs four hooks and **no test
      runner**. Mitigation: read the primary source before repeating a constraint.
- [ ] CONSTRAINT: **An action is not done until its EFFECT is observed** — new 2026-08-30. The UAT
      override was "cleared": the control file was empty and the plugin logged
      `override cleared`, so it was reported as reset. HomeKit was still showing a **false flood on
      a safety accessory**, and stayed that way until the user noticed. Both signals were real and
      both were about the input, neither about the result. Mitigation: assert on the observable
      output — here, the HAP characteristic — never on the fact that an input was applied.

**Do not proceed until all boxes are checked.**

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Trivially-passing assertion | Six assertions in this phase passed against absent or unpublished state. **It recurred on 2026-08-30 in a new form:** a wait loop `until docker logs \| grep -q "forcing water_level=9"` matched a **historical** line from an earlier test and returned instantly, so the observation ran against pre-change state and reported "no change yet". | blocking | Every new assertion must be falsified. For any wait or poll on an append-only source, capture a baseline COUNT first and wait for it to increase; never `grep -q` a pattern that could already be present. |
| Reporting an input as an outcome | See blocking constraint 4. The distance between "the override was cleared" and "the accessory recovered" was a false flood indication left standing on a safety device. | blocking | State changes are confirmed by reading the resulting published value back, not by confirming the write. |
| Test scaffold writing into canonical state | The UAT override was placed in `freeze()` — which is the state store's **persistence** chokepoint, not a view. Forced values were written into stored `data`. Once the shadow owned telemetry, `pollTelemetry` returned `previous.data`, so removing the override left the forced value **stuck** and the scope permanently degraded. | blocking | A scaffold must intercept where state is *read*, never where it is *persisted*. If that is impossible, it must reset by forcing a known-good value, never by ceasing to intervene (`./level reset`, never `off`). |
| Test that encodes the bug | Five existing tests asserted buggy behaviour as correct and were rewritten in fix iteration 1; iteration 2 found one rewrite had encoded a *new* contradiction. | blocking | A rewritten assertion must be strictly stronger, not merely different. Report a test that encodes a defect as a finding of its own. |
| Fix introducing a blocker | Iteration 1's WR-02 fix swallowed a throw between caching the accessory wrapper and registering the platform accessory, blanking the device permanently. | blocking | Re-review after every fix pass, scoped to exactly the files the fixes touched. |
| Substituting a different instrument | Reading `StatusActive` in the Homebridge UI and calling checks 1 and 2 closed. Those questions are about Apple Home's automation engine and Apple's rendering; another controller cannot answer either. | blocking | Name the instrument the question requires. If it is unavailable, the check stays open — it does not get a proxy. |
| `HapStatusError` as a degradation signal | Produces Apple Home "No Response", which erases the retained last-valid values `D-014` requires. Looks like a fix. | advisory | `D-05`: a degraded scope sets `StatusActive = false`, retains values, logs once. Never throw from a getter. |
| Commit title over 72 characters | gitlint rejects it, the commit silently does not happen, and the agent proceeds believing it did. | advisory | Keep titles ≤72 chars; verify each commit landed with `git show --name-only`. |
