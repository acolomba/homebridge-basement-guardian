<objective>
Separate "the plugin cannot vouch for this scope" from "the plugin must not publish this scope", so
a monitoring outage marks what it can no longer watch instead of discarding what is still arriving.
Then make the two causes compose in the order that keeps a blind plugin from reading trustworthy.

Purpose: `05-VERIFICATION.md` CR-01 reproduced, twice and independently, that with the shadow silent
and REST healthy a poll reporting `water_level: 31` produces `leakDetected = 0`. The reading is
decoded, validated by the family, and thrown away. Apple Home draws no `Status Active` row on a
tile, so the owner sees "no leak" while the plugin holds "leak", and no automation fires. That is
the exact false normal this project exists to prevent, and it fails ROADMAP success criterion 2 on
its own. WR-01 fails the same criterion by the other door: with the controller link lost and both
transports down, `Pump Controller Link Lost` still publishes an activated sensor with
`Status Active = true`, so a device adapter reads trustworthy while the plugin is blind.

Output: a publishing predicate distinct from the vouching predicate, a reason precedence that puts
the broader cause first, a Cucumber read step that cannot pass on an absent characteristic, and
assertions written as what a basement owner must observe.
</objective>

## The `D-014` reading this plan acts on

`PROJECT.md` `D-014` is ADR-locked and reads, in full:

> **D-014 — Preserve untrusted state:** Retain the last family-valid values through invalid data or
> communication loss, mark only the truthful scope faulty/inactive, and require fresh valid input
> for recovery.

**This plan does not amend, narrow, or reinterpret `D-014`, and inserts no decision checkpoint.**
The argument is from `D-014`'s own three clauses:

1. **"Retain the last family-valid values."** Withholding is the *mechanism* by which retention is
   achieved when the arriving value is bad: publishing a field that failed family validation would
   overwrite a retained good value with a bad one, so the row must publish nothing. That mechanism
   serves the clause. It does not serve it when the arriving value is family-valid and was delivered
   by a transport that is working — withholding then retains nothing, because nothing was
   threatening the retained value. It replaces a fresh valid reading with a staler valid one.
2. **"Mark only the truthful scope faulty/inactive."** The instruction for a scope the plugin cannot
   vouch for is to *mark* it. `D-014` names marking, and names it as the whole of the response
   beside retention. It nowhere says discard.
3. **"Require fresh valid input for recovery."** Under the shipped behaviour fresh valid input
   arrives, is validated, and is ignored. The clause is not merely unserved; it is inverted.

So the reading is that `D-014` always meant *preserve the value, mark the scope*, and the
implementation over-applied its withholding mechanism to a cause `D-014` never covered.
`05-CONTEXT.md` `D-02` says a monitoring degradation "marks every scope"; `05-01-PLAN.md`'s own
prohibition said in as many words that "preserve-and-mark must not become preserve-and-hide". Both
are served by this change rather than bent by it.

One structural guarantee makes the narrower predicate safe rather than merely defensible: **a row
can only publish a value some transport delivered.** The projection reads the last decoded snapshot,
and a snapshot exists only because a poll or a shadow message carried it. With both transports down
nothing new arrives, so "publish what arrived" cannot publish anything from a dead transport — every
tile holds exactly the value the last trustworthy observation left, marked. The change moves which
values reach HomeKit only in the case where a transport is still delivering them.

The change is `reversible`: it is one predicate, added beside the existing one, and reverting it
restores today's behaviour by pointing two call sites back at the old name.

## The rule every new assertion in this round obeys

`05-VALIDATION.md` recorded that every behaviour in the first round had its named mutation applied,
watched to fail, and reverted — and CR-01 shipped anyway. The mutations tested whether the tests
could detect the *implemented* behaviour changing, not whether the implemented behaviour was
*correct*. `retains every published value across a lost monitoring path and moves the trust flag
alone` is a well-written test of the wrong question: what it asserts is the defect's own signature.

So every assertion added in this round states **what a basement owner must observe**, and every
paired mutation is one a *correct* implementation survives and the current one fails. An assertion
that only says "nothing moved" is not acceptable evidence in this plan.
