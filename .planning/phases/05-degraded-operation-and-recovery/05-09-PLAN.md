<objective>
Make a press on a restored control Switch, in the window after a restart the vendor cloud never
answers, be refused with a named cause instead of silently accepted.

Purpose: `05-VERIFICATION.md` probe R2 recorded `press outcome = ACCEPTED (no error)`,
`commands sent = 0`, `switch value after press = true`, and confirmed against the pinned real HAP

`RES-04` names, an owner presses `System Self-Test`, Apple Home shows it worked, an automation
watching that switch fires, and nothing happened. Every other refusal this phase built names its
cause; this one is silent, and it is silent in the direction that reports success.

## The scoping dispute, and how it is resolved

`05-VALIDATION.md` and `05-04-PLAN.md`'s assumption PA-08 deliberately scoped this out of `RES-04`
as a pre-existing gap "outside `RES-04`'s 'commands stay disabled until valid state and command
transport return' — which governs commands the plugin can route". The verifier disagreed.
**This plan closes it, and the argument is stated here rather than settled by citing the earlier
deferral.**

`RES-04` reads: *"After a failed restart, getters return cached values without network calls,
accessories remain present and visibly stale, commands stay disabled until fresh valid state
returns, and only explicit credential rejection yields a persistent communication failure requiring
user action."* Success criterion 3 says the same window "prevents commands until valid state and
command transport return".

Three things decide it:

1. **The clause names this window.** Its opening is "After a failed restart", and the failed restart
   is precisely when no accessory has been built. A reading under which the clause governs only
   commands the plugin can already route makes the requirement's scope depend on how much of it is
   implemented: the less that exists, the less is demanded. That inverts what a requirement is for.
2. **"Disabled" is a claim about what the owner can do, not about what the code contains.** Nothing
   is sent today, which satisfies the requirement's *effect* on the vendor. It does not satisfy the
   requirement's effect on the owner: the toggle flips in Apple Home, the write is answered success,
   and an automation built on that switch fires. A control that reports success for an act that did
   not happen is a false normal on the control surface — the same class of defect as a tile reading
   "no leak" while the plugin holds "leak", which is the one thing this project exists to prevent.
3. **The deferral's premise is a description of the defect, not a boundary of the requirement.**
   PA-08 established, correctly, that a halted or unreached run builds no accessory and therefore
   binds no handler. That is why the press is not refused. It is not a reason the press need not be
   refused.

None of the three legitimate reasons to defer applies. The context cost is small: `05-02` already
established the exported restart-pass shape that the platform and the Cucumber harness both call,
`05-03` already built the refusal cause and the status this reuses, and the handler is replaced by
the real binder on the first publish. No information is missing. Nothing here waits on a later
phase.

**What closing it changes:** `configureAccessory` gains a second pass beside the marking one, which
binds a refusing write handler to every restored service carrying the control write surface. A press
in that window is answered with the same status and the same cause the transport rule already gives
a live accessory, the log line names it, and the clearing push returns the characteristic to
readable so the accessory does not present as No Response for a condition that clears itself. When
the first inventory finally succeeds, the binder's own handler replaces the refusing one, because a
set handler is a single slot in both the real and the stand-in HAP.

| Boundary | Description |
|----------|-------------|
| HomeKit controller write -> restored service | The only place a controller can act on this plugin, and after a restart it is unattended. |
| Restored accessory -> vendor command route | Nothing may travel it until the plugin has proven a route. |
| Refusal status -> Apple Home presentation | A stored status greys the whole accessory, which this project reserves for one cause. |
