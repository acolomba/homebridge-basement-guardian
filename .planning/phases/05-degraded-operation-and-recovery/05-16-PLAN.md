<objective>
Make the credential-refusal presentation a state the accessory holds, by closing the one seam through
which a control write can still republish over it, and by making the value underneath the refusal the
truthful one.

Purpose: `05-REVIEW-2.md` CR-02. Plan 05-12 closed the message route so no arriving heartbeat could
clear the `HapStatusError` that presents a refused credential as No Response. The write route is
still open. After the halt a press is correctly refused locally -- and the refusal arms a clearing
push, which republishes the control rows, and a row's republish ends in an ordinary value push, and an
ordinary value push clears a stored status. That is pinned against real HAP by this phase's own
write-fidelity test. Worse, a refused credential withdraws no trust scope, so the value pushed is
`true`: the accessory actively claims it vouches for what it shows, on a runtime that will never
observe anything again. Permanent, because a halted runtime never pushes again. Reproduced against the
built modules: after one press, both control services answered reads normally while the flood sensor
still refused, so the accessory presents as half working and is entirely dead. The request-expiry and
vendor-refusal paths leak identically, through the same seam.

Output: a closed seam, a truthful value under the refusal, a comparison member that is now provable, a
scenario, unit cases, and the validation rows.
</objective>

## The fix chosen, and the one rejected

`05-REVIEW-2.md` names two. This plan takes the second, in the shape the restored-control path already
demonstrates, and adds the withdrawal the reviewer files separately as WR-03.

**Chosen -- the accessory refuses to republish while the credentials stand refused, and the value
underneath is truthful.**

Two edits, in one module:

1. The `republish` closure the binder holds answers nothing while `monitoring.credentialsRejected` is
   set. This is `nothingToRepublish`'s shape, arrived at from the live side: there is nothing to
   re-assert, because the runtime has stopped for good and no fact the rows publish from will ever
   change again.
2. `monitoringDegradedScopes` reads `credentialsRejected` first and answers `EVERY_SCOPE`. A refused
   credential ends every observation this runtime will ever make, so nothing it holds is current
   whatever the transports last reported.

Four reasons this is the right layer:

- **One seam covers all three leaks.** `refuseLocally`, `expire` and `refuseOutcome` all reach the one
  `republish` callback the binder holds. Two of them arrive through `clearRefusal`; `expire` calls
  `republish()` directly at 443 and never touches `clearRefusal`. Closing the **callback** closes
  three paths without three guards, and any fourth path a later plan adds through the binder is closed
  by construction. Closing `clearRefusal` instead would close only two, and would look like it had
  closed three.
- **It keeps the forbidden act at one call site.** Teaching `publishRow` to push a persistent failure
  would put the act `03-CONTEXT.md` D-05 forbids in a second production location, and
  `publishPersistentFailure`'s docblock says in as many words that the single call site is what keeps
  the locked decision reviewable. The accessory tier's own file docblock would also have to be
  retracted. Neither is worth paying for a guard that covers less.
- **The `On` push still runs, and should.** `clearRefusal` pushes `On` after the republish, and `On`
  carries no trust report -- the status made unreadable sits on `Status Active`. So the press's own
  `-70412` clears, which is what a refusal's clearing push is for, while the D-10 presentation stands.
  That is precisely why `bindRestoredControlRefusal` does not leak.
- **The withdrawal makes the two facts agree.** With `EVERY_SCOPE` withdrawn, the value a republish
  would have pushed is `false` rather than `true`. The status is then the louder statement of a fact
  the boolean already carries, instead of the only thing saying anything is wrong. That also makes the
  credential member of `markMonitoring`'s comparison genuinely load-bearing, which is WR-04.

**Rejected -- teach `publishRow` to push the persistent failure while the credentials stand
refused.** It generalises further and costs more than it is worth here. It adds the second call site
above; it makes the accessory tier's file docblock false and requires retracting a claim two phases
rest on; and the branch is reachable from only two callers, one of which (`republishPublishedRows` at
the halt) is exactly where the truthful `false` should be pushed instead, so the generalisation would
suppress the very push that makes the underlying value honest.

## What WR-03 does not silence, and how that is proven

Widening the withdrawal to every scope looks like it should deactivate `Basement Guardian Offline` --
that is the trap `05-CONTEXT.md` D-02's narrowing was written to avoid, and the narrowing is
load-bearing. It does not, and the reason is plan 05-06's widening of `isRowPublishable`: the reason
filled in for a monitoring withdrawal is `unreachable`, `unreachable` is a seeing-less reason, and a
row untrusted for a seeing-less reason still publishes what a working transport delivered. So the
adapter keeps its verdict and stops vouching for it, which is the honest reading for a plugin that
will never poll again.

That must be asserted, not assumed. Task 2 carries a case that reads the connectivity row's published
value under a refused credential and fails if the row withholds it.
