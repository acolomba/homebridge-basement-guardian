## The one thing that will waste your time if you do not read it

**Executor dispatch is blocked by an isolation guard unless you degrade it first, and the obvious
fix is dangerous.**

`gsd_run query dispatch-isolation --raw` reports `harness-worktree` — that is the host *capability*,
not a verdict about this dispatch. `gsd_run query worktree base-check` returns
`shouldDegrade: true`, because the harness does not honour `worktree.baseRef:"head"` and would fork
agent worktrees from `origin/HEAD`.

`origin/HEAD` is `95f999b2` (= `origin/main`), and **Phase 3's `src/accessories/serviceCatalogue.ts`
does not exist there.** An executor in a harness worktree would open a tree with no Phase 3 and no
Phase 4 and try to build Phase 5 on top of nothing. Adding `isolation="worktree"` to satisfy the
guard is exactly the wrong move.

**Do this instead, immediately before every executor dispatch:**

```bash
node .claude/gsd-core/bin/gsd-tools.cjs query dispatch-isolation --raw --phase 05 --force-isolation none >/dev/null 2>&1
cat .gsd/dispatch-isolation-sentinel.json   # verify: {"isolation":"none","harness_flag":null,...}
```

Two traps: the sentinel goes **stale** (executors run 40-90 minutes, so re-force before each
dispatch), and a bare `dispatch-isolation --raw` **re-persists the capability** and silently undoes
the force — verify by reading the file, never by re-querying.

Executors therefore run **sequentially on the main working tree**. That is correct and deliberate.
Tell each executor so in its prompt, and tell it not to run any worktree-branch-check guard.

## D-12 is the one a planner will under-weight

`features/support/fakeHomebridgeApi.ts:106-110` deliberately drops the service surface on restart.
That was **correct for Phase 4's question and is wrong for Phase 5's**: with no restored services
there is nothing stale to read, so every `D-06` scenario would pass whether or not the plugin marks
anything.

That is the **seventh** instance on this project of a test passing for the wrong reason, and all
seven have the identical shape: *the fixture sits at the value the defect produces*. Six were found
during Phase 4 execution, every one by running a mutation, none by reading code.

The harness must carry services and values across a restart, and **all 78 existing scenarios must be
re-run immediately after that change**. Separately, `world.ts:571-585` *stands in for*
`configureAccessory` rather than calling it, so the marking pass must be an exported function both
callers share or Cucumber tests the harness's copy.

## Blocking constraints, all still holding

- **A green suite is not evidence.** Phase 3 shipped four blocker-severity false-normal defects
  inside 958 passing tests at 100% coverage. For any safety-bearing claim, reintroduce the defect
  and watch the specific test fail.
- **Subagent completion reports need verifying against artifacts.** A Phase 4 planner reported a
  commit hash that was not a valid git object; the work was fine, the report was not. Verify with
  `git show --name-only --format="" <sha>` and `git cat-file -e HEAD:<path>`.
- **A claim inherited from a prior summary is not verified.** Read the primary source.
- **An action is not done until its EFFECT is observed.**
- **`gsd-tools query commit` can report success while committing nothing.** Use `pre-commit run
  --files <changed>` → `git add` → plain `git commit` with **no pathspec** → verify with
  `git show --name-only --format="" HEAD`. Never `--no-verify`, never rebase.
- **`npm run test:coverage:all` is NOT in CI.** `.github/workflows/build.yml` runs lint,
  format:check, typecheck, fallow, `npm test`, build, audit. The 100/100/100 gate is local
  discipline only.
