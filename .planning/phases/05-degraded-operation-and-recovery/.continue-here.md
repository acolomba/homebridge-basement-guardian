## The one thing that will waste your time if you do not read it

**Executor dispatch is blocked by an isolation guard unless you degrade it first, and the obvious
fix is dangerous.**

`gsd_run query dispatch-isolation --raw` reports `harness-worktree` — that is the host *capability*,
not a verdict about this dispatch. `gsd_run query worktree base-check` returns
`shouldDegrade: true`, because the harness does not honour `worktree.baseRef:"head"` and would fork
agent worktrees from `origin/HEAD`.

`origin/HEAD` is `origin/main`, and **neither Phase 3's `src/accessories/serviceCatalogue.ts` nor
any Phase 4 source exists there.** An executor in a harness worktree would open a tree with no
Phase 3 and no Phase 4 and try to build Phase 5 on top of nothing. Adding `isolation="worktree"` to
satisfy the guard is exactly the wrong move.

**Do this instead, immediately before every executor dispatch:**

```bash
node .claude/gsd-core/bin/gsd-tools.cjs query dispatch-isolation --raw --phase 05 --force-isolation none >/dev/null 2>&1
cat .gsd/dispatch-isolation-sentinel.json   # verify: {"isolation":"none","harness_flag":null,...}
```

Two traps: the sentinel goes **stale** (executors run 40-90 minutes, so re-force before each
dispatch), and a bare `dispatch-isolation --raw` **re-persists the capability** and silently undoes
the force — verify by reading the file, never by re-querying.

Executors therefore run **sequentially on the main working tree**. That is correct and deliberate,
and it matches the plans: waves are 01 → 02 → 03 → 04 → 05 because four of the five plans touch
`platform.ts`, `basementGuardian.ts`, `accountRuntime.ts` or `degradedOperation.feature`. Tell each
executor so in its prompt, and tell it not to run any worktree-branch-check guard.

## Two findings from planning that no earlier document carries

**The Cucumber HAP stand-in models the inverse of production.**
`features/support/fakeHap.ts` stores an error as the characteristic's *value* and clears the stored
status. The pinned real `Characteristic.js` `updateValue` short-circuits on `value instanceof
Error`, assigns `statusCode`, and returns **before** touching `this.value`; `handleGetRequest`
throws the stored `statusCode` when no getter is registered. Nothing in the suite has ever pushed an
error, so no assertion ever noticed. Every `D-10` assertion would otherwise have run against a
fixture modelling the opposite of the real thing. **Fixing the stand-in is 05-04's first task**, with
a fidelity case that must be watched to fail against the unfixed version.

**A halted restart leaves a press silently succeeding.** `halted` is set only in `launchFailure`,
reached only from `launch()`. A run that halts never reaches `applyDevices`, so
`registerDiscoveredDevices` never runs and no `BasementGuardianAccessory` — and no `onSet` handler —
exists on any restored accessory. A press is not refused; it is never routed, and the fake's
`handleSetRequest` with no handler stores the value and returns. This is why the credential-rejection
press has **no** e2e row: `Then the vendor receives no command` would pass for a reason unrelated to
the transport predicate. The claim is carried by two falsifiable unit rows instead. The underlying
gap predates this phase and is recorded, not closed.
