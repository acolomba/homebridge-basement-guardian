<objective>
Prove the whole degraded-monitoring path on one case, end to end, against the fake cloud and the fake
broker: the shadow goes silent while REST keeps polling, and `Sump Pit Flood` reports
`Status Active` as `false` while it still carries the `Leak Detected` value it last vouched for —
and `Basement Guardian Offline` stays trusted, because REST is still feeding it. Then complete the
transport matrix and both clearing rules.

Purpose: this is the case the maintainer singled out as mattering most, and it is invisible today.
REST keeps working, every tile looks normal, and the plugin simply stops seeing pump runs that begin
and end between two polls. Nothing in `src/` counts consecutive REST failures, nothing observes
shadow message arrival, and `monitoringPathNow()` collapses two of the three cases this phase must
distinguish. Every layer the phase touches is wired once here on a single path, so an architectural
dead end surfaces after one commit rather than after five plans.
Output: the monitoring-trust projection, the runtime seams that feed it, the third distrust layer in
the accessory, the platform wiring, and the end-to-end transport matrix in Cucumber.
</objective>

## Plan size, and why the tracer is not split

Thirteen files, calibrated projection 115000 against a 100000 smart-zone budget — 1.15x.
`estimate-calibration` reports `sample_count: 0` and `factor: 1.00`, so the token figure is
uncalibrated for this project and the file count is the better signal. The size is accepted on one
argument, checked rather than asserted: the tracer's claim is that a *transport* fact reaches a
*HomeKit characteristic*, and there are exactly four modules between those two points
(`monitoringHealth.ts`, `accountRuntime.ts`, `platform.ts`, `basementGuardian.ts`) plus the harness
that observes it. Removing any one of them leaves the claim unproven end to end, which is the whole
purpose of leading with a tracer. The remaining nine files are the tests and harness steps those four
require.

A split into "the projection" then "the wiring" was considered and declined: it is the horizontal
layer cake the tracer discipline exists to prevent, and it would put the phase's central behaviour
behind two plans of scaffolding with nothing observable in between.

Feedback latency is bought back by sampling rather than by splitting. Each task runs its narrow gate
first — the focused coverage pair, then the `--name`-filtered scenario — and the whole suite after.

The over-budget projection is advisory and is recorded rather than acted on, but it is recorded for
the executor rather than for the file: watch actual context use through this plan instead of assuming
headroom, and if the tracer's `read_first` list alone consumes more than half the window, stop and
report rather than skimming the reads that make the wiring correct.

## Planner assumptions carried by this plan

Surfaced rather than dropped. Each is recorded here because no maintainer ruling exists.

**PA-01 — `05-RESEARCH.md` Open Question 2 has no ruling: is "no shadow message has ever arrived
this run" silence, or startup?** This plan adopts the research recommendation and makes the answer
structural: `createMonitoringHealth` seeds the arrival stamp from the injected clock at construction,
so a broker the plugin can never reach becomes silent two heartbeats after the runtime was built
rather than never. The alternative — an `undefined` stamp meaning "not silence" — leaves a shadow
that never connects permanently trusted, and would also add a branch no production path can reach,
which the 100% branch-coverage gate would then be satisfied by a test asserting the gap exists.
Reversible: one line in the factory.

**PA-02 — `D-02`'s second bullet and `D-04`'s first bullet do not agree, and this plan follows
`D-02`.** `D-02` (narrowed after research) reads: shadow silence withdraws `NON_CONNECTIVITY_SCOPES`;
"REST degradation **additionally** withdraws `connectivity`, because then nothing sources it";
both-down withdraws everything. `D-04` reads: "REST down, shadow alive … **does not** mark HomeKit."
Under `D-02` a REST-only degradation marks exactly one scope, `connectivity`; under `D-04` it marks
none. The two readings differ only for the one scope `D-04`'s prose never discusses — `D-04`'s whole
argument is about live telemetry and pump runs, and `connectivity` is sourced from REST alone. This
plan implements `D-02`, because it is the later text, it was written specifically to fix a
`connectivity` defect research found, and because a frozen `offlineCount` that keeps reading as
trustworthy while REST is down is the false normal this project exists to prevent. Read the two
decisions before changing this.

The reading is put in front of the maintainer **before the tracer runs**, as the checkpoint task
below, rather than at phase close-out. An earlier draft called the reversal "a one-line change in
`monitoringDegradedScopes` plus its three unit cases", which understated it. Six artifacts encode the
`D-02` reading and all six change under `D-04`: `monitoringDegradedScopes`'s `restDegraded`-alone arm
in `src/accessories/basementGuardian.ts`; the three `markMonitoring` scope-mapping cases in
`test/accessories/basementGuardian.test.ts`; must_haves truth 3 of this plan; the Cucumber scenario
`Polling failure alone leaves live values trustworthy` in `features/degradedOperation.feature`, which
asserts `Basement Guardian Offline` reports `Status Active` as `false`; the `05-VALIDATION.md` row
"REST down + shadow alive leaves every service `Status Active = true`", which already reads the
opposite way from this plan; and the README paragraph plan 05-05 writes about the REST-only case.
