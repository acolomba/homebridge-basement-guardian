<objective>
Give the end-to-end suite the ability to describe a two-pump account, and use it: two scenarios that
prove the plugin publishes one accessory per system and observes each system apart from the other.

Purpose: `05-REVIEW-2.md` found four blockers, and three are interactions between plans that each
verified cleanly alone. `CR-01` is invisible to the whole suite for one reason -- **no scenario uses
more than one `deviceId`** -- so an account-wide clock standing in for a per-device fact cannot be
caught by any end-to-end assertion that exists. This plan removes that blindness as a deliverable in
its own right, before the plan that depends on it. An owner with two sump systems is an ordinary
owner, and until now nothing proved the plugin serves them.

Output: a named-accessory read, a named-device publish, a named-device vendor change, two scenarios,
and validation rows. No production module changes. The three named steps are the whole vocabulary plan
05-14's scenario is written in, and 05-14 lands none of them.
</objective>

**Placeholder discipline (`REL-04`, `D-027`).** Every identifier in a feature table in this repository
is a placeholder: `placeholder-account_placeholder-pump`, `placeholder-gemini`,
`placeholder-serial-number`. New rows follow that, with no account identifier and no real serial.

**The legal `water_level` domain, and why a fixture must stay inside it.** `src/device/waterLevel.ts`
defines `PROVISIONAL_WATER_LEVEL_PERCENTAGES` at 26-33 over exactly **`{0, 1, 3, 7, 15, 31}`**, and
`PROVISIONAL_FLOOD_WATER_LEVEL_CODE = 31` at 42 -- the only legal code above 15, per the vendor rule
`WW-GEM-ALERT-7`. `waterLevelPercentage(code)` at 50-58 throws a `TypeError` for anything else, and
`isPitFlooded(code)` at 61-62 is `code >= 31`. `VALID_GEMINI_TELEMETRY` in
`features/support/steps/harness.ts:51` carries `water_level: 1`, so an unmodified seeded pump reads
20%.

A code outside that set makes the family adapter reject the whole snapshot: the water scope goes
untrusted, `Sump Pit Level` withholds, and a new named read step then fails for a reason that has
nothing to do with device routing -- while looking exactly like a routing failure an executor might
"fix" in `src/`. The `waterLevel` column exists precisely so a scenario *can* seed an out-of-domain
code (`harness.ts:145-150` says so in as many words), which is what makes an accidental one easy.
**This phase has already been burned by this**, with a fixture at `water_level: 2` making a sensor
deactivate on field validation rather than on the silence the scenario claimed to prove. Every
`waterLevel` this plan writes is drawn from `{0, 1, 3, 7, 15, 31}` and is stated in the scenario as a
value from that set.

## Why the harness comes first, and alone

`05-REVIEW-2.md` reproduced `CR-01` by executing the built modules directly, outside both test tiers,
because neither tier could express it. The unit tier can be taught a second `deviceId` in an
afternoon; the end-to-end tier cannot, because three separate helpers each collapse the account to one
device and 96 scenarios rest on that collapse.

Landing the harness change and the `CR-01` behaviour change together would make the behaviour change
unprovable in the way this phase has already been caught out by twice: a scenario that goes green when
two things move at once cannot say which one it was measuring. So this plan lands the capability and
proves it on behaviour that is **already correct today** -- two pumps publish two accessories, and a
message for one does not move the other. Both scenarios must pass on unmodified production code. If
either fails, that is a new finding, and it is recorded rather than fixed here.

That also makes the next plan's evidence sharp: `05-14`'s scenario is written against a harness whose
two-device reads are already proven, so a red result there is about `CR-01` and nothing else.

For that guarantee to hold, **every step `05-14`'s scenario needs must land here**, and that includes
the vendor-change step, which the first draft of this plan did not deliver. `05-14` must have the
vendor report a flooding pit for the quiet pump while leaving its neighbour alone; the only
vendor-change step in the suite rewrites every seeded device at once. Had `05-14` added the named form
itself, its commit would have carried a harness change and a three-module source change together --
the exact unreadability wave 8 exists to prevent -- and had it reached for the account-wide step
instead, its assertion that "the healthy pump's own reading is still its own" would have been a
different claim from the one its `05-VALIDATION.md` row states.
