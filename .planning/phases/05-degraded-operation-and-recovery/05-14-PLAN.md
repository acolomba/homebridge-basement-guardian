<objective>
Make shadow silence a fact about one device, measured from that device's own last message, and hand
telemetry back to the poll for the device that went quiet and for no other.

Purpose: `05-REVIEW-2.md` CR-01. `createMonitoringHealth` holds one `lastShadowMessageAt`, and the
arrival callback discards the `deviceId` it is handed. Telemetry ownership, however, is per device.
So on a two-pump account any one pump's heartbeat re-stamps the account clock: a pump whose
controller goes permanently quiet never trips `shadowSilent`, is never released, and has every poll
body discarded. Reproduced over ten simulated hours -- the poll reported a flooded pit on all forty
polls, the store still read the last live value, and `Status Active` stayed true throughout. That is
`05-CONTEXT.md` D-04's headline case, the invisible one, made strictly worse, because the marking
that was supposed to be the consolation prize never fires either. Both `releaseShadowSource`'s
docblock and `pollTelemetry`'s comment already state the rule in per-device language; the account-wide
implementation is the drift.

Output: per-device arrival stamps and a per-device release, the two-pump scenario that proves it, the
unit cases behind it, and the validation rows.
</objective>

## The shape, and the two shapes rejected

**Chosen -- stamps per device, verdict per device, marking per account.**

```ts
export interface MonitoringHealth {
  recordRestSuccess(): void;
  recordRestFailure(): void;
  /** Records one shadow message arriving for one device. */
  recordShadowMessage(deviceId: string): void;
  /** Starts a device's silence window when discovery first admits it. A device already tracked is untouched. */
  admitDevice(deviceId: string): void;
  /** Drops a removed device's stamp, so the map cannot grow for the life of the process. */
  forgetDevice(deviceId: string): void;
  /** Every admitted deviceId whose live path has been silent for two heartbeats. */
  silentDevices(): readonly string[];
  trustNow(): TransportTrust;
}
```

`trustNow().shadowSilent` is `silentDevices().length > 0`. `applyDevices` releases per device;
`handleShadowDisconnected` keeps releasing every device, because a connection that ended took every
device's live path with it.

**Rejected -- pass the known deviceIds into `silentDevices()` and `trustNow()`, as `05-REVIEW-2.md`
sketches.** It works, and it puts the same question in two places. The store's `deviceIds()` includes
devices admitted before the process learned anything about them and excludes nothing, so every caller
would have to remember to pass it, and a caller that passed the wrong list would get a silently
different answer. Owning the admitted set inside the module means one place decides who is being
watched, and `trustNow()` keeps the zero-argument shape thirteen existing unit cases already use.

**Rejected -- derive silence from `snapshot.receivedAt` now that it is per device.** The module's own
comment at 114-122 rules this out and the reason has not changed: a successful REST poll bumps
`receivedAt`, so a poll would clear a shadow-silence degradation, which is the one clearing
`05-CONTEXT.md` D-11 forbids.

## The marking stays account-wide, and why

`shadowSilent` remains one answer pushed identically to every accessory: true when **any** admitted
device is silent. A two-pump owner whose front pump goes quiet therefore sees both tiles stop
vouching, not one.

That is deliberate, and it is argued against the requirements rather than against convenience:

- **No requirement asks for per-device marking.** `RES-03` asks that a monitoring-path loss be
  separated from a confirmed-offline device without a false physical-device alert; account-wide
  marking raises no adapter and activates nothing. Roadmap SC-2 asks that users distinguish
  controller-link loss, confirmed offline, and a degraded monitoring path -- all three stay
  distinguishable. `05-CONTEXT.md` D-02 already ratifies marking every accessory for a monitoring
  failure and names the accepted cost in those words.
- **Over-marking cannot produce a false normal.** It withdraws trust the plugin does have; the defect
  class this project exists to prevent is the other direction. Under-marking is what `CR-01` is.
- **The cost of the alternative is real.** Per-device marking means a per-device `MonitoringTrust`
  crossing `onMonitoringHealth`, `applyMonitoringHealth` and the platform fan-out, and every
  `MonitoringTrust` literal in the unit suite. That is a second design change riding on this one, and
  landing two at once is how this phase has twice lost the ability to say which change a green result
  was measuring.

Record it as a `windows` entry of kind `todo` so a later diagnostics phase finds the reason rather
than the omission: a two-pump owner is told the plugin cannot vouch for both systems when it can
vouch for one, and the `FailureLog` line is where the distinction survives (`05-CONTEXT.md` D-03).
