<objective>
Make the recovery of the live path be reported by the evidence that proves it, rather than by the
next clock tick that happens to notice.

Purpose: `05-VERIFICATION.md` CR-02 confirmed by probe that the monitoring-health report runs only
from the two poll recorders. A shadow message arriving after a silence produces zero pushes; the
latch clears at the next poll tick, and the configured poll interval accepts up to 3600 seconds. So
a flood detected one second after the live path recovers can go unreported for an hour, and every
message arriving in that window is decoded, stored, and — before plan 05-06 — discarded.
`05-CONTEXT.md` D-05 ratifies lazy *detection* on the poll tick; it does not ratify lazy *clearing*,
and D-11 is explicit that a single good observation restores trust because a good observation is
direct evidence.

The existing scenario that ought to catch this runs under a short poll interval, which collapses the
distinction it is supposed to draw. Half of this plan is therefore the harness capability that makes
the distinction visible: park the plugin's device polling at the vendor, and the arriving message is
the only event left that could restore the trust.

Output: an arrival-driven report guarded to fire once per recovery, a standing device-route hold, a
step that waits until polling has actually parked, and a scenario that no poll tick can satisfy.
</objective>

## Why the parked poll, and not a longer interval

`05-VERIFICATION.md` asks for a scenario that clears the silence under a long poll interval. Traced
through the runtime this session, that is not buildable as written, and the reason is worth
recording rather than working around silently: **entering** the silent state needs a report, and the
only reporters are the two poll recorders. Under a long poll interval the first inventory lands at
launch and nothing reports again, so the scenario can never reach the state it means to recover
from. Lengthening the interval removes the defect's cover and the test's setup together.

Parking the poll separates the two. The scenario keeps the short interval that lets a poll tick
detect the silence, then holds the inventory route open so the loop parks inside a request that
never answers. From that moment no poll outcome can be recorded — the loop is strictly sequential,
so a recorded held request proves the previous poll already completed and reported — and the credential
rotation route still answers, which matters because rotation records no monitoring report and must
not be starved. The arriving message is then the only event in the process that could restore the
trust.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Shadow message arrival -> monitoring trust | The only direct evidence the live path is carrying; everything else is inference from a clock. |
| Monitoring trust -> HomeKit `Status Active` | The one signal that says whether a reading can be relied on. |
| Fake vendor service -> scenario determinism | A scenario that can be satisfied two ways proves neither. |
