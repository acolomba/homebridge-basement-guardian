<objective>
Make a credential refusal that lands mid-run a state the runtime stays in, rather than an act it
performed once, by ending the live connection at the halt and refusing to open another.

Purpose: `05-VERIFICATION.md` closed six of seven gaps and left one. Plan 05-07 made the refusal
reach the terminal branch -- real, and mutation-pinned -- but the halt leaves the shadow socket open
and `onReportedPatch` carries no halt guard. The temporary AWS credentials the socket is signed with
outlive the refused vendor credentials, which is the common case, so a heartbeat keeps arriving after
the plugin has stopped for good. On the pinned real HAP 2.2.2 an ordinary `updateValue` clears a
stored `statusCode`, so that one heartbeat returns all seventeen services to a fully-trusted read --
permanently, because nothing ever pushes again. A plugin that will never work until the owner changes
a password then looks completely normal in Apple Home. That is the false all-clear this project
exists to prevent, reached from a new direction.

Output: a halt that ends the live path, a scenario one step longer than the one that shipped, three
runtime cases, and the documentation and requirement rows brought back to what the code does.
</objective>

## The fix chosen, and the two rejected

The verifier named three fixes. This plan takes the first, and takes it far enough that it is a state
rather than an act.

**Chosen -- the halt ends the live path.** `haltOnTerminalAuthFailure` closes the shadow the way
`stop()` does, and the predicate `attemptShadow` already consults for a shutdown answers for a halt
too, so no path opens another connection afterwards. Three things make this the right layer:

1. **It removes the cause rather than the symptom.** The defect is not that `updateValue` clears a
   status. It is that a runtime which will never work again is still writing to HomeKit. Stop the
   writing and the presentation persists for free, with no code guarding anything.
2. **It shuts the arrival path synchronously.** `close()` sets `closing = true` before it ends the
   transport, and every notification in `attach` is gated on `isCurrent`, which reads `closing`.
   `closeQuietly` runs as far as the `close()` call in the same tick as `halted = true`. So there is
   no window -- not one message, not one microtask -- in which a heartbeat still reaches
   `onReportedPatch`. A callback guard would be a second statement of the same rule with a worse
   guarantee.
3. **It makes the code and its own stated contract agree.** The docblock already says nothing
   connects after the halt. Today that is false for the shadow. After this it is true, and the
   docblock gains one sentence naming the close rather than being retracted.

There is also a cost the open socket carries on its own: it is signed with temporary AWS credentials
that the rotation loop is no longer running to refresh, and `SYNC-05` asks for a lifecycle that can
be aborted idempotently. A dead runtime holding a live broker connection is wrong before anything is
said about characteristics.

**And the plugin currently disagrees with itself.** D-07's command-transport predicate reads `halted`
directly and stays unready for good, so a press on a switch is still refused by name after the
heartbeat. D-10's presentation is not, because it lives on a characteristic a value push overwrites.
An owner therefore meets an accessory that looks completely normal and refuses every press for a
reason nothing on screen explains. Two facts the plugin holds about one account, disagreeing. Closing
the live path puts them back together, because after it neither can move again.

**Rejected -- guard `onReportedPatch` on `halted`.** It is the cheapest edit and it is the wrong
layer. The socket stays open on a runtime that will never use it, still consuming rotating
credentials, still counting against the provider's connection ceiling, and the halt's docblock stays
false and would have to be weakened to say so. Worse, the canonical store would stop receiving
messages the broker is still delivering, so what the plugin holds and what the vendor is sending
diverge with nothing to observe the divergence. Dropping messages silently is the shape of a defect,
not the shape of a fix.

**Rejected -- re-apply the marking after each push.** This is a race the plugin must win every time,
forever, against every write path that exists now and every one added later. The push order inside
`applyMonitoringHealth` already exists because an ordinary push clears a stored status; building a
second ordering rule on top of it, on a path with no report to hang it from, means the presentation
survives exactly as long as nobody adds a third writer. And it leaves the runtime writing to HomeKit
after it has permanently stopped, which is the thing that is actually wrong.

**The lesson this repeats.** Plan 05-07 delivered a one-shot where a state was needed. The same
mistake is available here: closing the socket once, while leaving the connect path free to open
another, would be a one-shot close. That is why the halt is expressed as a predicate the connect path
reads, and why two of the three unit cases exist.
