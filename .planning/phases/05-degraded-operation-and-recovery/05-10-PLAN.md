The two README claims the verifier found untrue, in `## When the plugin cannot vouch for a value`:
```
README.md — "The delay is to the report and never to a safety state. The plugin holds no value back
while it waits, and it turns nothing normal. A late report is the only cost."
  Before this round: false. A withdrawn scope stopped publishing, so values from the working
  transport were held back. After 05-06 and 05-08 the first two sentences become true, and a third
  fact is now missing from the paragraph: until the poll notices the quiet connection, the services
  still say the plugin vouches for them.

README.md — "Every service then answers `No Response` in Apple Home, not the inactive state the
other failures use."
  Inaccurate as written. The credential pass pushes the status onto the trust characteristic alone;
  a controller reading a sensor value directly still gets the retained reading under a success
  status. Apple Home's accessory-wide No Response follows from the failing characteristic in a bulk
  read.
```

```
CHANGELOG.md — "The plugin now marks its services inactive when the vendor cloud stops sending live
changes, even while polling still succeeds."
  The review recorded this as omitting that the services also stopped updating. After 05-06 they no
  longer stop updating, so the entry becomes accurate as written — check it rather than assume it.

CHANGELOG.md — "The plugin now refuses a press of either switch while it has no way to reach the
vendor cloud, and the log says so."   (05-09 widens this to the restart window)

CHANGELOG.md — "When the vendor refuses your account email or password, every service answers
`No Response` until you correct them and restart Homebridge."   (05-07 widens this to a refusal that
```
