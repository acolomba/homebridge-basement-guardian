<objective>
Refuse a press for the right reason and say which one, and prove structurally that a HomeKit read
never reaches the network.

Purpose: success criterion 3 requires commands to stay disabled until valid state **and** command
transport return, and those two can differ — a fresh shadow snapshot can arrive while REST
authentication has not completed, or the reverse. A user diagnosing a refused press has to learn
which one blocked. Research found the state half already implemented and already answering -70412,
switched on for free by plan 05-01's withdrawal, so this plan proves that rather than rebuilding it,
and adds the transport half, which is genuinely new. The read-path invariant is the other half of
`RES-04` and is already true by construction; the work there is the gate that keeps it true, proven
non-vacuous the way this project's other static gates were.
Output: the transport predicate end to end, the refusal ordering pinned, and the read-path gate.
</objective>

## Planner assumptions carried by this plan

**PA-05 — `05-RESEARCH.md` A2: the refusal ordering is a judgement, not a fact.** This plan places
the transport rule immediately after `isNotAnOnRequest` and before `hasNoFreshState`, following the
research recommendation: when there is no way to send, naming the missing state is the less
actionable of the two truths. Either order is defensible. What is not optional is the unit case that
pins whichever order was chosen with both conditions true at once — without it a later reorder
changes the user-facing cause silently.
