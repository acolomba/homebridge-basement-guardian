<objective>
Make the fact a control row publishes from and the fact a write is refused on one fact, and make a
device's own confirmation resolve the request it confirms.

Purpose: `05-REVIEW-2.md` WR-02 and WR-06, two halves of one disagreement. Plan 05-06 widened the
publishing predicate so a scope withdrawn because the plugin is seeing less goes on publishing exactly
what the working transport supplied. It did not widen the write path's view of the same value, which
still treats any untrusted scope as no value at all. So during shadow silence the row publishes the
device's reported state while a press is refused with the cause `the plugin has no fresh state for
it` -- and the plugin has fresh state; what it lacks is a fast confirmation channel. Two documents
assert the opposite of the code: the binder's comment claiming the two facts cannot disagree, and the
scenario premise claiming the row withholds the value. The scenario passes for a different reason
than the one it states.

WR-06 is the same gate reaching one function too far. Reconciliation runs after the trust withdrawal
is recomputed, so a self-test the device confirmed on the snapshot that first observed the silence is
never matched, stays pending, and thirty seconds later logs that the device never confirmed it --
naming a device failure for a plugin-side trust withdrawal.

Output: a refusal cause that is true, one rule read by both halves, reconciliation against the
device's report, the corrected documents, and the validation rows.
</objective>

## The decision the review asked for, and why it goes this way

`05-REVIEW-2.md` WR-02 says: decide which fact the refusal is about, and make both halves read it. It
offers two routes. This plan takes both halves of the honest answer, because the two are not
alternatives -- they answer different questions.

**The refusal is about the transport, not the state.** During shadow silence the plugin has fresh
state: the poll delivered it and the tile is showing it. What the plugin lacks is a channel that can
observe a confirmation. The device confirms a self-test in about sixteen seconds; the pending window
is thirty; during silence the earliest confirmation is the next poll, which the configuration lets run
an hour. So a press allowed during silence would reach a real sump pump and then produce the exact
warning WR-06 is about -- the device never confirmed it -- for a plugin-side reason. The refusal stays.
Only the cause changes, from a missing state the plugin has to a quiet connection it does not.

**The published value and the read value are the same value, so they read one rule.** The row already
publishes the device's reported state during a seeing-less withdrawal, because plan 05-06 decided that
a value a working transport delivered belongs on the tile with the doubt carried by the trust row
alone. The write path's copy of the question was never updated. Making it read the same rule removes
the disagreement, makes the binder's own docblock true rather than aspirational, and leaves
`hasNoFreshState` meaning what its name says: the field did not decode, or its own scope's value
failed validation.

**Why not only widen the read.** Widening `reportedControlValue` alone would allow the press, which
the paragraph above rules out. **Why not only add the rule.** Adding the rule alone would leave the
row and the write path answering one question two ways, so the binder's docblock would have to be
retracted rather than made true, and the next reader would meet the same disagreement with a friendlier
log line over it.
