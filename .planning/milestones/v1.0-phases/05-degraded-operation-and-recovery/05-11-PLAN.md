<objective>
Give the REST poll back ownership of telemetry when the shadow has missed two heartbeats, so a
flooded pit reaches HomeKit on a device whose live path spoke and then went quiet.

Purpose: plan 05-06 fixed the accessory layer — a family-valid value arriving on a working transport
now reaches the tile and `Status Active` alone carries the doubt. A second gate sits upstream of it.
`pollTelemetry` returns the previous snapshot's telemetry whenever a shadow version is held, and the
watermark is released in exactly one place: `handleShadowDisconnected`. Shadow silence is not a
disconnection — that distinction is the whole point of D-05, since socket state flaps daily by
design. So for any device whose live path has ever delivered a versioned message, no REST poll
refreshes telemetry for as long as the silence lasts, and the flood CR-01 describes still cannot
reach HomeKit. `05-CONTEXT.md` D-13 rules that a shadow which has missed two heartbeats has stopped
owning telemetry and that REST polling takes it back.

Output: the handover fires from the silence predicate at the one point upstream of the poll's own
merge; ownership returns on the next message through the path that already exists; the two decisions
this amends say so in their own text.
</objective>

## The defect, proven twice

`pollTelemetry` returns `previous.data` whenever `previous?.shadowVersion !== undefined`. The
watermark is set by any shadow document that carries an observation and a version, which is every
real Gemini heartbeat. It is cleared in exactly one place — `handleShadowDisconnected` — and shadow
silence does not reach that handler, because the socket is open and the device has simply stopped
speaking. So once a versioned heartbeat has arrived, the poll stops replacing telemetry for the whole
duration of the silence.

The 05-06 executor reproduced it while writing the flood scenario: with a heartbeat delivered before
the clock moved past two missed heartbeats,
`Then the canonical snapshot carries these fields: | water_level | 31 |` never holds, however many
polls run; without a prior heartbeat the same scenario passes on the first poll
(`deferred-items.md`, "A shadow that goes silent never hands telemetry back to the poll").

The orchestrator reproduced it a second time against the built store on 2026-09-02:

```text
1. dry poll               water_level = 0
2. shadow heartbeat       water_level = 0 | shadowVersion = 5
3. FLOODED poll, silent   water_level = 0   <-- the poll is discarded
4. after release + poll   water_level = 31
```

**This is why 05-06's fix does not, on its own, deliver the outcome CR-01 names.** The accessory layer
now publishes what a working transport delivers; during silence nothing is delivered to it.

## Design question 1: where the release fires, and why not the obvious site

**The obvious site is wrong, and it is wrong by exactly one poll.** D-05 evaluates the silence
predicate lazily on the poll tick, so the natural-looking home is `reportMonitoringHealth`, which
already reads `trust.shadowSilent` and is the one place that turns silence into a report. But
`reportMonitoringHealth` is reached from `recordPollSuccess`, and `runPoll` calls
`await applyDevices(...)` **before** `recordPollSuccess()`. By the time the report runs, every
`applyDiscovery` of this poll has already gone through `pollTelemetry`, seen the watermark, and
returned `previous.data`. The flooded body this poll carried is gone. The release would take effect
for the *next* poll — and `pollIntervalSeconds` accepts up to 3600, so "one poll late" is up to an
hour late, which is the same cost 05-REVIEW WR-08 measured on the projection path.

**The site is the head of `applyDevices`, before the `for` loop that calls `applyDiscovery`.** Three
reasons, each checkable in the source:

1. **It is the only funnel.** `applyDiscovery` is called from exactly one place in the runtime — the
   loop at `accountRuntime.ts:299-301`. Every poll's telemetry enters the store through it, from both
   callers (`runPoll` and `launch`). A release at its head cannot be bypassed by a code path and
   cannot be one poll late by construction, rather than by the two calls happening to be in the right
   order.
2. **It is still the poll tick.** D-05 requires the predicate to be evaluated lazily on the poll tick
   rather than from a real-time loop, because the runtime schedules on `node:timers/promises`, which
   `advanceClock()` cannot move. The head of `applyDevices` is on the poll tick; it is simply earlier
   on the same tick than the report is.
3. **The two readings cannot meaningfully disagree.** Both sites call `health.trustNow()` against the
   injected clock. Time only advances between them, so a poll that released can only be *more*
   silent by the time it reports. The one interleaving is a shadow message arriving during the
   `await` inside `applyDevices`: then the release already happened and the report says the silence
   cleared. That is harmless and self-correcting, because the arriving patch re-establishes the
   watermark on its way through `applyReportedPatch` (design question 2).

A failed poll is deliberately **not** a release site. A poll that failed writes no telemetry, so there
is nothing to hand over, and firing there would churn the store on every failure for no observable
gain.

## Design question 2: how ownership returns, and that nothing new is needed

**The existing patch path already does it.** Trace a message arriving after a silence-release:

1. `onReportedPatch` calls `health.recordShadowMessage()`, which moves `lastShadowMessageAt` to now,
   so `shadowSilent` becomes false and the next poll performs no release.
2. It then calls `options.store.applyReportedPatch(deviceId, patch)`.
3. `isStalePatch(previous.shadowVersion, patch.version)` is `false`, because `applied === undefined`
   short-circuits it. The patch is applied rather than refused as stale.
4. `nextShadowVersion(previous, patch, observed)` skips its guard — the guard fires only when
   `!observed && previous.shadowVersion === undefined` — and returns `patch.version`. The watermark
   is back, and from the next `applyDiscovery` onward the poll leaves telemetry alone again.

This is the same mechanism the reconnect already relies on: after `handleShadowDisconnected` clears
the watermark, the complete-shadow request's document is applied for exactly this reason, which is
what makes the reconnect refresh restore anything at all. **Nothing new is required, and nothing new
may be added.**

Two consequences worth stating so nobody "fixes" them:

- **A document carrying no observation does not take ownership.** A `desired`-only command
  acknowledgement clears the silence — every routed message does, and 05-08 depends on that — but
  leaves the poll owning telemetry, because `nextShadowVersion`'s guard refuses to establish a
  watermark on the strength of having seen nothing. That asymmetry is safe: REST keeps feeding
  telemetry until a real heartbeat arrives, so there is no window where nothing is the source.
- **Out-of-order protection is given up for the first document after a release**, exactly as it
  already is after a reconnect, and for the reason the existing doc comment records: the alternative
  is a silently discarded refresh, which is a false normal. Silence adds a second trigger to a cost
  already accepted; it does not introduce a new one.

## Design question 3: idempotence, confirmed from the source

`releaseShadowSource()` becomes reachable on every poll of a long silence. Read at
`src/device/state.ts:328-334`, repeated calls are safe, and the reasons are structural rather than
incidental:

- The body writes one field, `shadowVersion: undefined`. A second call writes the same value over
  itself. `data` and `metadata` are carried across by reference in the spread, so no telemetry key
  and no receipt time moves — `receivedAt` in particular is untouched, which matters because it is
  the snapshot's only freshness field.
- It notifies nobody, deliberately and with the reason in a comment above it: clearing the watermark
  moves no telemetry key, so a listener filtering on the change report would be handed a change that
  did not happen. Repeated calls therefore produce no repeated notification.
- The only observable difference between one call and ten is snapshot object identity, and nothing
  reads it: `notify` is not called, and the per-key comparison in `changedKeys` compares the values
  inside `data`, whose object identity the spread preserves.

**No guard is added.** An early return "when nothing holds a watermark" would be a speculative
optimisation over a loop across a handful of devices, and it would add a branch that needs its own
coverage. Idempotence is proven by an assertion instead — task 2 carries it.

## Design question 4: what must not change, and the subtlest part of it

- **A shadow that is merely slow keeps ownership.** The release is gated on `shadowSilent`, which is
  `now - lastMessageAt >= 1_796_000`. Inside that window the watermark stands and `pollTelemetry`
  keeps returning `previous.data`, so a poll body cannot overwrite a value the live path delivered.
  Pinned by the existing case `SYNC-02 keeps the telemetry and metadata a later poll would overwrite
  while the shadow owns them`, which survives untouched because `POLL_INTERVAL_MS` in that suite is
  900 000 ms — one missed heartbeat, not two.
- **A reconnect still restores ownership the way it does today.** `handleShadowDisconnected` keeps
  its release, and the four parametrised cases
  `SYNC-03 hands telemetry back to the poll when the connection reports <reason>` keep passing.
- **`monitoringPathNow()` is not edited.** D-04 settled that.
- **D-11 still holds, and this is the easiest thing in the plan to get wrong.** D-11 says a REST poll
  must not clear a shadow-silence degradation. This plan does not touch that, because the two facts
  live in different objects:

  | | Where it lives | What changes it | What this plan does |
  |---|---|---|---|
  | **Who owns telemetry** | `snapshot.shadowVersion` in the store | `applyReportedPatch`, `releaseShadowSource` | adds a second trigger for the release |
  | **What the trust flags say** | `lastShadowMessageAt` in `monitoringHealth` | `recordShadowMessage` alone | nothing |

  `recordRestSuccess()` touches only `consecutiveRestFailures`. So after this plan, during shadow
  silence with REST healthy, **both** of these are true at once and neither implies the other: the
  poll's flooded reading reaches the tile, *and* every non-connectivity scope stays untrusted with
  `Status Active` false. Ownership moved; the degradation did not clear. Anything that lets a poll
  path call `recordShadowMessage()` or otherwise move `lastShadowMessageAt` breaks D-11 and must not
  be written.
- **The handover replaces telemetry wholesale; it does not merge.** `pollTelemetry` returns
  `{ ...device.data }`, the vendor body and nothing else. That is the established contract the
  disconnection handover already runs on: the REST snapshot is a complete observation of the device,
  and composing it with values the shadow left would produce a state no source ever reported. Do not
  "improve" this into a merge.

## Two things the existing tests will not tell you, and one they will get wrong

**The Cucumber suite cannot detect a late release.** `SHORT_POLL_INTERVAL_SECONDS` is `0.05` in
`features/support/steps/runtime.ts:18`, and `assertSnapshotFields` waits on `untilTrue` with a
5000 ms deadline. A release moved one poll later still lands 50 ms later, inside the deadline, so the
end-to-end scenario stays green under that mutation. **The "not one poll late" property therefore has
to be asserted in `test/runtime/accountRuntime.test.ts`**, where `advance(POLL_INTERVAL_MS)` steps the
runtime one poll at a time and the assertion can run after exactly one qualifying poll. Task 1 places
it there for that reason; do not move it into the feature file.

**Three existing scenarios rest on a telemetry record this handover will empty.** In the Cucumber
harness, `toDevice` gives every device `data: {}` unless a scenario says otherwise
(`features/support/steps/shadow.ts:65-74`). So once the release fires during silence, the poll body —
empty — replaces whatever a heartbeat had delivered. These three publish a heartbeat and then cross
1796 seconds:

| Scenario | Line today | What it would start passing on |
|---|---|---|
| `Shadow silence withdraws trust while polling continues` | 34 | `Sump Pit Flood sensor is not activated` would hold because `water_level` became absent, not because the retained 3 is not a flood |
| `A successful poll does not clear the shadow silence` | 139 | its prose says the poll keeps working while live signals go unobserved; the record it observed would be gone |
| `An identical heartbeat clears the shadow silence` | 157 | **its premise, directly.** The scenario exists to prove the recovery is driven from `onReportedPatch` and not from a snapshot listener, which only works if the republished heartbeat is genuinely identical. With `water_level` blanked in between, the heartbeat becomes a change, a snapshot listener would fire, and the scenario would pass against the very defect it was written to catch |

This is the fifth instance in this phase of "the check passes because the thing it rests on sits at
the value the defect produces". The repair is one line each — `Given these reported device fields:`
with the same value the heartbeat carries (`features/support/steps/shadow.ts:114-123`) — which gives
the REST body the field too, so the handover changes nothing observable and each scenario keeps
asserting what its prose claims. Task 1 owns the repair and the sweep for any fourth case.
