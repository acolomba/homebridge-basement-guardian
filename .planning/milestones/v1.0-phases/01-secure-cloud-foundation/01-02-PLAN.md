<objective>
Prove the whole Phase 1 architecture on one path: a valid configuration authenticates against the vendor Auth0 tenant, discovers devices over REST, produces one canonical snapshot per device in the store, and shuts down cleanly on the Homebridge shutdown event.

Purpose: this is the tracer slice. It wires every layer the phase will modify — bundled constants, configuration, authentication, REST transport, the state store, the account runtime, and the platform composition root — with one real end-to-end assertion. Every later plan in this phase expands outward from the modules this plan creates, so an architectural dead end surfaces here after one commit instead of after nine.

Output: a plugin that, given a valid account, holds live device state after `didFinishLaunching` and releases everything on `shutdown`.
</objective>

- Auth0 grant: `POST https://<auth0Domain>/oauth/token`, JSON body with `grant_type` of
  `http://auth0.com/oauth/grant-type/password-realm`, `realm`, `client_id`, `username`, `password`,
  and `scope` of `openid profile email`. Response carries `id_token`.
- REST authorization header: `Authorization: Bearer <id-token>`. An unauthenticated request returns
  HTTP 403.
- `GET /devices` returns device records shaped `{ deviceId, serialNumber, name, deviceTypeId,
  productLine, connectivity: { connected, timestamp }, data: { ... } }`. `deviceId` reads
  `<account-id>_<serial-number>`.

## Planner decisions recorded here

- The slice is delivered in three tasks rather than one. The plan is still a single tracer: one end-to-end path, one end-to-end assertion, no horizontal-layer plan hiding inside it. The split is a context-headroom decision, not a scope decision. A single task touching twenty-one files at a projected 95,000 tokens leaves no room for a mid-task correction, and the projection carries low confidence because no calibration samples exist yet. Three tasks give three commit boundaries at the natural seams — constants and configuration, then the vendor boundary, then the store, the runtime, and the composition root — so a bad estimate costs one task rather than the whole slice. The slice is still judged by one assertion end to end: task 3 writes that assertion before the store and the runtime have bodies, observes it fail, and commits it green.

- The red step lives inside task 3 rather than spanning three commits. An end-to-end case imports the store and the runtime, and a commit containing an import that resolves to nothing is rejected by `fallow dead-code --fail-on-issues`, which is the `npm-fallow` pre-commit hook and runs over the whole repository on any `src/**/*.ts` change; the same file also fails `npm run build:test` and repository-wide lint. A red step observed by running the test is worth the same as a red step recorded in a commit, and it is the only one this repository's hooks permit. Do not restore a cross-task red commit.
- `src/runtime/clock.ts` and `src/cloud/errors.ts` are additions to the `D-17` source tree, not narrowings of it. The clock is the discretion item `CONTEXT.md` left open about the injectable clock's shape; declaring it once and injecting it keeps retry, timeout, and receipt-time code testable without faking `Date`. The error module exists because `.claude/rules/typescript-unit-testing.md` requires errors to be asserted by class and structured fields.
- `pollIntervalSeconds` is carried in seconds through `BgConfig` and converted to milliseconds at the single scheduling site, so the configuration contract matches the units the settings form uses.
