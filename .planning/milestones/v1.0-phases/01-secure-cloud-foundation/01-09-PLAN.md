<objective>
Connect one socket to the vendor's shadow service, keep it fed with fresh credentials without disturbing it, and turn accepted shadow documents into reported patches the store can merge.

Purpose: `SYNC-03` needs a complete shadow after startup and after every reconnect, because the shadow service synchronizes current state rather than replaying missed events. `SYNC-04` needs credentials to rotate in place, which research established means keeping a cache fresh for the next handshake — no library re-signs a live socket, because the provider validates the signature only at the handshake and then leaves the connection alone for up to twenty-four hours. `SYNC-02` needs requested state to stay out of canonical state, which this layer enforces by never subscribing to the topic that carries it.

Output: a shadow client with a closed topic set, a synchronous signing hook over a credential cache, and reconnect owned by the capped retry policy.
</objective>

Shadow protocol facts this layer implements:

- The thing name equals the vendor device identifier.
- The plugin subscribes to get-accepted, get-rejected, and update-accepted, and publishes an empty
  payload to the get topic. It subscribes to no other topic and publishes to no other topic.
- Wildcard shadow subscriptions are explicitly discouraged by the provider and would also deliver
  requested-state messages.
- The device publishes partial reported updates that the service republishes on update-accepted; this
  is the approximately 898-second heartbeat.
- Shadow documents carry a monotonically increasing version used as the out-of-order watermark; the
  store already owns the discard rule.
- Two clients sharing a client identifier cannot be connected concurrently: the newer connection is
  accepted and the older one is disconnected. The vendor supplies a new client identifier with every
  credential response, so the identifier must be refreshed inside the signing hook.

Complete `src/cloud/shadow.ts` with the connection lifecycle. Build the signing closure to read the credential cache on **every** invocation and hand the result plus the injected scheme, region, and the clock's current time to the presigner, then set the client identifier on the supplied client object before returning the URL.

This is the whole of "rotate in place". The provider validates the signature only at the handshake and then leaves the connection alone for up to twenty-four hours, far past the roughly one-hour credential lifetime, and nothing re-signs a live socket. Refreshing the cache is therefore complete: the next handshake picks it up automatically. Do not call `end`, do not reconnect, and do not re-sign when credentials change.

Own reconnect through the injected retry policy. Register the error and close handlers so both route into one `retry.schedule` call; the policy's pending guard collapses the pair into a single retry chain, which is why the guard exists. Reset the policy on a successful connection. Do not use the transport library's own reconnect timer; it was set to zero for this reason.

Treat a close with no preceding error as routine: log it at debug with a message describing reconnection, never at warn or error. The provider closes a signed WebSocket at a non-adjustable twenty-four-hour ceiling, so at least one reconnect per day is expected operation, and logging it as a fault teaches the user to ignore the log.

On every successful connection, re-subscribe the full topic list and re-publish the complete-shadow request for every device, because the shadow service synchronizes current state rather than replaying what was missed.

`close()` sets a closing flag before ending the transport so a close notification arriving during teardown cannot schedule a reconnect, ends the transport, and resolves. It is idempotent.

Report state outward through `onConnected` and `onDisconnected` rather than deciding policy here: whether a failed shadow connection degrades the runtime to a polling-only path is the account runtime's decision, and this client owns transport only. The reason string passed outward carries a short classification, never the URL and never credential material.

Keep every named unit under 60 lines; the signing closure, the reconnect handler, and the post-connect resubscription are three separate named units.

## Flagged Planner Assumptions

The deterministic edge probe returned one `unclassified` row for `SYNC-04` that the auto-resolution
rules leave `unresolved`. It is surfaced here rather than dropped:

- **SYNC-04, category `unclassified`.** The probe could not classify the requirement. The planner's
  reading is that the uncharted edge is what happens when a credential refresh fails *and* the socket
  drops before the next successful refresh: the cache then holds credentials that are expired or
  nearly so, and the handshake will be rejected. This plan's client signs from whatever the cache
  holds and lets the rejected handshake become an ordinary transport failure routed through the capped
  retry policy, which is the correct behavior but is not a distinct code path. The account-runtime plan
  owns the companion half — a failed refresh always reschedules — and the degraded-operation scenario
  covers the observable outcome. Recorded here because no single test proves the combined case.

Additional assumptions carried from research, recorded so they are not rediscovered:

- The credential response is read as account-scoped: one endpoint, one client identifier, one
  credential object, serving every device shadow over one connection. Nothing in the ingested protocol
  record states this explicitly, but the response shape and the prior client's usage both imply it,
  and one connection is the cheaper direction to be wrong in.
- The device's partial reported updates are assumed to arrive on the update-accepted topic. If the
  vendor uses the documents topic instead, no heartbeat arrives and the subscription set is wrong.
  This is verifiable only against real hardware, which the opt-in profile reserves for a later phase.
