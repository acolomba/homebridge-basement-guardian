<objective>
Two of this phase's four false-normal paths live in the merge reducer, and both were reproduced against the built code. A shadow document with no reported section restamps `receivedAt` — the snapshot's only freshness field — while carrying zero telemetry, and the vendor publishes exactly that document every time it delivers a command. Separately, a REST poll replaces telemetry wholesale with no ordering guard, and because the version watermark survives the replacement, the shadow's re-delivery of the correct value is then refused as stale. A running pump reads as not running, and stays that way.

Purpose: the project's core value is that a source which has stopped carrying truth must not present as healthy. These two defects are that failure exactly. The fix is not "stop crashing" — it is to make the store say honestly which source currently owns telemetry and when an observation actually arrived.

Output: a reducer where receipt time means an observation landed, where the poll and the shadow cannot revert each other, and where a change report is a real change.
</objective>

    The version handling needs one more rule, and getting it wrong here creates a worse defect than the one being closed. A watermark is ordering information, so an observation-free document is still evidence about ordering and may **advance a watermark that already exists**. It may not **establish** one. Task 2 gives a defined watermark the meaning "the shadow currently owns telemetry", so a document carrying nothing would otherwise take ownership away from the poll on the strength of having observed nothing — telemetry would then freeze at whatever the poll last wrote while receipt time kept advancing on every poll, which is the same false normal wearing different clothes. So: when the patch carries no observation and the snapshot carries no watermark, the watermark stays absent; in every other case it takes the patch's version or keeps the previous one.

    That case is reachable in production, not only in a fixture. Ownership is released on every disconnect, and between a socket coming back up and the complete shadow landing there is a window in which a desired-only accepted document can arrive — the vendor publishes one on every command delivery. It is permanent for any device whose complete-shadow request is rejected, because that branch logs and returns without ever setting a version.

    Do not add the check in `applyReportedPatch` as an early return that drops the patch entirely. The document is real, the connection is alive, and the ordering information in it is worth keeping; what it does not carry is an observation of the device.

    Do not change `toReportedPatch` in `src/cloud/shadow.ts`. Building an absent-telemetry patch from a document with no reported section is the correct reading of the wire; the reducer is the layer that decides what an absent observation means, and putting the rule there also covers a REST-sourced patch and a future source.

    This is the design to implement; do not substitute either alternative the review sketches. A device-time ordering guard cannot work here: shadow patches carry no device time, so the stored device time is always the last poll's, and a comparison on it would either reject nothing or reject the poll updates D-15 depends on. Keeping telemetry shadow-sourced permanently while a watermark exists is the other alternative, and it breaks D-15 outright — during a shadow outage the watermark is still set, so polls would stop writing telemetry and the reconciliation backstop would silently stop reconciling. Releasing ownership on disconnect is what makes the same rule serve both.

    This is why the plan depends on 01-14 rather than running beside it. `releaseShadowSource` is only correct if the disconnect notification fires exactly when shadow ownership genuinely ends. Before 01-14's generation guard, a superseded connection's late close still raises that notification while the live connection is healthy and subscribed — which was reproduced during verification — so ownership would be released, the next poll would take telemetry back over, and the live shadow would look like it had stopped owning anything. With the guard in place every supersede path has already raised the notification for the generation it replaces, and `start()` supersedes nothing, so no ownership-ending path is missed and none is invented.

The provider forces at least one reconnect a day, so this happens at least daily. It is not a regression — today's polls clobber unconditionally — and it is not on the gap list, but D-014's preserve-the-last-valid-value rule says those keys should survive as stale rather than vanish. Marking a key stale needs the per-scope trust machinery that belongs to Phase 3, so record it in the summary as knowingly deferred rather than fixing it here.

That is bounded — the connection is opened with a clean session and no replay, so there is no queued backlog to arrive out of order, and a reported document that did arrive late still carries telemetry the device genuinely sent and merges key by key, with the next heartbeat correcting it. The alternative is the reconnect refresh being silently discarded, which is a false normal.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| AWS IoT message broker → canonical state | Untrusted shadow documents become the state HomeKit will read. |
| vendor REST body → canonical state | An untrusted snapshot describing an unknown moment lands in the same store. |
| canonical snapshot → listener | Arbitrary consumers receive the object that holds safety state. |
