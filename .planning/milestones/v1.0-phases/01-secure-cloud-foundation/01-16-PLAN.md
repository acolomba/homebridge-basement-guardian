<objective>
Four warnings sit on the two cloud clients and none of them is cosmetic. A success status with a body that is not JSON escapes as an untyped parse error, so every caller branching on the vendor error type falls through and the operator loses the route label the module promises. The command deadline is built after the token is fetched, so a lapsed token can push a two-and-a-half-second operation past twelve seconds. Two concurrent callers can both skip a valid cache and both issue a grant, against a tenant where the module's own documentation says every attempt extends a thirty-day block. And the token cache's temporary file is written without an exclusive create and is never cleaned up on failure, so its owner-only guarantee can be defeated and a file holding a bearer token can be orphaned in the Homebridge storage directory.

Purpose: none of these is a false-normal path, which is why they are warnings and not blockers. They are cheap, they are clearly correct, and two of them touch AUTH-02's own subject matter. Closing them here keeps them from being rediscovered in Phase 4, when commands make the deadline defect user-visible.

Output: typed failures on every REST path, a deadline that means what it says, one grant per lapse, and a cache write that keeps its permission guarantee.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| vendor REST response → plugin | An untrusted body, possibly not JSON at all, is read and typed here. |
| plugin → vendor token endpoint | Every attempt against this endpoint extends a thirty-day block on failure. |
| bearer token → Homebridge storage directory | Credential material is written to a shared filesystem location. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-87 | Information disclosure | parse error message embedding response bytes | medium | mitigate | The parse failure is caught and replaced with the module's own fixed unreadable-response message carrying only the route and the status; the raw error never reaches a caller or a log. |
| T-01-88 | Denial of service | operation deadline that starts after a token grant | high | mitigate | One combined signal is built before the token fetch and governs both, so a stated deadline is the deadline; the operation is still attempted exactly once. |
| T-01-89 | Denial of service | doubled grant rate against a throttling tenant | high | mitigate | One shared cache read and one shared in-flight grant, cleared on settle, so concurrent callers cannot double the attempt rate against an endpoint whose failures extend a thirty-day block. |
| T-01-90 | Information disclosure | token cache written without owner-only permissions | high | mitigate | The temporary file is created exclusively with the owner-only mode, so an occupied name fails rather than downgrading the mode; the resulting file mode is asserted in a case against a real temporary directory. |
| T-01-91 | Information disclosure | orphaned temporary file holding a bearer token | high | mitigate | The failure branch removes the temporary file before logging, so no failed write leaves credential material in the storage directory. |
| T-01-92 | Tampering | npm/pip/cargo installs | high | mitigate | This plan installs no package. The random suffix comes from the Node standard library already imported for the salt; if a task appears to need a dependency, stop and re-plan rather than installing. |
</threat_model>
