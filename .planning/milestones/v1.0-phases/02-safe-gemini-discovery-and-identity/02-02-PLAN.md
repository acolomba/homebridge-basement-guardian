<objective>
Build the DEV-05 absence-confirmation state machine as a standalone, fully unit-tested module, plus
the `DeviceStateStore.remove()` primitive it and the wiring plan (02-05) will need — independent of
the registry/accessory/platform work in Plan 02-01, so it can be reviewed and proven on its own
contract before anything calls it.

Purpose: this module stays family-neutral per D-003 — it tracks presence/absence by `deviceId` alone
and never reads a decoded field, so it composes with any current or future family without change.
`DEV-05`/`D-029` require a device to be removed only after two consecutive trustworthy
inventory responses omit it, plus one additional out-of-band confirmation immediately before the
accessory is unregistered — with failed responses never counting and an empty-but-valid list
counting. This plan delivers the counting half of that guarantee as a pure, injectable module;
`02-05` wires it into the account runtime and Homebridge unregistration once the identity/dispatch
plans ahead of it (`02-03`, `02-04`) have settled `platform.ts`.
Output: `src/accessories/reconciliation.ts` (new), `DeviceStateStore.remove()` (new method on the
existing Phase-1 store).
</objective>

    - `observe(deviceIds)` called once with a list that omits a never-before-seen deviceId does nothing
      for it (nothing to confirm absent yet) and returns an empty `confirmedAbsent` list.
    - `observe(deviceIds)` called once with a deviceId present, then again with that deviceId absent,
      returns an empty `confirmedAbsent` list (only one absent observation so far).
    - `observe(deviceIds)` called with a deviceId present, then twice in a row with it absent, returns
      that deviceId in `confirmedAbsent` on the second absent call.
    - `observe(deviceIds)` called with a deviceId present, absent, then present again, then absent again
      resets the counter — the fourth call's `confirmedAbsent` does not include it (counter was reset to
      zero by the reappearance, so only one absence has been observed since).
    - `observe([])` (a schema-valid empty list) is a legitimate trustworthy response — a deviceId
      previously observed present, then omitted by two consecutive `observe([])` calls, is reported
      confirmed-absent exactly like a non-empty list omitting it.
    - `observe(deviceIds)` called a third and further time while a deviceId stays absent keeps reporting
      it in `confirmedAbsent` on every call (so a caller whose out-of-band final check fails once can
      retry on the next successful poll without extra state).
    - `forget(deviceId)` stops all tracking for that deviceId — a subsequent `observe` that omits it does
      not report it in `confirmedAbsent` (there is nothing left to confirm), and a subsequent `observe`
      that includes it starts a fresh count from zero, exactly as if it had never been seen before.
  </behavior>
