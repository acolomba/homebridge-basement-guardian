# Phase 05.1 Plan 05: The Persisted Arrival Anchor Summary

**The wall-clock arrival anchor now survives a restart in a file of its own under the Homebridge storage path, so a bridge restarted after a pump has been quiet for hours no longer hands that pump a fresh certificate of health.**

## Performance

- **Duration:** 22 min across the four task commits; the gate, the four mutations and this summary were completed in a later session after the executor stopped
- **Tasks:** 2
- **Files created:** 2
- **Files modified:** 6

## Accomplishments

- `src/runtime/arrivalAnchors.ts` holds one anchor per device and one file. The map operations answer at once and the two disk operations are promises, which is what lets `monitoringHealth.ts` read anchors while keeping its stated property that it owns no timer and touches nothing outside itself.
- The read path follows the token cache: a first start with no file is ordinary and says nothing, every other unusable file is a debug note and never a failure, and unreadable and malformed give the same answer. The parsed value is narrowed by a hand-written predicate whose per-entry guard is a `typeof` test rather than a truthiness test — a zero anchor is legal, and `JSON.stringify` turns a non-finite number into `null`.
- A file carrying any bad entry is rejected whole rather than salvaged in part, with the reason written down: the entries that survived would go on vouching for their devices on evidence the rest of the file just contradicted.
- The write is a temporary file carrying the process id and a fresh random suffix, an exclusive create, a rename, and a removal of the temporary when the rename fails. The one deliberate difference from the borrowed shape — no owner-only mode — is stated in the code with its reason.
- `monitoringHealth.ts` reads and records anchors through the injected store and writes no file. Admission records an anchor **only when the store holds none**; a message arriving records unconditionally.
- The runtime builds the store beside the failure log where `deps.storagePath` already is, awaits `restore()` in `start()` before the launch, fires `persist()` unawaited on the reporting tick, and drops the anchor at the single confirmed-removal site beside the arrival stamp and the failure-log kind.

### V9a — admission overwrites a restored anchor

- **Result: red, three cases.** `test/runtime/monitoringHealth.test.ts:452` (*holds a pump silent across a restart…*), `test/runtime/monitoringHealth.test.ts:488` (*leaves a stored anchor where it is when a device is admitted…*), and `test/runtime/accountRuntime.test.ts:795` (*D-07 reports a pump silent on its first report when a stored anchor predates the whole window*). ### The pruning mutation — the anchor drop deleted

`options.anchors.forget(deviceId)` deleted from the confirmed-removal site in
`src/runtime/accountRuntime.ts`.

- **Result: red, two cases — one more than expected.** The expected one is `test/runtime/accountRuntime.test.ts:2676` (*drops the arrival anchor of a removed pump…*). The second is `test/runtime/accountRuntime.test.ts:2635` (*drops the reporting kind of a removed pump, so the identifier coming back announces no recovery*), which failed on `warnings: 2` where it expects `1`.
- **Why the second one fires, since it is worth keeping:** a retained anchor outlives the removal, so when the same identifier returns it is admitted, finds an anchor already in the store, keeps that stale one, and reads silent at once — producing a second silence warning for a device that had just been re-admitted. The drop is therefore load-bearing beyond bookkeeping: it is what stops a returning identifier from inheriting the silence of the device that carried the identifier before it.

## Decisions Made

- **The narrow reading of D-08, in the form D-12 uses.** *Decision:* D-08's "falls through to D-02 — silent until told otherwise" governs the platform-map lookup, not the silence measurement. *Alternative named:* read literally as a rule about the measurement, so a device admitted but never heard from is silent at once. *The measurement behind the choice:* the literal reading contradicts `createMonitoringHealth`'s shipped rule that admission is the right zero, and would leave every device on every install untrusted for fifteen minutes after an upgrade, for no observation anyone made. Both readings agree on the case D-08 is actually about — an accessory restored from cache before discovery completes has no map entry and does not vouch — and that answer comes from the platform lookup rather than from this module. The paragraph's conclusion is in the code beside `silenceElapsedMs`. **If a later reader concludes D-08's wording should be amended rather than read narrowly, that is a CONTEXT.md amendment and not a silent code change.**
- The owner-only file mode was not carried over from the token cache, and the code states the reason rather than leaving the omission to be noticed.
- A malformed file is rejected whole rather than in part.
- The ENOTEMPTY teardown failure was fixed in the harness rather than in the runtime — see Deviations.

## Deviations from Plan

### The harness teardown, one file outside the plan's `files_modified`

`features/support/fakeHomebridgeApi.ts` is not in the plan's file list and was changed anyway. The
full suite failed once on `A reported mains power fact reaches both power services` with
`ENOTEMPTY: directory not empty, rmdir '/tmp/basement-guardian-mUBnsS'` raised from the `After` hook —
**103 of 104 scenarios passed, and the failure was in teardown rather than in a step.**

The cause is this plan's own fire-and-forget write. `void options.anchors.persist()` on the reporting
tick can land the anchor file in the storage directory between `rm`'s listing of that directory and
its `rmdir`, and the removal then fails. The fix gives the harness's `rm` `maxRetries: 5` and
`retryDelay: 20`, with the cause written above it.

**Why the harness rather than the runtime:** making `stop()` await the write would contradict the
reason the plan gave for firing it unawaited — the report must not wait on a disk — and the race does
not exist in production, where nothing deletes the Homebridge storage directory under a running
plugin. The residual exposure, a `.tmp` file stranded by a process killed mid-rename, is the same one
`src/cloud/auth.ts` has carried since Phase 1 and is not this plan's to change.

After the fix the suite is green at 104 of 104, run alone.
