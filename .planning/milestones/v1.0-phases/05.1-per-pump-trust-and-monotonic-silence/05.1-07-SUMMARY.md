## The Live Single-Device Check

Performed 2026-09-04 against the real Gemini in the `dev/hb` container (`homebridge/homebridge:latest`,
Homebridge v2.4.0, HAP v2.2.2), running the plugin built from this branch. The full table is in
`05.1-VALIDATION.md` under *Manual-Only Verifications*. In short:

1. **17 services, all `Status Active=1`**, values plausible — `Water Level=20` on raw code 1, mains present, battery 100 % and charging, controller link present, primary pump 15 activations since 2026-09-02.
2. **Restart marks then recovers**, on both boots: `Loading accessory from cache: Gemini (17 services no longer vouched for, 2 controls refusing presses)` before any poll, then all 17 active again after the first successful poll.
3. **The anchor file, read from disk:** 58 bytes, one entry, the vendor `deviceId` mapped to a finite millisecond number matching the admission in the log. No credential, token, email or local-network value.
4. **The controller-link warning did not appear.** The link was present for the whole session. Recorded as not observed rather than inferred from the code.
5. **No live-reporting warning or recovery line appeared.** No warning of any kind was logged after either launch.

**The result worth keeping.** The anchor file was copied before a deliberate restart and compared
after it: **byte-identical, `2026-09-04T19:12:41.078Z` before and after.** That is plan 05.1-05's
rule — admission records an anchor only when the store holds none — observed on the live path rather
than argued from the unit tier. The suite pins the same rule against a stale anchor; this run shows
the real plugin writing, restoring and declining to overwrite one.

**What the session did not cover, stated rather than softened.** No pump cycle, fault, power event,
controller-link drop or reconnect occurred, so every degradation path stayed unexercised end to end,
and the warning this phase rewrote was never emitted on hardware. The container holds exactly one

## Deviations from Plan

### The checkpoint was run here, on the maintainer's instruction

The plan hands the live check to a human. The maintainer instead authorised this session to run it
(`"you can edit it yourself. credentials are in ~/bg.env. then run it"`), so the container was started
and the log, the HAP database and the anchor file were read directly. `.env` was already filled, so
no credential was written or read into any artifact.

### The container storage was root-owned, and the repair was chosen for being reversible

`./dev/hb up` failed with `EACCES` writing `dev/homebridge/config.json`: a previous run had left that
file and `accessories/` owned by root, so the renderer could not rewrite them. **`./dev/hb reset` was
rejected** — it wipes storage and forces re-pairing with the phone, destroying the cached accessories
this very check needs. The ownership was repaired instead with a throwaway root container
(`docker run --rm -v dev/homebridge:/s alpine:3 chown -R 1000:1000 /s`), which preserves every file.

### Two self-inflicted process failures, both of the kinds this phase tracks

- **A masked failure.** The first `./dev/hb up` was run as `./dev/hb up 2>&1 | tail -25`, and with `pipefail` off the harness reported exit 0 while the render had died on `EACCES`. This is the phase's own named blocking anti-pattern, committed by the orchestrator. Every later invocation captured the status separately.
- **A rejected commit.** `gitlint` refused the first records commit for a 73-character title. It was shortened and re-committed; nothing was amended, because a rejected hook means the commit never happened.

### Auto-fixed Issues

`prettier` reformatted `test/accessories/basementGuardian.test.ts` during wave 6's task-2 commit. The
file was restaged and the commit re-run.
