<objective>
Rename two published HomeKit service-name pairs for internal consistency ("Backup Pump Activated" ->
"Backup Pump Running"; the two `backup-battery` rows swap to "Backup Battery Level" / "Backup
Battery"), fix a README config example that omits the two schema-required fields, convert a manual
footnote into a GFM admonition, run the project's `simple-english`/`humanizer` skills over README.md
and CONTRIBUTING.md, and reset CHANGELOG.md's `0.1.0` entry to a two-line summary.

Purpose: "Primary Pump Running" and "Backup Pump Activated" name the same kind of thing (a sensor
that follows live pump activity) with two different words; unifying on "Running" removes a naming
inconsistency while the plugin is still very early in its published life. The battery-row swap gives
the row Apple Home actually renders a plain name ("Backup Battery") and moves the estimated-percentage
row to a name that says what it is ("Backup Battery Level"). The README and CHANGELOG edits bring
those documents in line with the schema and with the project's own prose conventions.

Output: renamed service kind/displayName pairs threaded through `src/`, `config.schema.json`, every
affected `test/` and `features/` file; a corrected README config example and admonition; a
simple-english/humanizer pass over README.md and CONTRIBUTING.md; a reset CHANGELOG.md `0.1.0` entry.
</objective>

  `Backup Pump Running`. This is the contact-sensor row in `pumpDefinitions()` that follows live
  `backup_pump_running`. Do not touch `Primary Pump`/`Backup Pump` (the truthful condition services)
  or `Primary Pump Fault`/`Backup Pump Fault` (fault sensors) -- only this one row is in scope.

  `batteryDefinitions()`): `Backup Battery` -> `Backup Battery Level`.
- Display name (custom `services.BackupBatteryService` row, `kind: 'backup-battery'`, second in
  `batteryDefinitions()`): `Backup Battery Facts` -> `Backup Battery`.
- The shared `kind: 'backup-battery'` string, the `BackupBatteryService`/`batteryFactsValues`/

  explaining why the two rows share one kind and subtype are unchanged -- only the two `displayName`
  string literals move.

**Two orderings exist among the seven `ignoredFaults` names, and they answer to different rules.**
`src/accessories/services.ts`'s `NOTIFICATION_SERVICE_KINDS` -- and every list in `test/`/`README.md`
that mirrors it (`test/config.test.ts`, `test/accessories/services.test.ts`,
`test/accessories/serviceCatalogue.test.ts`, `test/platform.test.ts`, `README.md`'s `ignoredFaults`
bullet list) -- is in catalogue **declaration** order, which is arbitrary and does not change here:
rename the one slug/name in place, at its existing position, in every one of those lists.
`config.schema.json`'s `ignoredFaults.items.enum`/`enumNames` (and its mirror,
`test/configSchema.test.ts`'s `expectedValues` array in the 'CONF-06 offers exactly the seven
removable notification sensors' test) is instead **deliberately alphabetical by label** -- confirmed
by that test's own comment ("The order is deliberately alphabetical by the label an administrator
reads..."). `Backup Pump Activated` sorted before `Backup Pump Fault` (`A < F`); `Backup Pump Running`
sorts after it (`R > F`). Task 1 below reorders only these two arrays/lists, moving the renamed pair
from first to second position; every other one of the seven names, in every file, keeps its current
order untouched.

**A text-prefix relationship inverts under the battery rename, and one test file's disambiguation
trick has to move with it.** Today, `Backup Battery` (short) is a text prefix of `Backup Battery
Facts` (long); `test/accessories/basementGuardian.test.ts` disambiguates a warning-string substring
search between them with a trailing-comma needle (`'Backup Battery,'`) on the *short* name. After the
rename the short name becomes `Backup Battery` (the former Facts row) and the long name becomes
`Backup Battery Level` (the former standard row) -- `Backup Battery` is still the shorter, still a
prefix of the other, but it is now attached to the *other* row. Task 1 moves the trailing-comma needle
to the row it now belongs to. Full detail is in Task 1's action for the two affected test cases.
