## The regex (finding 3)

Current: `/^[^\s@]+@[^\s@]+\.[^\s@]+$/`. The two `[^\s@]+` runs around `\.` both admit dots, so the engine tries every dot split and the domain match is quadratic.

Replacement: `/^[^\s@]+@[^\s@][^\s@.]*\.[^\s@]+$/`

Equivalence argument (this is why it is safe, and what the new test pins). Both patterns require a local part of one or more non-space non-`@` characters, exactly one `@`, and a domain of non-space non-`@` characters. The old pattern's domain condition is "some dot exists that is neither the first nor the last character". The new pattern consumes one leading character, then all characters up to the *first* dot at index >= 1, then requires at least one character after it — which is "the first dot at index >= 1 exists and is not the last character". Those are the same condition: if any interior dot exists, the earliest dot at index >= 1 is at or before it and so is also interior; conversely the dot the new pattern matches is interior by construction. Backtracking is now linear because the run before `\.` excludes dots.

Ten cases were checked by hand and both patterns agree on all ten, including the two that look wrong but are pre-existing behaviour: `user@example..test` and `user@example.test.` are both accepted today and must stay accepted. Tightening them would be a validation change, which this task does not authorize.

## The selector parameter (finding 6)

`nextOfflineCount(previous, connected, threshold)` is a module-local helper with two call sites, both passing `snapshot.connectivity.connected`. Its comment carries the RES-03 / D-016 invariant: the count only ever reads `connectivity.connected`, never the device's own `data.offline` report.

What the rule literally asks for — two methods — was considered and rejected as disproportionate. It would push `snapshot.connectivity.connected ? 0 : ...` to both call sites, so the safety invariant that currently has one home would be expressed twice, in a file whose whole design is "one narrowing, in one place".

The chosen fix is smaller and removes the smell the rule detects rather than working around it: take the connectivity value instead of a bare flag.

```
function nextOfflineCount(previous: number, connectivity: DeviceSnapshot['connectivity'], threshold: number): number
```

`DeviceSnapshot` is already imported as a type in this file, so this needs no new import and does not open a question about the accessories tier importing from `src/cloud/`. The two call sites drop one property access (`snapshot.connectivity.connected` -> `snapshot.connectivity`). No boolean parameter remains, so the rule has nothing to report, and the comment's claim about what the count reads becomes structurally true rather than a promise.

**Fallback, not applied by this plan.** If a later SonarCloud analysis still reports `S2301` at this site, the proposal is a narrowly-scoped ignore entry in `sonar-project.properties` mirroring the existing S5332 entry's style — an `e2` criterion for `typescript:S2301` on `src/accessories/basementGuardian.ts`, with a comment recording that splitting the helper would duplicate the RES-03 / D-016 invariant across two call sites. Do NOT add it pre-emptively: it would suppress the rule for the whole file while the real fix is untested.
