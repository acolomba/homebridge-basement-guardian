<objective>
Fix four measured defects in how the plugin reads the vendor REST device routes, so
production discovery stops failing on every real response.

The four defects, all confirmed against the live vendor API during Phase 1 UAT:

- WIRE-01: `GET /devices` answers `{ devices: [ ... ] }`, not a bare array.
- WIRE-02: `GET /devices/{deviceId}` answers `{ device: { ... } }` — a **singular** key,
  different from the list route's plural key.
- WIRE-03: `serialNumber` sits at `attributes.serialNumber`, not at the top level.
- WIRE-04: `productLine` sits at `attributes.productLine`, not at the top level.

Purpose: production discovery currently fails 100% of the time with
"Device discovery failed on GET /devices with HTTP 200." Every unit test and every
Cucumber scenario passes because the fixtures encode the shape we imagined, not the
shape the vendor sends. The fixtures are part of the defect.

Output: wire-level types, guards, and a normalizer at the REST boundary in
`src/cloud/types.ts`; envelope unwrapping in `src/cloud/api.ts`; test fixtures and the
Cucumber fake rebuilt on the measured wire shape.
</objective>

<approach_note>
The suggested approach — normalize at the wire boundary, leave the internal `ApiDevice`
interface untouched — is the right one and this plan adopts it. Reasons it holds up:

- `ApiDevice.serialNumber` is read at `src/device/state.ts:178` and flows into
  `src/persistence/accessoryContext.ts`. Reshaping `ApiDevice` would push the change
  through `state.ts`, `events.ts`, `health.ts`, `accessoryContext.ts`, `accountRuntime.ts`,
  and four more test files for no gain.
- The real wire record carries eight keys the plugin has no use for — `accountId`,
  `location`, `homeId`, `roomId`, `state`, `timestamp`, `shadow`, `attributes`. A
  boundary normalizer that builds `ApiDevice` field by field keeps all of them out of
  accessory context and out of logs. A widened `ApiDevice` would carry them inward.

One deviation from the stated file list, and it is required: **`features/support/steps/harness.ts`
must also change.** Its step `the device list holds the devices the scenario sets`
(line 289-291) compares the raw REST body against `world.devices`, which are internal
`ApiDevice` records. Once the fake serves the real envelope that comparison is false and
`features/harness.feature` fails. The step is amended, not deleted.

Two deliberate narrowing choices, both stated so a reviewer can challenge them:

- The wire guard requires `attributes.serialNumber` to be a string and does **not**
  require `attributes.productLine`, even though the live response carries it. The plugin
  reads nothing from `productLine`. The existing guard convention in this file is to
  require exactly the fields the plugin reads; requiring an unread field only adds a way
  to fail closed on a device we could have served. WIRE-04 is satisfied by recording where
  the field lives in a comment and by never looking for it at the top level.
- `toApiDevice` builds its result field by field. It never spreads the wire record.

Two facts to state plainly rather than let the summary overclaim:

- **WIRE-04 has no test and cannot have one.** It is discharged by a comment naming where
  `productLine` lives and by the absence of any top-level lookup for it. An absence is not
  observable behavior, so no assertion can prove it. The summary must say WIRE-04 was
  addressed by documentation and by a code review of the diff — not that it was verified.
- **The Cucumber fake's records break the measured `deviceId` invariant.** The live probe
  showed `deviceId` is byte-identical to `<accountId>_<attributes.serialNumber>`, but the
  fake pairs its scenario devices' identifiers with one fixed placeholder account
  identifier, so the relation does not hold in the fake. Nothing in the plugin reads
  `accountId` or splits `deviceId`, so this costs nothing today; it would matter only if
  some future change came to depend on that relation, and the fake would not catch it.
  Task 1 records this in a comment in the fake's serializer.
</approach_note>

<measured_wire_shape>
This section is the specification. It is measured, not inferred. Fixtures must match it.

List route body: an object with one key, `devices`, holding an array of wire device records.

Single-device route body: an object with one key, `device`, holding one wire device record.
The key is singular. It is not the same key the list route uses.

Wire device record — the confirmed top-level keys, in the order the vendor sends them:

`accountId`, `deviceId`, `deviceTypeId`, `location`, `name`, `homeId`, `roomId`, `state`,
`data`, `timestamp`, `shadow`, `attributes`, `connectivity`

- `accountId` — 24 lowercase hex characters.
- `deviceId` — exactly `<accountId>_<attributes.serialNumber>`, both segments verified
  byte-identical. The plugin still treats it as opaque and never splits it.
- `deviceTypeId` — `wayneWaterGemini`.
- `state` — `{ wifi_signal_dbm: number, mcu_firmware_version: string }`.
- `attributes` — `{ productLine: string, serialNumber: string }`. `productLine` reads
  `wayneWater`. `serialNumber` is 15 characters.
- `shadow` — `{ state: {...}, data: {...}, timestamp: number }`, an embedded snapshot.
- `homeId` and `roomId` — null on the probed device.
- `connectivity` — `{ connected: boolean, timestamp: number }`. Already correct. Do not change.
- `data` — all 18 telemetry fields under the names already expected. Already correct. Do not change.

`wifi_firmware_version` and `mcu_target_version` are **absent**, from both REST `state`
and embedded `shadow.state`. That is a Phase 2 DEV-07 planning input, not a defect here.
Do not add handling for it.

`GET /credentials/aws` already satisfies `isAwsCredentialsResponse` against the live
response. Do not touch it.
</measured_wire_shape>
