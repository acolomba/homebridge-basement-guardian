## The judgement about which unit shapes earned their place

Three shapes were added and two were deliberately not:

- **`null`** — what the scenario now feeds, and what a serializer emits for an empty section.
- **An array** — the only one of the three a plausible future simplification would wrongly accept.
  A naive `typeof value === 'object'` guard admits an array, so this is the shape that discriminates
  the mutation a later reader would actually write.
- **A string** — one more line in the same loop, and it pins truncation.
- **A missing or non-record `reported`: not added.** The shipped case `leaves a requested state
  section nowhere in the produced patch` (`test/cloud/shadow.test.ts:481`) already drives that branch
  — it sends `{ state: { desired: ... } }`, `sections` falls back to `{}`, and both halves come out
  absent. A second case would pin nothing better.
- **No case at the store tier: not added.** `ReportedPatch.data` is typed
  `Record<string, unknown> | undefined`, so `test/device/state.test.ts` cannot be handed a malformed
  section without a cast that lies. The tier where the shape is decided is `toReportedPatch`, and that
  is where the cases went.

## The five corrected sites, and what each now says

1. **`src/device/state.ts`, the comment above `nextShadowVersion`.** Replaced the paragraph that
   justified the guard with "a document reporting only device metadata -- a firmware revision, a
   signal strength". It now says `patch.data` is absent for two inputs, that `toReportedPatch` keeps
   the section only when `isRecord` accepts it, and that validation above "checks only two levels --
   the payload is an object and its `state` is an object -- and says nothing about `reported` or the
   sections under it, so a truncated or corrupt telemetry section parses, validates, and arrives here
   with the telemetry half empty." The `CR-03`, `SYNC-02` and `D-014` anchors are kept.
2. **`src/device/state.ts`, the `ReportedPatch.data` doc comment.** Was "Absent when the message
   carries none". Now: "Reported telemetry. Absent when the message carried none, and equally absent
   when what it carried is not an object."
3. **`src/cloud/shadow.ts`, the `toReportedPatch` comment.** Both original sentences kept; added "A
   section that is not an object is refused here rather than passed on, and this is the only place
   that refuses it: validation above reaches two levels, the payload and its `state`, and says nothing
   about the sections under `reported`. Handing a corrupt section on as telemetry would let a message
   which delivered no reading take the readings from the poll (CR-03)."
4. **`features/degradedOperation.feature`, the scenario.** Renamed to `A report whose telemetry section
   cannot be read leaves the readings with the poll`. The second paragraph now carries the count in
   the sentence: "A 90-minute window on one system on 2026-09-03 caught seven messages. All seven
   carried both sections: telemetry in one, device metadata in the other." It adds "The plugin's
   shadow validation checks two levels only, the whole payload and the state wrapper inside it, and
   says nothing about the sections below that." The delta-topic claim is deleted.
5. **`features/support/steps/shadow.ts`, three comments.** The `publishReported` comment loses the
   false delta claim and now says "Nothing upstream refuses such a section: the plugin's shadow
   validation reads two levels, the payload and its `state` wrapper". The metadata step's own comment
   says the telemetry section "travels beside it as `null`... the reading is present on the wire and
