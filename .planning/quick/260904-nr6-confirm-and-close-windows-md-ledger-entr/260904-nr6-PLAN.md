Read in full during planning, so the task below does not need to re-derive it:

- **The log call site is `liveReportingSilent(deviceId)` in `src/runtime/accountRuntime.ts:78-83`,
  called from `recordFailure(liveReportingKind(deviceId), liveReportingSilent(deviceId))` at
  `:589`.** The function interpolates exactly one value into the sentence — the vendor `deviceId` —
  and nothing else. The comment immediately above the sibling `liveReportingKind` function
  (`:61-70`) states why: `FailureLog` rate-limits per `kind` string, so a per-device kind buys each
  pump independent warning cadence, and "the vendor `deviceId` is the Phase 2 ruling's non-sensitive
  value, permitted in logs and in accessory context, and it names no route, header, credential or
  account (D-14, D-027, AUTH-02)."
- **The redaction test is `test/runtime/accountRuntime.test.ts:2230-2250`**, titled *"names the
  controller and no route, no header, and no credential in the line a silent live connection
  records."* Its own comment (`:2226-2229`) states the same reasoning as the source: "The vendor
  deviceId is the one identifier a Phase 2 ruling admits to logs, and on a two-pump account a
  sentence without it does not say which basement stopped being watched. Everything the redaction
  rules actually forbid — route, header, credential — still has to be absent." The shipped assertion
  is `{ reported: true, scheme: false, authorization: false, secret: false, device: true }` — the
  three things redaction actually forbids (a URL scheme, an `authorization` mention, any registered
  secret) all still assert `false`; only `device` asserts `true`.
- **This is exactly what the phase's own threat model disposed of, not a drift from it.** `T-05.1-03`
  ("the per-device kind and reason strings" / "the per-device kind and reason name a `deviceId`") is
  registered in both `05.1-02-PLAN.md:471` and `05.1-03-PLAN.md:261` as `Information disclosure`,
  severity `low`, disposition `mitigate`, with the mitigation text: "Only the vendor `deviceId` is
  added. The Phase 2 ruling of 2026-08-29 records it as non-sensitive and permitted in logs and
  accessory context; `D-027` still keeps it out of public artifacts. No token, URL, response body or
  account identifier enters either string." `05.1-02-SUMMARY.md:306-312` (deviation 2, "The
  silent-live-connection log line now names the device, and one shipped assertion flipped") records
  the flip from `device: false` to `device: true` as the plan's own D-14 instruction reaching a
  shipped assertion, and `05.1-02-SUMMARY.md:362` records `T-05.1-03` as `Mitigated`, citing the same
  positive assertion this task re-reads.
- **D-14 (`05.1-CONTEXT.md:211-223`) is the decision that made this change.** It made the
  `LIVE_REPORTING` failure-log observation per device (rather than account-wide), and states plainly:
  "the vendor `deviceId` is a Phase 2 ruling's non-sensitive value that may enter logs." The Phase 2
  ruling itself is recorded in `STATE.md` Accumulated Context (`[Phase 2, decided 2026-08-29]`): "The
  vendor `deviceId` is treated as non-sensitive and may enter accessory context and logs. `D-027`
  still keeps it out of public artifacts." `D-027` (`PROJECT.md:165`) is the sanitized-artifacts rule
  the ruling carves an exception into: "Use stable placeholders, exclude raw/account/local-network
  data, and run secret and identifier scans before release" — a `deviceId` in a log line or in
  accessory context is neither a public artifact nor scanned for exclusion, so the two rules do not
  conflict.
- **Conclusion: this is confirmed correct, not a leak.** No production code change and no test change
  are needed. Every one of AUTH-02's actually-forbidden values (passwords, tokens, temporary AWS
  credentials, authorization headers, authentication bodies) stays asserted absent from the line; only
  the vendor `deviceId`, which AUTH-02 does not name and the Phase 2 ruling explicitly permits, is
  present.
- **Verb choice: `windows waive`, not `windows fixed`.** `markFixed`
  (`.claude/gsd-core/bin/lib/broken-windows.cjs:275-283`) takes no `reason` parameter at all and only
  ever sets `status` and `resolved_at`; the CLI's own usage error confirms `windows fixed <id>` takes
  exactly one positional argument, the id. Every one of the ledger's 16 `fixed` rows carries an empty
  `reason` — that verb is for entries where the underlying thing changed (code, a document) and the
  commit itself is the record. `markWaived`
  (`.claude/gsd-core/bin/lib/broken-windows.cjs:263-274`) requires a non-empty `reason` and is the verb
  every prior "investigated, confirmed correct or already-explained, no code change needed" deviation
  in this ledger has used — entries 3, 9, 10, 15, 16, 20-25, 28, 29, 31 and 41 are all `deviation`-kind
  entries closed `waived` with a reason recorded, and none of them changed production code to close.
  Entry 42 is that same shape: an observation that a shipped assertion changed direction, confirmed
  correct against the code and the ruling it cites, with nothing to change. `windows fixed 42` would
  both lose the reason the task requires and misrepresent the entry as a repair rather than a
  confirmation.
