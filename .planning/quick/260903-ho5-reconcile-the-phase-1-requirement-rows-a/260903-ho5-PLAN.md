<the_governing_rule>

**Mark a row complete ONLY where measured evidence supports it. Where it does not, say so in the
record rather than marking it.**

This project has already made the opposite mistake. `05-VERIFICATION.md` certified a README sentence
as true that the code contradicted; the code review measured it false; plan 05-19 deleted the
sentence. That was ledger entry 33. A reconciliation pass that flips 46 cells to shipped because a
phase passed would repeat that failure at scale.

Every status this task changes carries a citation to the artifact and the assertion that justifies
it. A row that cannot be justified keeps a status that says what is true and gains a note saying why.

**Status vocabulary.** Every cell in the two verification-map tables ends up carrying exactly one of
these four strings. Define the vocabulary once, in the file, immediately above the first table that
uses it — **as a bulleted list, not as a table.** The table below is the plan's own copy; reproducing
it inside `05-VALIDATION.md` would put four more pipe-led lines carrying the vocabulary strings into
the file and break every count gate in this plan. Prohibition 9 says the same thing about the notes.

| Status string | Meaning |
|---|---|
| `✅ shipped` | The named test exists, is green, AND its named mutation was applied and failed a test at the tier the row's own `Automated Command` runs. Nothing else is recorded against it. |
| `⚠️ green, mutation failed nothing` | The named test is green and the named mutation left every tier green. The cell names what pins the behaviour instead, or states that nothing does. |
| `⚠️ green, blind at this tier` | The named test is green and the named mutation fails only at a tier the row's own `Automated Command` does not run. The cell names the tier that carries it. |
| `⚠️ shipped, blind to CR-0N` | The named mutation DID fail at the row's own tier, and the Test Quality Audit in commit `4631d46` separately marks the test that carries the row blind to blocker CR-0N, which then shipped. The cell names the tier and the blocker. |

The fourth string exists because a mutation and an audit answer two different questions. A mutation
asks whether the test can see the implementation move. The audit asks whether the test can see the
implementation being wrong. `05-VALIDATION.md`'s own gap-closure preamble draws exactly this line:
"the mutations tested whether the tests could see the implemented behaviour change, not whether the
implemented behaviour was right." A row can pass the first and fail the second, and three do.

**Do not collapse the fourth case into either neighbour.** Writing `⚠️ green, blind at this tier` on
a row whose mutation demonstrably failed at that tier understates a measurement, which corrupts the
record exactly as badly as overstating one. Writing plain `✅ shipped` on it drops the audit finding
that ledger entry 13 exists to preserve.

The two `⚠️ green` strings share that prefix and the gates count them together. The fourth string is
counted separately by the prefix `⚠️ shipped`.

</the_governing_rule>
